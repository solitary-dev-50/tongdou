# 铜豆实时语音后端架构

这份文档只负责一件事：

> 定义铜豆固件如何组织实时语音后端模块。

大白话说：  
这是铜豆自己的语音架构，不是小智固件。  
第一版只是兼容 `tongdou-server` 的 WebSocket 语音协议。

---

## 1. 一句话结论

固件里不要出现 `xiaozhi` 目录或一堆 `Xiaozhi*` 模块名。  
统一使用铜豆自己的命名：

```txt
firmware/src/tongdou_voice/
```

模块统一叫：

```txt
TongDouVoice*
```

协议来源写在文档和配置里：

```txt
backend_protocol = xiaozhi_esp32_serve
```

这样别人看代码时，会理解成：

> 铜豆固件有自己的实时语音后端层，当前兼容小智服务端协议。

而不是：

> 这是小智固件改壳。

---

## 2. 总体分层

```txt
AppCommandService
  -> RealtimeVoiceService
    -> TongDouVoiceClient
      -> TongDouVoiceProtocol
      -> TongDouVoiceWebSocketClient
      -> TongDouVoiceAudioCodec
      -> TongDouVoiceStreamQueues
      -> TongDouVoicePerfTracer
      -> AudioInput
      -> AudioOutput
```

职责边界：

| 层 | 只负责什么 |
| --- | --- |
| `AppCommandService` | 接收按钮、网页、MCP 的高层命令 |
| `RealtimeVoiceService` | 管理铜豆的一轮语音回合 |
| `TongDouVoiceClient` | 串起连接、上传、播放、打断、重连 |
| `TongDouVoiceProtocol` | 生成和解析后端协议消息 |
| `TongDouVoiceWebSocketClient` | 管 WebSocket 连接和收发 |
| `TongDouVoiceAudioCodec` | PCM 和 Opus 编解码 |
| `TongDouVoiceStreamQueues` | 管上行、下行短队列 |
| `TongDouVoicePerfTracer` | 打印语音性能打点 |
| `AudioInput` | 只采集麦克风 PCM |
| `AudioOutput` | 只播放 PCM 到功放 |

`App` 仍然只做三件事：

1. 初始化模块。
2. 每轮调用模块更新。
3. 连接模块事件。

`App` 不直接写 `hello`、`listen`、`abort`、Opus、WebSocket、`session_id`。

### 当前实机状态：2026-08-24

- N4R2 的 `2 MB` 四线 PSRAM 已在正式固件中启用并通过实机识别。
- 独立 Opus 自测可以完成 `960` 个采样点的编码和解码。
- 编解码初始化失败会阻止语音客户端继续连接，不能再出现 `codecReady=false` 但客户端报告准备完成。
- 设备已经完成 PCM、Opus、WebSocket 上行、后端收包、语音识别、对话模型、语音合成、下行解码和扬声器播放的完整回合。
- 后端完成正常告别并关闭本次会话后，设备能够回到空闲、自动重连并重新完成握手。
- 网页显式入口、MCP 工具入口、Logo 物理触摸和回复后的连续对话，均已验证复用同一条语音链路，没有入口专用上传实现。
- 连续对话按半双工运行：回复播放队列排空，等待 `120 ms`，发送 `auto listen start` 并立即上传；服务端做人声检测。
- 当前无需调整编码器和解码器生命周期；已删除不再使用的两份预录音缓存和本地简单音量门控，只保留语音回合有效时的短上传队列。
- 实机至少连续完成 `7` 轮自然追问。阶段 6 曾以本地 `20 s` 停止完成无人说话验证；阶段 7 已删除该正常收口职责，改由服务器无声时限统一裁决。
- 正常在线退出由服务器统一裁决：精确命令、语义退出、无人说话和设备手动请求共用一个出口，固定执行“告别音频 -> `tts stop` -> `goodbye`”。
- 铜豆收到 `goodbye` 后进入“正在退出”状态，禁止再次监听；最后一包音频的软件队列和扬声器硬件缓冲都排空后才回到空闲。
- 自动连续监听不再使用本地 `20 s` 作为正常收口；网络断开、发送失败或服务器无响应才走本地异常兜底。

## 3. 建议文件

目录：

```txt
firmware/src/tongdou_voice/
```

建议文件：

| 文件 | 单一职责 |
| --- | --- |
| `TongDouVoiceConfig.h/.cpp` | 保存服务端地址、设备编号、协议版本、音频参数 |
| `TongDouVoiceProtocol.h/.cpp` | 生成和解析 `hello/listen/abort/tts/llm` 等消息 |
| `TongDouVoiceWebSocketClient.h/.cpp` | 建立连接、带请求头、收发 JSON 和二进制 Opus |
| `TongDouVoiceAudioCodec.h/.cpp` | PCM16 和 Opus 互转 |
| `TongDouVoiceStreamQueues.h/.cpp` | 管 PCM 队列、Opus 队列、下行播放队列 |
| `TongDouVoicePerfTracer.h/.cpp` | 打印 `[voice] ...` 性能日志 |
| `TongDouVoiceClient.h/.cpp` | 对外提供实时语音客户端能力 |
| `TongDouVoiceState.h` | 定义语音后端状态枚举 |

不要新增：

```txt
firmware/src/xiaozhi/
```

也不要新增：

```txt
XiaozhiWebSocketClient
XiaozhiProtocol
XiaozhiVoiceClient
```

## 4. 当前兼容协议

当前第一版兼容：

```txt
xiaozhi_esp32_serve
```

但它只作为后端协议类型，不作为固件模块名。

配置建议：

```cpp
enum class TongDouVoiceBackendProtocol {
  CurrentCompatibleServer,
};
```

或者配置字符串：

```txt
backend_protocol = xiaozhi_esp32_serve
```

这样后续如果换服务端，可以扩展：

```txt
tongdou_cloud
local_voice_server
custom_websocket_voice
```

铜豆自己的模块名不需要跟着改。

## 5. 上行语音流水线

用户说话时，铜豆必须实时上传：

```txt
AudioInput
  -> PCM16 960 samples
  -> PcmFrameQueue
  -> TongDouVoiceAudioCodec
  -> OpusPacketQueue
  -> TongDouVoiceWebSocketClient
  -> 服务端
```

硬要求：

- 一边说，一边采音。
- 一边采音，一边 Opus 编码。
- 一边编码，一边 WebSocket 发送。
- 不等整句话录完再上传。
- WebSocket 发送不能阻塞采音任务。

队列策略：

| 队列 | 长度建议 | 满了怎么办 |
| --- | --- | --- |
| `PcmFrameQueue` | 3 到 5 帧 | 丢旧 PCM |
| `OpusPacketQueue` | 3 到 5 包 | 丢旧 Opus |
| 下行播放队列 | 3 到 5 包 | 丢旧播放包 |

原因很简单：  
实时语音宁愿丢一点声音，也不能越积越慢。

---

## 6. 下行播放流水线

服务端返回 Opus 后，铜豆要边收边播：

```txt
TongDouVoiceWebSocketClient
  -> Opus 二进制包
  -> DownlinkAudioQueue
  -> TongDouVoiceAudioCodec
  -> PCM16
  -> AudioOutput
  -> NS4168
```

`tts start` 不等于喇叭开始响。  
真正的 `speaker_start` 必须以第一包 PCM 成功写入 I2S 为准。

下行采样率规则：

- 铜豆上行可以固定 `16000 Hz`。
- 铜豆下行必须以服务端 `hello.audio_params.sample_rate` 为准。
- 第一版建议把服务端下行也配置成 `16000 Hz`。
- 后续再让 `AudioOutput` 支持 `16000 / 24000` 动态切换。

## 7. 协议消息边界

`TongDouVoiceProtocol` 只负责消息生成和解析。

### WebSocket 请求头

优先使用请求头：

```txt
Authorization: Bearer 服务端返回的token
Protocol-Version: 1
Device-Id: AA:BB:CC:DD:EE:FF
Client-Id: tongdou-demo
```

所以 `TongDouVoiceWebSocketClient` 选库时必须支持自定义请求头。

### hello

发送：

```json
{
  "type": "hello",
  "version": 1,
  "transport": "websocket",
  "features": {
    "mcp": false
  },
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

收到服务端 `hello` 后：

- 保存 `session_id`。
- 保存服务端下行 `audio_params`。
- 后续 `listen/abort/mcp` 消息都带 `session_id`。

### listen

开始：

```json
{
  "session_id": "...",
  "type": "listen",
  "state": "start",
  "mode": "manual"
}
```

结束：

```json
{
  "session_id": "...",
  "type": "listen",
  "state": "stop",
  "mode": "manual"
}
```

`listen stop` 必须等最后一包 Opus 发完后再发。

顺序：

```txt
停止采集新 PCM
  -> 等 PcmFrameQueue 清空
  -> 等 OpusPacketQueue 清空
  -> 确认最后一包 Opus 已发送
  -> 发送 listen stop
```

### abort

铜豆正在说话时，如果用户再次按按钮：

```txt
发送 abort
  -> 停止 AudioOutput
  -> 清空下行播放队列
  -> 开始新一轮 listen
```

消息：

```json
{
  "session_id": "...",
  "type": "abort"
}
```

## 8. 半双工规则

第一版先做半双工。

| 状态 | 规则 |
| --- | --- |
| `Listening` | 只录音，不播放 |
| `Speaking` | 只播放，不录音 |
| 用户打断 | 按按钮 -> abort -> 新一轮 Listening |

原因：

铜豆有喇叭，也有麦克风。  
没有回声消除时，边播边听容易把自己的声音录回去。

## 9. 状态机

```cpp
enum class TongDouVoiceState {
  Idle,
  Connecting,
  Handshaking,
  Ready,
  Listening,
  WaitingReply,
  PreparingSpeak,
  Speaking,
  Disconnected,
  Reconnecting,
  ReconnectBackoff,
  Failed,
};
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `Idle` | 未启动 |
| `Connecting` | 正在连接 WebSocket |
| `Handshaking` | 已连接，等待 `hello` |
| `Ready` | 可以开始语音回合 |
| `Listening` | 正在采音、编码、发送 |
| `WaitingReply` | 用户说完，等待服务端首个回复包 |
| `PreparingSpeak` | 收到 `tts start`，但喇叭还没响 |
| `Speaking` | 第一包 PCM 已写入 I2S，正在播放 |
| `Disconnected` | 连接已断 |
| `Reconnecting` | 正在重连 |
| `ReconnectBackoff` | 重连失败后短暂等待 |
| `Failed` | 本轮失败，等待剧情补救 |

状态转移：

```txt
Idle -> Connecting -> Handshaking -> Ready
Ready -> Listening -> WaitingReply -> PreparingSpeak -> Speaking -> Ready
Speaking -> abort -> Listening
任意联网状态 -> Disconnected -> Reconnecting -> Handshaking -> Ready
Reconnecting -> ReconnectBackoff -> Reconnecting
任意状态 -> Failed -> Ready
```

## 10. 性能打点

`TongDouVoicePerfTracer` 负责打印：

```txt
[voice] listen_start
[voice] first_audio_captured
[voice] first_opus_encoded
[voice] first_audio_sent
[voice] listen_stop
[voice] first_tts_packet_received
[voice] speaker_start
[voice] tts_done
```

每条日志带：

- 当前毫秒时间。
- 距离 `listen_start` 的耗时。

例子：

```txt
[voice] listen_start t=123456
[voice] first_audio_sent t=123522 dt=66
[voice] first_tts_packet_received t=125010 dt=1554
[voice] speaker_start t=125045 dt=1589
[voice] tts_done t=127400 dt=3944
```

判断方式：

| 现象 | 优先查哪里 |
| --- | --- |
| `first_audio_sent` 慢 | 铜豆采音、编码、发送 |
| `first_audio_sent` 快但 `first_tts_packet_received` 慢 | 服务端 ASR / LLM / TTS |
| `first_tts_packet_received` 快但 `speaker_start` 慢 | 铜豆播放缓冲 / I2S |

## 11. 和现有模块关系

### `RealtimeVoiceService`

保留它作为铜豆语音回合入口。

它负责：

- 开始一轮语音。
- 查询当前状态。
- 处理失败。
- 把失败事件交给剧情层。

它不负责：

- 拼 JSON。
- WebSocket 请求头。
- Opus 编码。
- 下行采样率。
- `session_id`。

### `AudioInput`

只负责：

- PDM 麦克风初始化。
- 读取 PCM16。
- 音量诊断。

它不知道：

- WebSocket。
- Opus。
- `listen start`。
- 服务端协议。

### `AudioOutput`

只负责：

- I2S 输出。
- 流式 PCM 播放。
- 停止播放。
- 清空播放缓冲。

建议接口：

```cpp
bool writePcm16Mono(const int16_t* samples, size_t sampleCount, uint32_t sampleRate);
void stopStream();
```

### `WebConfigServer`

后续只负责配置：

- 服务端地址。
- 是否使用 OTA。
- 设备编号。
- 连接测试。

它不直接发 `hello`，不直接发音频。

## 12. 第一版实现顺序

1. 新增 `TongDouVoiceConfig` 和 `TongDouVoiceProtocol`。
2. 新增 `TongDouVoiceWebSocketClient`，先连上服务端并发 `hello`。
3. 用 `listen detect` 文本确认服务端能回 TTS。
4. 做下行 Opus 解码和 `AudioOutput` 播放。
5. 做本地 Opus 编码 / 解码自测。
6. 做静音 Opus 上行。
7. 做真实麦克风流式上行。
8. 做 `listen stop` 停止屏障。
9. 做 `abort` 打断和半双工。
10. 做断线重连。
11. 接按钮 `5` 完整实时语音回合。
12. 接表情、灯光、电机表现。

这个顺序的目的：

> 先证明下行能播，再接麦克风。

否则一开始就接真实麦克风，出了问题很难判断是麦克风、Opus、WebSocket、ASR、TTS 还是 I2S。

## 13. 命名原则

对外命名：

```txt
TongDouVoice*
```

后端协议名：

```txt
xiaozhi_esp32_serve
```

不要把协议名变成固件目录名。  
不要让别人误以为铜豆固件是小智固件。

一句话：

> 铜豆是主体，小智服务端只是第一版兼容的语音后端。
