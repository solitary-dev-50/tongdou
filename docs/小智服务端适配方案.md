# 小智服务端适配方案

这份文档只负责一件事：

> 说明铜豆固件怎么接入平级目录里的 `tongdou-server` 服务端。

大白话说：  
小智服务端当“会听、会想、会说的大脑”，铜豆当“桌面上的小身体”。  
铜豆负责采音、播放、表情、灯光和动作；小智服务端负责语音识别、大模型回复和语音合成。

---

## 1. 一句话结论

铜豆固件适配小智服务端，优先走：

> **WebSocket 长连接 + Opus 音频包 + JSON 控制消息。**

第一版演示固件必须做实时语音，不走“先文字后语音”的主路线。

第一轮就按三件事做，而且这三件事必须是流水线，不是排队等上一件做完：

1. **铜豆实时上传**：用户一边说，铜豆一边采音、一边 Opus 编码、一边 WebSocket 发送。
2. **小智服务端流式处理**：语音识别、大模型、文字转语音都要用流式能力。
3. **铜豆流式播放**：服务端一边回传语音包，铜豆一边解码、一边通过喇叭播放。

文字触发只保留为开发排查手段，不进入演示主流程。

---

## 2. 本地服务端查到的关键事实

本地服务目录：

```txt
E:\ESP32-S3\tongdou-server
```

核心服务：

```txt
tongdou-server/main/xiaozhi-server
```

服务端启动后主要提供：

| 服务 | 默认地址 | 用途 |
| --- | --- | --- |
| `OTA` 地址 | `http://电脑IP:8003/xiaozhi/ota/` | 设备拿 WebSocket 地址和令牌 |
| `WebSocket` 地址 | `ws://电脑IP:8000/xiaozhi/v1/` | 设备和服务端实时通信 |
| 视觉接口 | `http://电脑IP:8003/mcp/vision/explain` | 视觉能力，铜豆第一版不用 |

小智服务端支持：

- `WebSocket` 协议。
- `MQTT + UDP` 协议。
- `Opus` 音频包。
- `ASR`，也就是语音识别。
- `LLM`，也就是大语言模型。
- `TTS`，也就是文字转语音。
- `MCP` 工具能力。

铜豆第一版只接：

- `WebSocket`
- `Opus` 音频
- 基础文字消息
- 基础语音收发

性能选型参考：

- 参考仓库：`https://github.com/xinnan-tech/xiaozhi-performance-research`
- 这个仓库不是服务端代码，而是小智各组件响应速度测试报告。
- 报告自己也说明：测试结果基于上游小智服务端架构，只适合作为本项目架构下的选型参考，不是严格权威的商用评测。

对铜豆最有用的不是“完整回复总耗时”，而是这条链路：

```txt
用户说完关键句
  -> ASR 首词出来
  -> LLM 首 token 出来
  -> TTS 首音出来
  -> 铜豆开始说话
```

大白话说：  
用户最在意的是“铜豆多久开始有反应”，不是它憋半天后能不能说一大段聪明话。

报告里全 API 调用推荐组合：

| 环节 | 推荐组件 | 报告里的关键指标 |
| --- | --- | --- |
| ASR | `XunfeiStreamASR` | 平均首词等待 `0.795` 秒 |
| LLM | `qwen-flash-2025-07-28` | 首 token `0.434` 秒 |
| TTS | `HuoshanDoubleStreamTTS` | 平均首音 `0.317` 秒 |

理想首响估算：

```txt
0.795 + 0.434 + 0.317 = 1.546 秒
```

这还没算网络、VAD 等待、铜豆缓冲、Opus 编解码和播放启动。  
所以铜豆第一版要按下面的体验线判断：

| 首响时间 | 体感 |
| --- | --- |
| `1.5` 秒以内 | 很像实时 |
| `1.5` 到 `2.5` 秒 | 可以接受 |
| `3` 秒以上 | 铜豆显得反应慢 |
| `5` 秒以上 | 像普通语音助手，不像桌面小生命体 |

铜豆第一版的优先级：

1. **TTS 首音快**：铜豆要尽快开口。
2. **ASR 流式快**：用户说话时服务端就要开始听。
3. **LLM 首 token 快**：先出第一句话，比完整大段回答更重要。
4. **回答内容聪明**：第一版不要追求最强大模型。

人格提示词也要短。  
不要第一版就塞几千字世界观，否则会拖慢首 token。

先不接：

- 摄像头。
- 小智原项目的智能家居控制。
- 小智原项目的设备管理后台。
- 小智原项目的移动端。
- 复杂 `MCP` 工具下发。

## 3. 通信方式定版

### 3.1 推荐方式

铜豆启动后：

1. 连接用户配置好的 WiFi。
2. 请求小智服务端 `OTA` 地址。
3. 从 `OTA` 返回结果里拿到 `WebSocket` 地址。
4. 建立 `WebSocket` 长连接。
5. 发送 `hello` 握手消息。
6. 后续通过这个连接收发文字和音频。

流程：

```txt
铜豆
  -> POST /xiaozhi/ota/
  <- 返回 websocket.url 和 token
  -> 连接 ws://电脑IP:8000/xiaozhi/v1/
  -> 发送 hello
  <- 服务端 hello
  -> 发送 listen / 音频包
  <- 服务端 stt / tts / Opus 音频包
```

### 3.2 演示版可用简化方式

如果小智服务端配置里关闭认证，也就是：

```yaml
server:
  auth:
    enabled: false
```

铜豆可以先跳过 `OTA`，直接连接：

```txt
ws://电脑IP:8000/xiaozhi/v1/?device-id=铜豆MAC&client-id=tongdou-demo
```

这个方式只适合第一轮联调。  
正式演示前，固件要优先使用 WebSocket 请求头传设备信息，不要只依赖 URL 参数。

原因很简单：  
URL 参数像临时写在门口的小纸条，请求头才像正式证件。后面一旦打开认证，或者服务端协议检查变严格，只靠 URL 参数很容易出现“连上后马上断开”。

## 4. 小智协议要点

### 4.1 连接参数

服务端要求连接时带上设备信息。

WebSocket 握手优先使用这些请求头：

```txt
Authorization: Bearer 服务端返回的token
Protocol-Version: 1
Device-Id: AA:BB:CC:DD:EE:FF
Client-Id: tongdou-demo
```

固件选 WebSocket 库时必须满足一个硬要求：

```txt
必须支持自定义 header
```

如果固件库暂时不好加自定义请求头，第一轮联调可以把参数放到地址后面：

```txt
ws://电脑IP:8000/xiaozhi/v1/?device-id=AA:BB:CC:DD:EE:FF&client-id=tongdou-demo
```

但这只能算临时方案。  
后续认证开启后，`Authorization` 也必须走请求头。

### 4.2 hello 握手

铜豆连接成功后，先发：

```json
{
  "type": "hello",
  "version": 1,
  "transport": "websocket",
  "features": {
    "mcp": true
  },
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

说明：

- `version: 1`：协议版本。
- `transport: websocket`：告诉服务端当前走 WebSocket。
- `format: opus`：音频用 Opus 编码。
- `sample_rate: 16000`：这里指铜豆上行音频采样率。
- `channels: 1`：单声道。
- `frame_duration: 60`：每包 60 毫秒。
- `mcp: true`：允许服务端通过同一条长连接调用铜豆明确开放的设备工具。
- 当前实时语音只开放创建、查询、删除提醒三个工具，不把语音后端配置、剧情播放等管理工具交给大模型。

`Device-Id`、`Client-Id`、`Authorization` 放 WebSocket 握手请求头。  
不要指望服务端一定从 `hello` 的 JSON 正文里读取设备编号。

服务端会回：

```json
{
  "type": "hello",
  "version": 1,
  "transport": "websocket",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  },
  "session_id": "..."
}
```

铜豆要保存 `session_id`。

如果服务端 `hello` 返回了 `session_id`，后续 `listen`、`abort`、`mcp` 消息都要带上它。

### 4.3 实时语音触发对话

这是第一版演示固件的主流程。  
这里的“实时”指：用户说话的同时，铜豆已经在发送音频包，不等一句话录完。

开始录音时发：

```json
{
  "session_id": "服务端返回的session_id",
  "type": "listen",
  "state": "start",
  "mode": "manual"
}
```

然后铜豆不断发送二进制 `Opus` 音频包。  
每包建议：

```txt
16kHz 单声道 PCM
每帧 960 个采样点
每帧 60 毫秒
编码成 1 个 Opus 包
通过 WebSocket 二进制发送
```

用户说完后发：

```json
{
  "session_id": "服务端返回的session_id",
  "type": "listen",
  "state": "stop",
  "mode": "manual"
}
```

服务端会做：

```txt
Opus 音频流 -> 流式语音识别 -> 流式大模型 -> 流式文字转语音 -> Opus 音频流回传
```

这里的几个专业词，大白话解释：

- `ASR` 是语音识别，就是把用户说的话变成文字。
- `LLM` 是大语言模型，就是生成回答。
- `TTS` 是文字转语音，就是把回答变成声音。
- `流式` 就是边来边处理，不等整段内容攒完。

### 4.4 文字触发对话

这是开发排查用的捷径，不作为演示主流程。  
当怀疑麦克风、Opus 编码或录音链路有问题时，可以直接发：

```json
{
  "session_id": "服务端返回的session_id",
  "type": "listen",
  "state": "detect",
  "text": "刚才有什么邮件？"
}
```

服务端会把这句话当成识别结果，直接进入大模型回复流程。

这个方式只用来确认：

- WebSocket 能连上。
- 服务端能回复。
- 铜豆能收到服务端文字状态。
- 铜豆能收到服务端下行音频包。
- 铜豆能播放服务端音频。

不要把这个方式放进众筹视频主线。

### 4.5 一轮实时语音时序

```txt
用户看向铜豆
  -> 操盘手点按钮 5，铜豆进入聆听
  -> 铜豆发送 listen start
  -> 用户说“刚才什么邮件？”
  -> 铜豆一边采音，一边 Opus 编码，一边 WebSocket 发送
  <- 服务端流式 ASR 持续接收音频
  -> 用户说完或铜豆检测到尾音结束，发送 listen stop
  <- 服务端返回 stt 文本或最终识别文本
  <- 服务端开始流式 LLM
  <- 服务端返回 tts start
  <- 服务端返回 sentence_start
  <- 服务端流式 TTS 返回 Opus 音频包
  -> 铜豆一边接收，一边解码，一边播放
  <- 服务端返回 tts stop
  -> 铜豆回待机或轻点头
```

第一版不要写死“录音 3 到 5 秒再上传”。  
可以有一个最长聆听保护时间，但音频上传必须从用户开口时就开始。

### 4.6 手动录音消息

开始录音时发：

```json
{
  "session_id": "服务端返回的session_id",
  "type": "listen",
  "state": "start",
  "mode": "manual"
}
```

中间发送二进制 `Opus` 音频包：

```txt
16kHz 单声道 PCM
每帧 960 个采样点
每帧 60 毫秒
编码成 1 个 Opus 包
通过 WebSocket 二进制发送
```

用户说完后发：

```json
{
  "session_id": "服务端返回的session_id",
  "type": "listen",
  "state": "stop",
  "mode": "manual"
}
```

`listen stop` 不能插队。  
按钮松开或检测到用户说完后，发送顺序必须是：

```txt
停止采集新的 PCM
  -> 等 PcmFrameQueue 清空
  -> 等 OpusPacketQueue 清空
  -> 确认最后一包 Opus 已经 WebSocket send
  -> 发送 listen stop
```

如果 `listen stop` 比最后一包音频先到服务端，服务端可能会认为这一句已经结束，后面的音频包就会被忽略或进入错误状态。

### 4.7 服务端返回消息

铜豆需要处理这些消息：

| 类型 | 示例 | 铜豆动作 |
| --- | --- | --- |
| `hello` | 服务端握手成功 | 标记已连接 |
| `stt` | `{"type":"stt","text":"刚才有什么邮件"}` | 可显示认真眼或短状态 |
| `tts start` | `{"type":"tts","state":"start"}` | 进入准备说话，不等于喇叭已响 |
| `tts sentence_start` | `{"type":"tts","state":"sentence_start","text":"..."}` | 可触发表情、灯光 |
| `tts stop` | `{"type":"tts","state":"stop"}` | 服务端本轮 TTS 结束，仍要等本地播放队列清空 |
| `llm` | `{"type":"llm","emotion":"happy","text":""}` | 可映射铜豆眼睛表情 |
| 二进制消息 | Opus 音频包 | 解码并通过喇叭播放 |

第一版可以先忽略：

- `mcp`
- `iot`
- `audio`

收到未知消息，只打印日志，不要卡死。

注意：  
这里说的是铜豆固件不用处理复杂的 `llm` 文本逻辑，不是说服务端可以不用大模型。  
服务端的 LLM 必须走流式输出。第一版可以只处理 `llm.emotion`，把 `happy`、`sad`、`angry` 这类情绪映射成铜豆眼睛表情；如果 `llm.text` 为空，就不要显示文字。

### 4.8 打断 abort

第一版必须支持 `abort`。  
否则铜豆正在说话时，用户再次按按钮开始说话，很容易出现旧音频还在播、新一轮又开始录的混乱状态。

发送：

```json
{
  "session_id": "服务端返回的session_id",
  "type": "abort"
}
```

最简单规则：

```txt
如果当前是 Speaking，用户再次按按钮：
  -> 先发 abort
  -> 停止本地 AudioOutput
  -> 清空下行音频队列
  -> 再发 listen start
```

第一版先做半双工：

| 状态 | 规则 |
| --- | --- |
| `Listening` | 只录音，不播放 |
| `Speaking` | 只播放，不录音 |
| 用户要打断 | 按按钮 -> abort -> 进入 Listening |

铜豆有喇叭也有麦克风。没有回声消除时，边播边听容易把自己的声音录进去。  
所以第一版不要硬上全双工。

## 5. 铜豆固件新增模块

建议新增目录：

```txt
firmware/src/tongdou_voice
```

### 5.1 文件职责

| 文件 | 只负责什么 |
| --- | --- |
| `TongDouVoiceConfig.h/.cpp` | 保存服务端地址、设备编号、协议类型、音频参数 |
| `TongDouVoiceOtaClient.h/.cpp` | 请求 `/xiaozhi/ota/`，拿 WebSocket 地址和令牌 |
| `TongDouVoiceProtocol.h/.cpp` | 生成和解析后端 JSON 消息 |
| `TongDouVoiceWebSocketClient.h/.cpp` | 管理 WebSocket 连接、收发文字和二进制包 |
| `TongDouVoiceAudioCodec.h/.cpp` | PCM16 和 Opus 的编码、解码 |
| `TongDouVoiceStreamQueues.h/.cpp` | 管理 PCM、Opus、下行播放短队列 |
| `TongDouVoicePerfTracer.h/.cpp` | 打印实时语音性能打点 |
| `TongDouVoiceClient.h/.cpp` | 把连接、录音、播放、状态串起来 |

职责边界：

- `TongDouVoiceWebSocketClient` 不知道表情、灯光、电机。
- `TongDouVoiceAudioCodec` 不知道服务端地址。
- `TongDouVoiceClient` 不直接写硬件引脚。
- `RealtimeVoiceService` 负责语音回合，不直接解析后端协议细节。

命名边界：

- 固件模块统一使用 `TongDouVoice*`。
- 不新增 `firmware/src/xiaozhi/`。
- 不新增 `Xiaozhi*` 固件类。
- `xiaozhi_esp32_serve` 只作为兼容的后端协议名或真实 URL 路径出现。

### 5.2 和现有模块的关系

当前已有：

```txt
RealtimeVoiceService
RealtimeAudioSender
AudioInput
AudioOutput
AppCommandService
ScenarioExecutor
```

适配后关系：

```txt
AppCommandService
  -> RealtimeVoiceService
    -> TongDouVoiceClient
      -> TongDouVoiceWebSocketClient
      -> TongDouVoiceAudioCodec
      -> TongDouVoiceStreamQueues
      -> TongDouVoicePerfTracer
      -> AudioInput
      -> AudioOutput
    -> ScenarioExecutor
```

大白话说：  
`RealtimeVoiceService` 还是铜豆自己的语音入口，`xiaozhi_esp32_serve` 只是当前兼容的后端协议。

## 6. 音频适配方案

### 6.1 上行：铜豆发给小智

铜豆麦克风当前已经是：

```txt
PDM -> PCM16 -> 16000 Hz -> 单声道
```

适配小智时要做：

```txt
PCM16 960 个采样
  -> Opus 编码
  -> WebSocket 二进制包
```

每个 `Opus` 包对应 60 毫秒。  
这和小智测试页里的做法一致。

固件里不要写成“读完一整段再编码再发送”。  
要拆成三个连续工作的小环节：

```txt
AudioInput 采音任务
  -> PcmFrameQueue
OpusEncode 任务
  -> OpusPacketQueue
WebSocket 发送任务
  -> 小智服务端
```

大白话说：  
这就像三个人传零件，第一个人刚拿到一小块声音，第二个人马上压缩，第三个人马上发出去，不等一整句话攒满。

第一版建议参数：

| 项目 | 建议值 | 说明 |
| --- | --- | --- |
| 采样率 | `16000 Hz` | 和当前麦克风、服务端测试页一致 |
| 声道 | `1` | 单声道 |
| 每帧采样点 | `960` | 对应 `60` 毫秒 |
| 上行格式 | `Opus` | WebSocket 二进制包 |
| 发送节奏 | 每产生 1 包就发 1 包 | 不等整句话结束 |
| 队列长度 | 3 到 5 包 | 只做短缓冲，避免声音越积越慢 |

队列满了要丢旧包，不要无限等待：

| 队列 | 满了怎么办 |
| --- | --- |
| `PcmFrameQueue` | 丢最旧 PCM 帧，并记录 `overflow` |
| `OpusPacketQueue` | 丢最旧 Opus 包，并记录 `overflow` |
| 下行播放队列 | 丢最旧播放包，避免越播越延迟 |

实时语音最怕“不卡，但越积越慢”。  
宁愿丢一点声音，也不要让延迟一路堆上去。

按钮 `5` 触发后，固件状态应该是：

```txt
Listening
  -> AudioInput 持续读 PCM
  -> OpusEncode 持续编码
  -> WebSocket 持续发送
```

`listen stop` 只表示“用户这句话结束了”。  
它不能表示“现在才开始上传音频”。

不要在 I2S/audio 回调或高优先级采音任务里直接 `WebSocket send`。  
网络发送可能阻塞，一阻塞就会丢采音节奏。正确做法是采音任务只把 PCM 放进队列，发送任务单独处理网络。

### 6.2 下行：小智发给铜豆

小智服务端下发的是 `Opus` 二进制包。

下行采样率不能默认写死 `16000 Hz`。  
铜豆上行固定 `16000 Hz` 可以，但下行播放必须以服务端 `hello.audio_params.sample_rate` 为准。

小智服务端配置里，`xiaozhi.audio_params.sample_rate` 默认可能是 `24000`。  
如果铜豆按 `16000` 去播 `24000` 的音频，声音可能变慢、变调、卡顿，听起来会很怪。

第一版有两个选择：

| 方案 | 做法 | 建议 |
| --- | --- | --- |
| 方案 A | 把服务端下行 `sample_rate` 配成 `16000` | 第一版优先用，少踩坑 |
| 方案 B | 铜豆 `AudioOutput` 支持 `16000 / 24000` 动态播放 | 后续更稳，但固件工作量更大 |

当前演示版建议先用方案 A。

铜豆要做：

```txt
WebSocket 二进制包
  -> Opus 解码
  -> PCM16
  -> I2S 输出到 NS4168
```

当前 `AudioOutput` 只有测试音和日志式 `playClip()`，还不能播放流式 PCM。  
所以需要给 `AudioOutput` 增加一个方法：

```cpp
bool writePcm16Mono(const int16_t* samples, size_t sampleCount, uint32_t sampleRate);
```

内部把单声道复制成左右声道，再写入 I2S。  
虽然喇叭是单声道功放，但 I2S 配置当前是左右声道输出，先保持这个写法最稳。  
如果第一版服务端固定 `16000`，`sampleRate` 可以先传 `16000`，但接口要给后续 `24000` 留位置。

### 6.3 Opus 库选择

需要给固件增加 Opus 编解码能力。

建议先做一次最小编译验证，目标是：

- 能把 `960` 个 `int16_t` 编成一个 Opus 包。
- 能把一个 Opus 包解码回 `960` 个 `int16_t`。
- 编译能过。
- 内存占用能接受。

如果 Arduino 库不顺，就考虑把官方 `xiaozhi-esp32` 里的 Opus 组件思路拆出来用。  
不要为了省半天时间，把音频编码写成一堆临时拼接代码。

## 7. 性能打点方案

这部分只定义方案，当前不改代码。

目标不是做漂亮日志，而是能看出“铜豆为什么慢”。  
第一版至少打这些串口日志：

| 日志 | 含义 |
| --- | --- |
| `[voice] listen_start` | 铜豆进入聆听，已经准备开始采音 |
| `[voice] first_audio_captured` | 麦克风采到第一帧有效 PCM |
| `[voice] first_opus_encoded` | 第一帧 PCM 编成 Opus |
| `[voice] first_audio_sent` | 第一包 Opus 通过 WebSocket 发出 |
| `[voice] listen_stop` | 用户这一句话结束，铜豆发出停止聆听 |
| `[voice] first_tts_packet_received` | 铜豆收到服务端第一包 TTS 音频 |
| `[voice] speaker_start` | 铜豆喇叭真正开始播放 |
| `[voice] tts_done` | 本轮语音播放结束 |

每条日志建议带毫秒时间戳：

```txt
[voice] listen_start t=123456
[voice] first_audio_captured t=123482 dt=26
[voice] first_opus_encoded t=123515 dt=59
[voice] first_audio_sent t=123522 dt=66
[voice] first_tts_packet_received t=125010 dt=1554
[voice] speaker_start t=125045 dt=1589
[voice] tts_done t=127400 dt=3944
```

这里的 `dt` 是从 `listen_start` 算起的耗时。  
大白话说：按秒表从铜豆开始听那一刻算，每一步花了多久。

服务端也要对应看这些点：

| 服务端打点 | 作用 |
| --- | --- |
| WebSocket 收到第一包音频 | 判断铜豆上传是否慢 |
| ASR 首词 | 判断语音识别首响 |
| LLM 首 token | 判断模型是不是太慢 |
| TTS 首音 | 判断语音合成是不是太慢 |
| 第一包 TTS 发出 | 判断服务端到铜豆之间是否慢 |

第一版目标：

| 指标 | 目标 |
| --- | --- |
| `listen_start` 到 `first_audio_sent` | 小于 `150` 毫秒 |
| `listen_start` 到 `first_tts_packet_received` | 尽量小于 `2500` 毫秒 |
| `listen_start` 到 `speaker_start` | 尽量小于 `2600` 毫秒 |
| 用户说完到铜豆开口 | 目标小于 `1500` 毫秒 |

如果 `first_audio_sent` 很慢，问题在铜豆固件。  
如果 `first_audio_sent` 快但 `first_tts_packet_received` 慢，问题在服务端链路。  
如果 `first_tts_packet_received` 快但 `speaker_start` 慢，问题在铜豆播放缓冲或 I2S 输出。

## 8. 状态机设计

新增状态：

```cpp
enum class TongDouVoiceState {
  Idle,
  OtaResolving,
  Connecting,
  Handshaking,
  Ready,
  Listening,
  WaitingReply,
  PreparingSpeak,
  Speaking,
  Disconnected,
  Reconnecting,
  ReconnectBackoff,
  Failed,
};
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `Idle` | 没启动连接 |
| `OtaResolving` | 正在请求 OTA |
| `Connecting` | 正在连 WebSocket |
| `Handshaking` | 已连接，等 hello 回复 |
| `Ready` | 可开始语音回合 |
| `Listening` | 铜豆正在采音并发给服务端 |
| `WaitingReply` | 用户停止说话，等服务端首个回复包 |
| `PreparingSpeak` | 收到 `tts start`，但喇叭还没真正响 |
| `Speaking` | 收到第一包 Opus 并成功写入 I2S，正在播放服务端语音 |
| `Disconnected` | WebSocket 已断开 |
| `Reconnecting` | 正在重连 |
| `ReconnectBackoff` | 重连失败后短暂等待 |
| `Failed` | 本轮失败，交给剧情层做补救 |

转移：

```txt
Idle -> OtaResolving -> Connecting -> Handshaking -> Ready
Ready -> Listening -> WaitingReply -> PreparingSpeak -> Speaking -> Ready
任意联网状态 -> Disconnected -> Reconnecting -> Handshaking -> Ready
Reconnecting -> ReconnectBackoff -> Reconnecting
任意状态 -> Failed -> Ready
```

`tts start` 只能进入 `PreparingSpeak`。  
真正的 `[voice] speaker_start` 必须以“第一包 Opus 解码成 PCM 并成功写入 I2S”为准。  
`tts stop` 也不能马上回 `Ready`，要等本地下行播放队列清空。

断线处理：

- 断线后进入 `Disconnected`，不要假装 `Ready`。
- 重连成功后必须重新发送 `hello`。
- 当前语音回合判失败，触发补救剧情。
- `hello` 超时、TTS 超时、WebSocket 发送失败，都要能回到可恢复状态。

不能在 `App` 里直接写这些细节。  
`App` 只调用：

```cpp
realtimeVoiceService_.startTurn();
realtimeVoiceService_.update();
```

## 9. 第一轮实现顺序

### 第一步：服务端配置准备

在小智服务端的 `data/.config.yaml` 里覆盖这些内容：

```yaml
server:
  websocket: ws://电脑IP:8000/xiaozhi/v1/

prompt: |
  你是铜豆，一个嘴上很凶、动作很怂的桌面搭子。
  你回答要短，不要长篇大论。
  你可以嘴欠，但不能羞辱用户。
  你不是智能音箱，也不是管家。
  你是帮助用户少惦记几件破事的小桌面伙伴。
```

如果先做演示，建议认证保持关闭：

```yaml
server:
  auth:
    enabled: false
```

第一版服务端组件优先这样选：

| 环节 | 首选 | 备选 | 先不要选 |
| --- | --- | --- | --- |
| ASR | 讯飞流式 ASR | 阿里流式 ASR、豆包流式 ASR | 非流式 ASR |
| LLM | `qwen-flash` | `qwen-turbo` | 超大模型、本地 72B、视觉模型 |
| TTS | 火山双流式 TTS | 讯飞流式 TTS、阿里流式 TTS | 普通整句 TTS |

提示词控制原则：

- 第一版人格提示词宁可短，不要长。
- 先保证首 token 快。
- 铜豆可以先说“哎，我听见了，等我想想”，不要憋 5 秒再说聪明长句。
- 不要一开始塞几千字世界观、长背景、复杂设定。

改模型时不要只填供应商配置。  
必须同步检查 `selected_module`，因为真正生效的是这里：

```yaml
selected_module:
  ASR: XunfeiStreamASR
  LLM: AliyunQwenFlash
  TTS: HuoshanDoubleStreamTTS
```

实际名字以当前 `config.yaml` 或智控台里的模块名为准。  
大白话说：只填了 API Key，但 `selected_module` 还指向旧模块，服务端还是会用旧东西。

Docker / 局域网部署时，`server.websocket` 必须写成铜豆能访问的电脑局域网地址：

```yaml
server:
  websocket: ws://192.168.1.25:8000/xiaozhi/v1/
```

不要写：

```txt
127.0.0.1
localhost
容器内 IP
```

这些地址对铜豆来说不是那台电脑。

认证策略：

- 联调阶段可以临时 `auth.enabled: false`。
- 拍众筹或公开演示前，不建议裸奔。
- 至少把铜豆的 `Device-Id` 加进服务端白名单，例如 `allowed_devices` 一类配置。

### 第二步：固件先直连 WebSocket

新增 `TongDouVoiceWebSocketClient`，先不要做 `OTA`。

目标：

- 固件能连上 `ws://电脑IP:8000/xiaozhi/v1/?device-id=...&client-id=tongdou-demo`
- 能发送 `hello`
- 能收到服务端 `hello`

验收：

```txt
串口输出：tongdou_voice connected
串口输出：tongdou_voice hello ok session=...
```

### 第三步：发送 `listen detect` 文本，确认服务端能回 TTS

这是开发排查步骤，不进入演示视频主线。

固件先发：

```json
{
  "session_id": "服务端返回的session_id",
  "type": "listen",
  "state": "detect",
  "text": "刚才有什么邮件？"
}
```

验收：

- 服务端能收到文字。
- 服务端能进入 LLM。
- 服务端能返回 `tts start`、`sentence_start` 和二进制 Opus 音频包。

这一步先证明下行链路是通的。  
否则一上来就接真实麦克风，出了问题很难判断是麦克风、Opus 编码、WebSocket、ASR、TTS 还是 I2S 播放。

### 第四步：播放下行语音

先做 Opus 解码和 I2S 播放。

验收：

- 铜豆能把服务端回来的语音从喇叭播出来。
- 收到 `tts start` 只进入 `PreparingSpeak`。
- 第一包 PCM 成功写入 I2S 时，才打印 `[voice] speaker_start`。
- `tts stop` 后，要等播放队列清空再回 `Ready`。

### 第五步：本地 Opus 编码 / 解码自测

先不接麦克风，做最小闭环：

```txt
测试 PCM
  -> Opus 编码
  -> Opus 解码
  -> PCM 对比 / 播放测试
```

验收：

- 能把 `960` 个 `int16_t` 编成一个 Opus 包。
- 能把这个 Opus 包解回 `960` 个 `int16_t`。
- 编译通过，内存占用可接受。

### 第六步：静音 Opus 上行

先发送静音 Opus 包，不接真实麦克风。

验收：

- `listen start` 发出。
- 静音 Opus 包按 `60` 毫秒节奏持续发出。
- 等 `OpusPacketQueue` 清空后再发 `listen stop`。
- 服务端不崩、不乱状态。

### 第七步：确认服务端流式配置

确认小智服务端选的是：

- 流式 ASR。
- 流式 LLM。
- 流式 TTS。

验收：

- WebSocket 收到音频包后，服务端立即进入 ASR 队列处理。
- LLM 输出第一段文本时，TTS 队列马上收到文本。
- TTS 生成第一批 Opus 包后，服务端马上下发给铜豆。

### 第八步：真实麦克风流式上行

接入 `AudioInput.readPcm16()`：

```txt
每 60 毫秒收集 960 个采样
编码成 Opus
马上通过 WebSocket 发出二进制包
```

开始时发：

```json
{"type":"listen","state":"start","mode":"manual"}
```

结束时发：

```json
{"type":"listen","state":"stop","mode":"manual"}
```

验收：

- 用户对铜豆说一句话。
- 铜豆说话过程中持续发送 Opus 包。
- 服务端能边收边送进流式 ASR。
- 服务端能识别出文本。
- 铜豆能播出回答。

同时验收 `mode=manual` 和 `mode=auto`：

- 先用 `mode=manual`。
- 再用 `mode=auto` 做对照。
- 如果某个流式 ASR 在 `manual` 下异常，先换 ASR，不要先怀疑铜豆麦克风。

### 第九步：实时语音回合控制

按钮 `5` 不再只是播放固定摘要，而是启动一轮实时语音：

```txt
按钮 5
  -> 显示认真眼 / 信封图标
  -> 发送 listen start
  -> 用户说话时持续采音、编码、发送
  -> 用户说完后发送 listen stop
  -> 服务端流式 ASR / LLM / TTS
  -> 铜豆持续接收、解码、播放服务端语音
  -> 回待机
```

验收：

- 用户真的对铜豆说“刚才什么邮件？”。
- 服务端能识别出这句话。
- 铜豆播出的回答来自服务端，不是固件预录音。

### 第十步：接铜豆表演

把服务端状态映射到铜豆表现：

| 服务端事件 | 铜豆表现 |
| --- | --- |
| 连接成功 | 轻轻眨眼 |
| 开始听 | 认真眼、低亮白光 |
| 收到 `stt` | 点头或认真眼 |
| `tts start` | 醒着说话状态 |
| `sentence_start` | 根据文本简单选择表情 |
| 二进制音频播放中 | 灯光弱呼吸 |
| `tts stop` | 回待机或开心眼 |
| 连接失败 / 超时 | 识别失败补救剧情 |

## 11. 需要修改的现有文件

### 11.1 `platformio.ini`

需要增加：

- WebSocket 客户端库。
- Opus 编解码库。

具体库名先通过最小编译验证确定。  
不要一次性塞多个音频库，避免依赖打架。

WebSocket 客户端库必须支持：

- 自定义请求头：`Authorization`、`Protocol-Version`、`Device-Id`、`Client-Id`。
- 发送二进制 raw Opus 帧。
- 收到二进制帧时能直接交给 Opus 解码。

`version=1` 时，二进制帧就是 raw Opus。  
不要自己加自定义包头，否则服务端可能按错误音频解析。

### 11.2 `AudioOutput`

新增：

```cpp
bool writePcm16Mono(const int16_t* samples, size_t sampleCount, uint32_t sampleRate);
void stopStream();
```

用途：

- 播放服务端返回的语音。
- 停止播放时清空 I2S 缓冲。

`sampleRate` 第一版可以先固定传 `16000`，前提是服务端下行也配置成 `16000`。  
后续如果服务端返回 `24000`，这里要能切换 I2S 播放参数。

### 11.3 `RealtimeAudioSender`

从“只统计”改成“交给铜豆语音后端发送”。

建议改为持有一个引用：

```cpp
TongDouVoiceClient& voiceBackend_;
```

或者先让 `RealtimeVoiceService` 直接调用 `TongDouVoiceClient`，后续再整理。

### 11.4 `RealtimeVoiceService`

新增：

- 铜豆语音后端状态查询。
- 开始语音回合时连接检查。
- 用户停止说话后，等待队列清空再发送 `listen stop`。
- `Speaking` 状态下再次开始听时，先发送 `abort`。
- 半双工控制：听的时候不播，播的时候不录。
- 语音后端失败时触发 `VoiceRecognitionFailed` 事件。

### 11.5 `WebConfigServer`

后续需要增加配置项：

- 小智 OTA 地址。
- 小智 WebSocket 地址。
- 是否跳过 OTA 直连。
- 设备名。
- 连接测试按钮。

第一轮可以先写死在固件常量里，等链路通了再进网页配置。

## 12. 不改小智服务端的部分

第一轮不改小智服务端代码。

只改配置：

- `server.websocket`
- `server.auth.enabled`
- `prompt`
- `selected_module`
- `ASR / LLM / TTS` 的实际供应商配置

原因很简单：  
小智服务端已经有完整链路，铜豆先按它的协议做客户端。  
等铜豆跑通后，再考虑给小智服务端加铜豆专用插件。

### 12.1 服务端必须选流式模块

这次演示不是“上传一段音频文件再等回答”。  
服务端配置必须满足：

| 环节 | 必须能力 | 本地代码里看到的方向 |
| --- | --- | --- |
| 语音识别 | 流式识别 | 选择 `InterfaceType.STREAM` 的 ASR |
| 大模型 | 流式输出 | `llm.response()` 要能一段一段产出文本 |
| 文字转语音 | 流式合成 | 选择带 `stream`、`_stream` 或队列式 TTS 的实现 |

本地服务端已经有这些流式方向：

- `core/providers/asr/aliyun_stream.py`
- `core/providers/asr/aliyunbl_stream.py`
- `core/providers/asr/xunfei_stream.py`
- `core/providers/asr/doubao_stream.py`
- `core/providers/tts/aliyun_stream.py`
- `core/providers/tts/alibl_stream.py`
- `core/providers/tts/xunfei_stream.py`
- `core/providers/tts/huoshan_double_stream.py`
- `core/providers/tts/minimax_httpstream.py`
- `core/providers/tts/index_stream.py`

配置时要避开非流式语音识别，例如普通 `aliyun.py`、`baidu.py`、`openai.py` 这类“整段识别”的路径。  
大白话说：铜豆前面已经边说边传，服务端后面也必须边听边干活。

### 12.2 服务端流式验收

服务端单独验收时看三件事：

1. 铜豆开始发 Opus 包后，服务端马上把包放进 `asr_audio_queue`。
2. 用户没完全说完时，流式 ASR 已经在接收音频。
3. 大模型刚产出第一段文字，TTS 就开始合成，不等完整回答结束。

## 13. 铜豆专用能力

基础语音链路跑通后，按能力白名单逐项接入：

### 13.1 实时语音提醒工具（已接入）

当前服务端可以通过设备 MCP（模型上下文协议）调用：

- `tongdou.reminder.create`：创建一次性提醒。
- `tongdou.reminder.list`：查询固件真实保存的提醒。
- `tongdou.reminder.delete`：删除已有提醒。

设备握手为：

```json
{
  "features": {
    "mcp": true,
    "goodbye": true
  }
}
```

完整时序：

```text
用户说提醒要求
  -> 服务端识别文字并理解时间
  -> 相对时间整理成 delaySeconds
  -> 明确日历时间整理成 localDateTime
  -> 服务端调用铜豆提醒工具
  -> 固件用本地已同步时钟换算、校验并写入 ReminderStore
  -> 固件返回真实创建结果
  -> 服务端根据结果生成语音确认
  -> 到点后 ReminderManager 在固件本地触发
```

固件仍是提醒数据和到期执行的唯一裁判。MCP 只负责调用，不保存提醒；工具没有返回成功前，服务端不能对用户说“记下了”。

创建提醒的时间参数必须三选一：

| 参数 | 用途 | 示例 |
| --- | --- | --- |
| `delaySeconds` | “五分钟后”这类相对时间 | `300` |
| `localDateTime` | “今天 19:10”这类本地日历时间 | `2026-08-24 19:10:00` |
| `dueAt` | 外部已经从可信时钟获得的 Unix 秒级时间戳 | `1787569800` |

大模型禁止自己心算 Unix 时间戳。固件时间未同步、时间参数多传或少传、时间已过期时，创建必须失败。

当前不向语音大模型开放电量、语音后端配置、剧情播放等其他设备工具。以后每增加一个工具，都必须单独说明用途、风险和验收办法。

### 13.3 动态提醒播报与离线兜底（已实机落地）

提醒到期后，固件仍负责准时触发，服务端负责生成包含具体提醒正文的铜豆口吻台词并完成在线语音合成。大模型可以润色表达，但不得改写药量、金额、时间、地址等关键提醒内容。

在线播报失败时，固件按以下固定顺序兜底：

```text
OLED 立即显示具体提醒正文
  -> 播放当前语言的一条通用异常播报
  -> 等语音在喇叭里真正播放完
  -> 喇叭播放“嘀、嘀、嘀”三声本地提示音
  -> OLED 继续保留提醒正文，等待用户确认或超时处理
```

通用异常播报建议为：

> 当前无法使用在线语音，请查看屏幕上的提醒内容。

多语言资源不得全部打包进固件。服务端保存所有语言版本，固件只保留当前语言的一套资源包。资源包包含欢迎语、配网、验证码、升级、错误提示、数字播报、`offline_notice.ogg` 和固定界面小字库；其中语音文件使用 Ogg 容器封装 Opus 音频。设备永久存储中始终只占一套当前语言资源，语言无关的短提示音尽量由固件实时生成。

语言切换时，设备先把完整新资源包下载到 2 MB 外部扩展内存，完成大小、摘要和格式校验后，再覆盖唯一的持久资源槽，最后保存新语言。单资源槽不能同时保证严格的掉电原子替换；若写入期间断电，启动校验必须识别损坏状态，临时退化为 OLED 提示和三声提示音，并在网络恢复后重新下载。铜豆不为极低概率的掉电窗口长期浪费第二份资源包空间。

固定界面只下载当前语言实际需要的小字库。用户输入的任意提醒正文不引入完整多语言字库，而是在提醒创建时由服务器预先渲染为 128×48 单色图片并随提醒保存；每张未压缩图片为 768 字节，12 条提醒约占 9 KB。

如果当前语言资源包缺失、校验失败或异常播报无法解码，固件跳过语音，直接显示 OLED 正文并播放三声提示音。三声提示音由固件实时生成，不保存成音频文件。

## 16. 必须避免的坑

1. WebSocket 必须优先使用请求头：`Authorization`、`Protocol-Version`、`Device-Id`、`Client-Id`。
2. `hello` 必须包含 `version` 和 `transport`。
3. `version=1` 时，二进制帧必须是 raw Opus，不要加自定义包头。
4. 收到服务端 `hello` 后，必须保存 `session_id`。
5. 后续 `listen`、`abort`、`mcp` 消息尽量带 `session_id`。
6. 上行采样率可以固定 `16000`，但下行采样率要以服务端 `hello` 为准。
7. 第一版建议把服务端下行 `sample_rate` 配成 `16000`，避免铜豆端重采样。
8. `listen stop` 必须等最后一包 Opus 发送完成后再发。
9. WebSocket 发送不能阻塞采音任务。
10. 队列满时丢旧包，不要无限等待。
11. `tts start` 不是 `speaker_start`，真正 `speaker_start` 以第一包 PCM 写入 I2S 为准。
12. `Speaking` 状态下再次开始听，必须先 `abort` 并清空播放队列。
13. 第一版先半双工，不做边播边听。
14. 服务端不要只填 provider 配置，必须检查 `selected_module`。
15. Docker / 局域网部署时，OTA 返回的 WebSocket 地址不能是 `localhost`、`127.0.0.1` 或容器内 IP。
16. 断线、`hello` 超时、TTS 超时都要回到可恢复状态，不要卡死。
17. 未知 JSON 消息只打印，不阻塞状态机。
18. 每一轮语音必须打印 `listen_start`、`first_audio_sent`、`first_tts_packet_received`、`speaker_start`、`tts_done`。
