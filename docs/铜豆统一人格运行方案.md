# 铜豆统一人格运行方案

状态：实施前方案  
日期：2026-08-26

## 一句话结论

铜豆的性格不能只靠一段大模型提示词，也不能每句话都通过 MCP 工具临时决定。正确做法是：服务器统一决定“怎么说”，语音协议传递“这句话是什么情绪”，固件稳定执行表情、灯光和动作，MCP 只负责显式设置人格模式和调用具体能力。

## 1. 为什么要做这项工作

当前铜豆已经具备实时语音、提醒、唤醒、退出、表情和灯光等基础能力，但这些能力还没有共用同一套人格出口。

结果是：普通对话偶尔像铜豆，唤醒、提醒或退出时又变成客服、播报员或者通用语音助手。用户看到的是同一个铜豆，实际听到的却像几个不同角色轮流说话。

这次要解决的不是“多写几句俏皮台词”，而是建立一套长期可维护的统一人格运行机制。

## 2. 已确认的现状

### 2.1 人格定义已经存在

现有文档已经明确铜豆是谁：

> 嘴上很凶，动作很怂；爱提醒，爱邀功，但不会真的给用户添乱的小桌面搭子。

人格宪法、三种人格剧本、声音风格、剧情包、表情、灯光和动作规则都已经有基础。问题不在“没有设计”，而在“设计没有完整进入运行链路”。

### 2.2 服务器说话出口没有统一

目前至少存在这些独立出口：

| 说话出口 | 当前来源 | 主要问题 |
| --- | --- | --- |
| 普通对话 | 设备角色提示词加通用基础提示词 | 有部分铜豆描述，但仍容易生成通用助手口吻 |
| 唤醒回复 | helloHandle.py 内的随机固定台词和缓存音频 | 包含“请吩咐”“等候您的指令”等客服腔 |
| 到期提醒 | reminder/announcement.py 的独立提示词 | 只保证短和正文准确，没有完整铜豆人格 |
| 正常退出 | conversationExitHandle.py 的固定告别语 | 时序正确，但人格没有跟随当前模式 |
| 工具执行回复 | 大模型根据工具结果自由组织 | 容易回到模板化确认语 |
| 异常和离线 | 固件本地剧情与当前语言资源 | 能兜底，但与在线人格模式尚未统一 |

### 2.3 当前人格按钮没有真正控制服务器说话

固件中的 set_personality 当前只执行一件事：修改 ScenarioContext.personality。

它存在三个问题：

1. 只保存在运行内存，重启后恢复默认值。
2. 没有同步给服务器，所以普通语音对话不知道用户选了什么模式。
3. 网页默认把 balanced 显示为已选择，但没有先读取设备真实状态。

因此现在的人格按钮更像“本地剧情测试开关”，还不是正式的人格设置。

### 2.4 情绪字段已经收到，但没有形成表现闭环

现有协议能够解析 llm 消息中的 emotion，并保存到 lastEmotion，但 VoiceVisualFeedback 只按“听、想、说、退出”四类语音状态切换固定表情和灯光。

也就是说，固件知道铜豆正在说话，却不知道它这句话是在得意、心虚、关心还是嘴硬。

### 2.5 当前情绪依赖表情符号，不够可靠

服务器当前通过大模型回复开头的第一个表情符号推断情绪，再发送 llm 情绪消息。这会造成两个问题：

1. 为了驱动表情，台词被迫带表情符号，口语听起来容易像网络聊天机器人。
2. 同一个表情符号只能表达粗糙情绪，不能表达铜豆特有的“嘴硬后马上怂回来”。

正式方案不能继续把表情符号当成人格协议。

## 3. 目标与非目标

### 3.1 本次目标

1. 让普通对话、唤醒、提醒、工具确认和退出都像同一个铜豆。
2. 保留 gentle、balanced、dramatic 三套不同演法。
3. 让人格模式可保存、可查询、可同步、重启不丢。
4. 让服务器发出的语义情绪能稳定驱动固件表情和灯光。
5. 让 MCP 有清晰边界，不成为每句话都要经过的中间层。
6. 给后续多语言人格台词留下统一入口。

### 3.2 本次不做

1. 不更换大模型、语音识别或语音合成供应商。
2. 不让大模型直接发送电机速度、灯珠颜色或屏幕像素。
3. 不给每句话都增加电机动作。
4. 不把所有剧情台词一次性塞进固件。
5. 不让人格系统改动已经跑通的采音、编码、播放和退出时序。
6. 不把用户长期记忆和铜豆人格混在一起。

## 4. 必须遵守的总原则

### 4.1 核心身份只有一个

三种人格模式不是三个不同角色，也不是从温柔逐级叠加到发疯。

- gentle：温柔提醒，重点是克制和有分寸。
- balanced：嘴欠打工搭子，作为默认模式。
- dramatic：彻底戏精，重点是更会演，不是更吵。

它们都必须遵守人格宪法，不能改变铜豆的存在意义和安全边界。

### 4.2 在线说话由服务器统一裁决

服务器生成正常在线台词，因此它必须是正常在线人格的唯一话语裁判。

固件不能在服务器回复后再拼一条本地人格台词，否则会出现重复说话、语气打架和时序混乱。

### 4.3 固件只执行稳定的语义动作

服务器只发送“得意、心虚、关心、困惑”等语义编号。固件负责把编号映射成已经审核过的表情、灯光和可选动作。

服务器禁止直接控制：

- 电机方向和速度。
- 灯珠具体亮度和颜色值。
- OLED 像素。
- 动作持续时间。

### 4.4 高频状态不表演

“正在听、正在想、正在说”仍然是基础状态反馈，不因为人格模式改变而增加动作。

人格表现只在一句回复开始时选择一次，而且默认只改变表情。电机动作只允许在低频、明确、安全的剧情中出现。

### 4.5 人格不能掩盖真实错误

可以说“我刚才卡了一下”，但日志和诊断必须保留真实错误码。不能用“脑子打了个嗝”把断网、解码失败或存储损坏藏起来。

## 5. 总体运行结构

~~~text
用户输入或设备事件
        ↓
服务器识别意图和场景
        ↓
统一人格策略
  ├─ 选择当前人格剧本
  ├─ 约束台词长度和口吻
  ├─ 选择语义表情
  └─ 决定是否允许低频剧情
        ↓
服务器输出：台词 + 表情语义 + 强度
        ↓
语音协议传输
        ↓
固件执行：播放语音 + 表情 + 灯光 + 受控动作
~~~

MCP 位于能力调用侧：

~~~text
用户明确要求设置或执行某项能力
        ↓
大模型或控制台调用 MCP
        ↓
统一设置服务或业务服务执行
        ↓
真实结果返回服务器
        ↓
服务器仍按统一人格策略组织最终回复
~~~

## 6. 各模块职责

| 模块 | 只负责什么 | 明确不负责什么 |
| --- | --- | --- |
| 人格宪法 | 定义铜豆是谁和不能做什么 | 不保存运行状态，不直接生成硬件动作 |
| 服务器人格策略 | 把身份、模式、场景和语言组合成说话约束 | 不直接控制硬件参数 |
| 服务器说话出口 | 按统一策略生成或选择最终台词 | 不各自维护互相冲突的人格定义 |
| 人格设置存储 | 按设备保存当前人格模式 | 不决定具体台词和剧情 |
| 语音协议 | 传递人格模式、语义表情和执行结果 | 不解释人格含义 |
| 固件人格设置服务 | 保存服务器确认过的模式并提供本地查询 | 不自行改写服务器台词 |
| 固件表现映射 | 把语义编号映射为表情、灯光和受控动作 | 不理解用户自然语言 |
| MCP | 显式设置、查询或调用能力 | 不承担每句话的人格生成 |
| 网页控制台 | 显示真实模式并发起修改 | 不先假装设置成功 |

## 7. 统一人格策略

### 7.1 固定核心

服务器每一轮普通对话都必须带上不可被聊天历史覆盖的固定核心：

1. 铜豆是桌面搭子，不是客服、上级、管家或主人仆从关系。
2. 先解决用户的问题，再露一点性格。
3. 默认一到两句话；高频确认尽量一句话。
4. 可以嘴欠，但不能羞辱、审判或制造负罪感。
5. 可以聪明，但不能假装拥有不存在的能力。
6. 嘴上可以凶，身体表现必须怂、小、短、可中断。
7. 不主动堆表情符号，不靠网络流行语硬装人格。
8. 不在每次回复末尾强行追问。

### 7.2 三套演法

三种模式使用同一身份核心，但分别选择不同的台词节奏和表现分支。

| 模式 | 台词节奏 | 表情倾向 | 动作边界 |
| --- | --- | --- | --- |
| gentle | 温和、直接、少吐槽 | 开心、认真、关心 | 高频场景不动，低频只轻点头 |
| balanced | 先解决问题，再轻轻嘴硬或邀功 | 得意、眯眼、心虚、委屈 | 仅明确剧情做小晃或前探后缩 |
| dramatic | 短小舞台感，演完立刻收 | 震惊、紧张、凶后变怂 | 仅用户主动或低频彩蛋做短动作 |

人格路由必须按“同一事件的三套剧本”选择，不能继续用枚举大小比较，把 dramatic 当成自动继承全部 balanced 规则。

### 7.3 台词生成结构

普通回答优先采用这个结构：

1. 第一部分直接回答或确认真实结果。
2. 第二部分可选地补一句铜豆式反差。

例如用户问当前音量：

- 不合格：“您好，当前设备音量为百分之百，请问还需要什么帮助？”
- gentle：“现在是百分之百，已经挺响啦。”
- balanced：“现在百分之百。小喇叭都顶到头了，别再拧我了。”
- dramatic：“百分之百！本豆的小喇叭已经在拼命营业了。”

### 7.4 禁用口吻

统一人格策略必须拦住以下表达：

- “等候您的指令”。
- “请随时吩咐我”。
- “请问还有什么可以帮助您”。
- “主人”。
- “任务已成功执行”。
- 没有真实依据的“已经为您完成”。
- 连续使用多个表情符号。
- 为了显得聪明而写长篇说明。

## 8. 所有说话出口必须统一

### 8.1 普通对话

普通对话使用完整人格核心、当前模式、设备语言和真实工具结果。

人格核心必须放在稳定系统层，用户聊天内容和长期记忆只能补充偏好，不能覆盖铜豆身份。

### 8.2 唤醒回复

唤醒追求快，不需要每次调用大模型。服务器按当前模式和语言，从经过审核的短句池中选择并使用缓存语音。

要求：

- 一句话。
- 正常不超过约两秒。
- 不说“请吩咐”和“等候指令”。
- 同一小段时间内避免连续重复。

中文示例：

| 模式 | 示例 |
| --- | --- |
| gentle | “我在呢，你说。” |
| balanced | “在呢，耳朵借你用一下。” |
| dramatic | “本豆上线。说吧，什么大事？” |

### 8.3 到期提醒

提醒正文必须逐字保留，任何人格润色都不能修改时间、姓名、药量、金额和单位。

结构固定为：短人格前缀或后缀 + 完整提醒正文。大模型输出不满足完整包含正文时，立即使用当前语言、当前模式的安全模板。

### 8.4 工具执行回复

所有工具回复必须以真实返回值为依据：

- 成功才说成功。
- 失败要说清原因和下一步。
- 查询类工具必须播报真实值，不能根据聊天历史猜。

工具本身不返回最终人格台词，只返回结构化事实；最终口吻仍由服务器人格策略统一生成。

### 8.5 正常退出

退出时序继续保持现有定版：服务器先生成或选择告别语，再发送 goodbye，固件等喇叭排空后回到空闲。

只替换告别语的来源，不修改已经跑通的退出时序。

### 8.6 异常和离线

网络故障时仍使用当前语言唯一一条通用异常播报，再加三声提示音。第一版不为三种人格分别保存离线音频，避免浪费闪存。

人格模式可以影响屏幕眼神，但不能增加更多本地语音文件。

## 9. 人格模式的唯一数据源与同步

### 9.1 唯一数据源

正常在线状态下，服务器保存的设备人格模式是唯一有效配置。固件只缓存服务器已经确认的值，用于本地剧情和离线表现。

这样做的原因是：在线台词由服务器生成，如果服务器不知道当前模式，固件本地切换得再漂亮也只是半套人格。

### 9.2 启动同步

服务器在 hello 回复中增加：

~~~json
{
  "personality": {
    "mode": "balanced",
    "version": 1
  }
}
~~~

固件收到后：

1. 校验模式是否为 gentle、balanced 或 dramatic。
2. 更新当前运行模式。
3. 与本地缓存不同才写入持久存储，避免反复擦写闪存。
4. 打印同步结果日志。

### 9.3 控制台修改

本地控制台不能再直接把内存值改掉就显示成功。正式流程为：

1. 控制台读取当前真实模式。
2. 用户选择新模式。
3. 固件向服务器发送设置请求。
4. 服务器校验并按设备保存。
5. 服务器返回明确确认。
6. 固件收到确认后更新缓存和本地剧情上下文。
7. 控制台读取确认后的真实值再更新选中状态。

离线时不能假装全局设置成功。第一版直接提示“当前离线，暂时无法同步人格设置”，继续使用上次已确认并缓存的模式。

### 9.4 会话内立即生效

模式修改成功后，服务器必须立即更新当前连接的人格上下文，并清除该设备旧的提示词缓存。否则控制台显示已经切换，当前会话仍可能继续使用旧人格。

下一轮回复必须使用新模式，不要求断开重连。

## 10. MCP 的正式边界

### 10.1 可以通过 MCP 做的事

- 查询当前人格模式。
- 在用户明确要求时切换人格模式。
- 主动触发经过审核的低频剧情。
- 查询真实设备状态。
- 创建、查询、延后和删除提醒。

### 10.2 不能通过 MCP 做的事

- 每句话都调用一次“生成性格”。
- 让大模型直接下发电机速度。
- 让大模型直接下发灯光颜色和闪烁时序。
- 让大模型直接画 OLED 像素。
- 在没有用户明确要求时偷偷切换人格模式。

### 10.3 人格工具要求

最终保留两个规范工具：

- tongdou.personality.get：查询服务器与设备当前已确认模式。
- tongdou.personality.set：用户明确要求切换时设置模式。

旧的 set_personality 可以在过渡期保留为兼容别名，但内部必须走同一个人格设置服务，不能再直接修改 ScenarioContext。

语音工具白名单只有在以下条件满足后才加入人格工具：

1. 模式已经能持久保存并同步。
2. 工具结果能返回服务器真实保存结果。
3. 大模型提示词明确要求只有用户直接提出切换时才能调用。
4. 已有误调用测试。

## 11. 语义表情协议

### 11.1 复用现有 llm 消息

不新增一套平行语音协议。扩展现有 llm 消息，增加明确的 expression 和 intensity 字段：

~~~json
{
  "type": "llm",
  "text": "",
  "emotion": "happy",
  "expression": "proud",
  "intensity": "low",
  "session_id": "..."
}
~~~

emotion 暂时保留用于兼容现有客户端；铜豆固件优先读取 expression。没有 expression 时，再把旧 emotion 映射成安全默认表情。

### 11.2 第一版语义编号

第一版只保留少量稳定编号：

| 语义编号 | 中文含义 | 默认表情 | 默认灯光 | 电机 |
| --- | --- | --- | --- | --- |
| neutral | 平静 | Awake 或 Smile | 低亮暖白 | 无 |
| cheerful | 开心 | Smile | 低亮暖白 | 无 |
| proud | 得意 | Proud | 暖色低亮 | 无 |
| cheeky | 嘴欠 | Squint 或 RollEyes | 暖色低亮 | 无 |
| shy | 心虚、怂回来 | Shy 或 Wronged | 很低亮暖白 | 无 |
| concerned | 关心 | Serious | 低亮暖白 | 无 |
| confused | 没听懂 | Confused | 暖色短闪 | 无，交给失败剧情时除外 |
| serious | 重要信息 | Serious | 低亮蓝白 | 无 |
| nervous | 异常紧张 | Nervous | 暖色短闪 | 无 |
| tired | 装累或低电量 | Wronged | 弱呼吸 | 无 |

这里的默认映射只负责普通语音回复。剧情包如果需要动作，仍通过已有剧情事件进入 ScenarioEngine，不从 expression 自动推导动作。

### 11.3 表情生效时序

1. 正在听：基础语音状态接管，显示倾听眼。
2. 正在想：基础语音状态接管，显示认真眼。
3. 服务器准备播放：先发送本轮 expression。
4. 第一段语音开始：固件显示语义表情和对应低亮灯光。
5. 连续对话下一轮：回到倾听眼，不插入睡觉眼。
6. 正常退出并排空：回到睡觉眼并熄灯。

提醒正文、低电量和故障仍高于普通语义表情，优先级规则不变。

### 11.4 不再依赖表情符号

服务器不能再要求大模型必须用表情符号作为每条语音回复的第一个字符。表情选择改为结构化语义，实际播报文本保持纯口语。

## 12. 人格口吻检查

第一版先使用确定性规则检查，不额外调用第二个大模型，避免增加延迟和费用。

检查内容：

1. 是否出现客服禁词。
2. 是否超过场景长度上限。
3. 是否包含多个表情符号或不适合播报的格式。
4. 是否在工具失败时谎称成功。
5. 是否改写提醒正文中的关键事实。
6. 是否包含不存在的设备能力。

处理方式：

- 普通对话发现轻微问题：清理格式后继续。
- 唤醒、提醒、退出等关键出口不合格：直接使用审核过的安全模板。
- 工具结果矛盾：禁止播报成功，使用真实失败说明。

口吻检查只做护栏，不能替代正确的人格提示词。

## 13. 多语言处理

人格核心是语义规则，不是中文俚语表。不同语言可以改写表达，但必须保留同样的角色关系和边界。

每种语言至少需要：

1. 三种模式的短唤醒句池。
2. 三种模式的正常告别句池。
3. 三种模式的提醒安全前缀。
4. 客服禁词和不自然表达清单。

语言切换后：

- 服务器立即按新语言和当前人格模式说话。
- 固件仍只保留当前语言一条通用离线异常播报。
- 不为三种人格复制三套离线音频。

## 14. 日志要求

人格链路必须能像语音链路一样用日志钉死。每次模式同步或回复至少能看到：

### 14.1 服务器日志

- device_id。
- personality_mode。
- personality_source：数据库、连接缓存或默认值。
- speech_exit：normal、wakeup、reminder、tool_result、farewell。
- expression。
- prompt_cache：命中、失效或重建。
- validator_result：通过、清理或安全回退。

禁止记录完整私密提示词和不必要的用户隐私。

### 14.2 固件日志

- personality hello received。
- personality apply ok 或失败原因。
- personality save skipped、saved 或失败原因。
- expression received。
- expression mapped。
- expression ignored 以及更高优先级原因。

## 15. 分刀实施顺序

### 第一刀：建立服务器统一人格策略

只做服务器内部人格规则和自动测试，不改协议、不改固件。

内容：

1. 把人格核心从零散设备提示词整理成一个统一策略模块。
2. 明确三种模式的剧本分支。
3. 增加客服禁词、长度和真实性检查。
4. 给普通问答和工具结果建立基线测试。

通过标准：相同输入在三种模式下身份一致、演法不同，不出现客服腔。

### 第二刀：统一唤醒、提醒和退出台词出口

只换台词选择和生成入口，不改原有唤醒速度、提醒可靠性和退出时序。

通过标准：同一模式下四类出口听起来是同一个铜豆；提醒正文不被改写；goodbye 顺序不变。

### 第三刀：人格模式持久化和启动同步

服务器按设备保存模式，hello 下发模式，固件缓存已确认值。

通过标准：断电重启、服务器重启和 WebSocket 重连后模式一致。

### 第四刀：修正控制台和人格 MCP

控制台读取真实值；设置必须等服务器确认；MCP 查询和设置统一走人格设置服务。

通过标准：页面选中值、服务器值、固件值三方一致；离线时不假装成功。

### 第五刀：结构化语义表情

服务器不再从第一个表情符号猜情绪，扩展 llm 消息，固件解析 expression 和 intensity。

通过标准：不带表情符号的语音台词仍能得到正确表情。

### 第六刀：固件表现映射

让 VoiceVisualFeedback 在“正在说”期间使用语义表情，同时保持优先级和无动作默认规则。

通过标准：听、想、说、提醒、故障、退出不抢状态；普通对话不乱动。

### 第七刀：完整实机验收

完成三种模式、多语言、提醒、工具、退出和异常场景矩阵测试，再决定是否增加低频动作剧情。

## 16. 验收矩阵

每个场景都分别测试 gentle、balanced、dramatic：

| 场景 | 必测内容 | 通过标准 |
| --- | --- | --- |
| 唤醒 | “你好，铜豆” | 快速、短句、无客服腔，随后正常进入监听 |
| 普通问答 | “你吃饭了吗” | 先回答，再体现模式；不长篇，不强行追问 |
| 事实查询 | “现在音量多少” | 调用真实查询，数值准确，口吻有性格 |
| 设置动作 | “音量调小一点” | 成功与失败都按真实工具结果回复 |
| 创建提醒 | “五分钟后提醒我喝水” | 创建成功信息准确，不编造编号和时间 |
| 到期提醒 | 包含数字、时间、姓名的正文 | 正文逐字保留，模式只改变安全前后缀 |
| 延后提醒 | “五分钟后再提醒我” | 同一事件增加延后节点，正点节点不丢 |
| 正常退出 | “退下吧” | 人格告别语后发 goodbye，喇叭排空后空闲 |
| 无人说话退出 | 保持安静 | 轻量告别或规定的安静出口，不继续监听 |
| 识别失败 | 故意说含糊 | 不怪用户，说明重说；真实错误日志可查 |
| 网络断开 | 回复中断网 | 不伪装正常告别，走当前语言唯一离线兜底 |
| 模式切换 | 控制台和语音切换 | 服务器、固件、页面一致，下一轮立即生效 |
| 重启恢复 | 断电再启动 | 使用上次服务器确认过的模式 |

## 17. 自动测试要求

服务器至少增加：

1. 三种模式普通回答口吻测试。
2. 唤醒句池禁止客服词测试。
3. 提醒正文完整保留测试。
4. 工具失败不能说成功测试。
5. 告别音频在 goodbye 之前测试。
6. 人格缓存修改后失效测试。
7. expression 不依赖表情符号测试。

固件至少增加：

1. 三个模式解析测试。
2. 非法模式拒绝测试。
3. 相同版本不重复写闪存测试。
4. expression 到 FaceExpression 映射测试。
5. 高优先级状态覆盖语义表情测试。
6. 旧服务器没有新字段时的兼容测试。

## 18. 回滚办法

每一刀必须独立提交，不能把服务器提示词、协议、固件表现和网页一起塞进一个无法定位问题的大提交。

回滚顺序：

1. 人格策略异常：退回旧提示词，不动语音协议。
2. 台词出口异常：退回对应出口句池，不动退出和提醒时序。
3. 同步异常：服务器停止下发 personality，固件继续使用 balanced 默认值。
4. 表情协议异常：固件忽略 expression，退回现有听、想、说基础视觉反馈。
5. MCP 异常：从语音白名单移除人格工具，不影响普通对话。

## 19. 完成标准

只有同时满足以下条件，才能说“铜豆人格链路跑通”：

1. 所有在线说话出口共用统一人格策略。
2. 三种模式不是简单强弱叠加，而是同一角色的三套演法。
3. 当前模式在服务器、固件和控制台三方一致。
4. 重启和重连后模式不丢。
5. 台词不依赖表情符号驱动表情。
6. 表情、灯光和动作不越过固件安全边界。
7. 提醒正文、工具结果和错误原因保持真实。
8. 原有语音采集、连续对话、提醒回应和正常退出时序没有被破坏。

## 20. 最终定案

人格系统的职责分配正式定为：

> 人格宪法定灵魂，服务器负责思考和说话，语音协议传递情绪，固件负责脸和身体，MCP 只负责明确的能力与设置。

后续不得用“给大模型多写几句提示词”代替完整人格链路，也不得让 MCP 或固件各自维护一套互相不一致的铜豆性格。
