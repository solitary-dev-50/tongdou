# 系统架构

本文锁定当前固件架构边界。

## 一句话原则

铜豆固件按职责分层：硬件只管硬件，剧情只管表现，提醒只管时间，网页只管配置，`App` 只负责把它们接起来。

## 分层

```text
SystemBootstrap
  -> App

App
  -> Hardware
  -> Scenario
  -> Reminder
  -> Firmware Update
  -> Realtime Voice
  -> Web
  -> MCP
```

## App 职责

`App` 只做三件事：

1. 初始化模块。
2. 每轮调用模块更新。
3. 把事件交给剧情层。

`App` 不允许直接写：

- 具体灯效。
- 具体电机动作。
- 具体台词。
- 存储格式细节。
- 电池百分比算法。
- 网页接口细节。

## 应用命令层

应用命令层负责接收网页或 MCP 的高层命令，并转交给应用内部模块。

| 文件 | 职责 |
| --- | --- |
| `AppCommandService.*` | 承接剧情、人格模式、实时语音回合、短动作、喇叭音量和网络信息查询命令 |

它不解析网络协议，也不直接操作硬件。

## 启动层

启动层负责系统入口和启动编排。

| 文件 | 职责 |
| --- | --- |
| `SystemBootstrap.*` | 系统启动入口，负责调用 `boot()` 和 `run()` |

`main.cpp` 只创建 `SystemBootstrap`，不直接初始化具体模块。

## 硬件层

硬件层只负责把真实硬件包成简单接口。

| 文件 | 职责 |
| --- | --- |
| `HardwareManager.*` | 按顺序初始化硬件，并统一更新硬件诊断 |
| `AudioInput.*` | PDM 麦克风输入和音量诊断 |
| `AudioOutput.*` | NS4168 I2S 输出、`SPK_CTRL / IO15` 控制和测试音 |
| `AudioCuePlayer.*` | 本地提示音播放，负责选择内置提示音并交给音频输出 |
| `AudioVolumeService.*` | 保存并应用统一喇叭输出音量，不修改麦克风增益或识别灵敏度 |
| `OggOpusDemuxer.*` | 只负责从 OGG 文件中拆出 Opus 音频包 |
| `BatteryMonitor.*` | 选择电量计或备用电压数据，读取 USB、充电和充满状态 |
| `Bq27220.*` | V9.4 电量计运行参数、分步采样和中断事件记录 |
| `BatteryConfig.h` | 单节电池容量、电压和读取周期常量 |
| `DisplayBus.*` | I2C 初始化 |
| `FaceDisplay.*` | OLED 表情显示 |
| `ImuSensor.*` | 读取 `QMI8658A` 姿态、倾斜、敲击和倾倒原始数据 |
| `LedPixel.*` | SK6812-EC20 控制 |
| `LogoTouchInput.*` | 读取铜豆 Logo 触摸输入，做基础滤波和触摸事件 |
| `MotorDriver.*` | AT8833CT 双电机控制、`MOTOR_SLEEP / IO42` 睡眠控制和 `MOTOR_FAULT / IO37` 故障检测 |
| `RadarSensor.*` | 雷达信号读取 |
| `HardwareSelfTestService.*` | 统一执行硬件自检命令 |

硬件层禁止知道剧情名。

V9 注意事项：

- OLED 和 `QMI8658A` 共用 `IO6/IO7` I2C，总线只能统一初始化。
- `LogoTouchInput` 只负责识别触摸，不负责“还债”“召唤”等剧情含义。
- `ImuSensor` 只负责输出姿态事件，不负责决定表情、灯光、动作或台词。
- `MotorDriver` 只负责电机输出、睡眠控制和 `nFAULT` 故障读取；检测到 `MOTOR_FAULT / IO37` 低电平时，上层应停止电机并进入降级处理。

## 诊断层

诊断层只负责把已有硬件接口组合成自检命令，方便串口和后续网页诊断复用。

| 文件 | 职责 |
| --- | --- |
| `HardwareSelfTestService.*` | 电池、雷达、麦克风、喇叭、灯和电机的自检入口 |

诊断层不保存业务配置，不决定剧情，不直接处理网页路由。电机方向和力度设置由诊断层转交 `MotorDriver`，由电机驱动负责持久化并在保存时停止电机。

V9 诊断层需要增加：

- I2C 扫描和 `QMI8658A` 原始数据输出。
- `IO4` Logo 触摸原始值、基线和触摸状态输出。
- `MOTOR_FAULT / IO37` 原始电平和电机动作后的故障状态输出。
- 电机和喇叭工作时的触摸误触检查。

## 剧情层

剧情层负责把事件变成表现。

| 文件 | 职责 |
| --- | --- |
| `ScenarioEngine.*` | 根据事件和上下文选择计划 |
| `ScenarioExecutor.*` | 非阻塞执行计划 |
| `ScenarioLibrary.*` | 内置剧情规则 |
| `FacePack.*` | 表情帧 |
| `LightPack.*` | 灯光帧 |
| `MotionPack.*` | 动作帧 |
| `VoiceLinePack.*` | 台词表 |

剧情计划由四部分组成：

- 表情
- 灯光
- 动作
- 台词

## 提醒层

| 文件 | 职责 |
| --- | --- |
| `DeviceLocaleStore.*` | 保存设备语言，用于提示音、验证码播报和后续语音服务默认语言 |
| `LocaleResourceStore.*` | 只读取并校验当前语言资源分区，不负责下载、语言切换或播放 |
| `TimeService.*` | 提供当前时间 |
| `ReminderStore.*` | 持久保存事件编号、节点类型、到期时间和正文，把节点位图放入独立原始分区，并在运行时把完整记录放入 PSRAM |
| `ReminderManager.*` | 按时间选出最早到期节点，并在真实送达流程结束后提交完成状态 |
| `ReminderAlertService.*` | 编排一个到期节点的正文显示、在线播报、离线声音兜底和播报完成事件 |

`ReminderManager` 只产生到期事件和提交送达结果，不直接控制硬件。`ReminderAlertService` 只负责一个提醒节点的播报编排，具体显示、联网和播放仍分别交给现有模块。普通一次性提醒使用一个节点；会议等事件可以用同一 `eventId` 关联提前、用户延后和正点节点。完整规则见 `docs/事件提醒系统实施方案.md`。

## 固件升级层

电池层由 `HardwareManager` 在共享总线初始化后启动，并在原有硬件更新之后推进。`Bq27220` 不使用延时等待，只在每次更新执行一次短读写；`BatteryMonitor` 提供缓存快照，数据失败或过期时选择 ADC 备用电压。网页与诊断不直接访问电量计。具体边界见 [BQ27220 电量计接入](BQ27220电量计接入.md)。

`BoardProfile.h` 只定义编译目标的主板身份。正式程序和固定救援程序共用这份定义；V9.0 保留 `tongdou-esp32s3`，V9.4 使用 `tongdou-esp32s3-v9.4`。主板版本不由电量计通信是否成功来猜测。出厂构建必须搭配同一主板的救援环境，发布时校验应用镜像内部的主板及软件版本标识。

固件升级层只负责把服务器的新版本通知安全地交给固定救援程序，不直接处理语音、剧情或提醒。

| 文件 | 职责 |
| --- | --- |
| `DeviceActivationService.*` | 在现有设备注册请求中上报正式版本，解析服务器返回的升级版本、下载地址、字节数和摘要 |
| `FirmwareUpdateService.*` | 校验升级通知、保存待升级信息、选择救援分区，并在新固件稳定运行后确认版本 |
| `recovery/main.cpp` | 只在救援分区运行，联网下载正式固件、逐块写入、核对摘要并切回正式分区 |

`App` 只判断当前是否适合重启：必须接着 USB 电源，没有语音或提醒正在进行，并且喇叭已经排空。满足条件后，`App` 停止当前动作并把升级交给 `FirmwareUpdateService`。

救援程序是固定的最小程序，不随普通远程升级一起覆盖。新正式固件第一次启动后保留 10 秒确认窗口；确认前崩溃或复位时，芯片启动器会回退到救援程序。救援程序不会反复安装已经启动失败的同一镜像，而是请求服务器上的另一版本。

完整发布、回退和测试步骤见 `docs/远程固件升级.md`。

## 实时语音层

实时语音层负责本地语音链路和一次语音回合：让本地麦克风链路常驻运行，在明确唤醒后开始上传，等待服务端回放，记录失败状态。

| 文件 | 职责 |
| --- | --- |
| `LocalAudioPipeline.*` | 负责常驻本地采音，以及语音回合有效时的短上传队列 |
| `RealtimeVoiceService.*` | 管理普通回合、连续对话回合、独立提醒播报和最长 8 秒的提醒回应回合 |
| `RealtimeAudioSender.*` | 接收出站音频帧并记录发送统计 |
| `VoiceVisualFeedback.*` | 把普通语音回合状态映射为表情和低亮灯光，不控制声音、电机或语音时序 |

当前定版原则：本地音频链路常驻，唤醒词和 Logo 单击只负责开始上传，不负责打开麦克风。详细方案见 `docs/语音链路常驻方案.md`。

连续对话时序已经按小智的半双工思路对齐：铜豆回复播放队列彻底排空后，等待 `120 ms` 扬声器尾音保护时间，再自动以 `auto` 模式开始下一轮上传。固件不再用本地平均音量门控决定用户有没有继续说话，而是交给服务端人声检测。

正常在线退出也由服务端统一裁决。精确命令、语义退出、无人说话和设备手动请求都进入服务器同一个出口；服务器先发送告别音频，再发送明确的 `goodbye`。铜豆收到后锁住连续监听，等软件音频队列和扬声器硬件缓冲都排空，再回到空闲。只有网络断开、发送失败或服务器无响应时，固件才走本地异常兜底。

实时语音层不决定铜豆怎么演。失败时只产生失败事件，由 `App` 交给剧情层选择“被咖啡呛到”等补救剧情。

普通语音回合的基础视觉反馈由 `VoiceVisualFeedback` 单独负责：正在听使用倾听眼和低亮青色，等待回复使用认真眼和低亮蓝紫色，播放回复使用开心眼和低亮暖白色。连续对话的短轮次空档保持上一状态，不闪睡觉眼；服务端正常退出并等喇叭排空后才切睡觉眼并熄灯。提醒正文和失败补救剧情优先，控制器遇到这两类状态必须释放屏幕和灯光。

### 实时语音后端层

实时语音后端层负责接外部语音服务，但命名必须保持铜豆主体。

当前定版：

- 目录使用 `firmware/src/tongdou_voice/`。
- 模块使用 `TongDouVoice*` 命名。
- 当前兼容协议是 `xiaozhi_esp32_serve`。
- 不使用 `firmware/src/xiaozhi/` 作为固件目录。
- 不使用 `Xiaozhi*` 作为铜豆固件模块名。

`2026-08-24` 实机验收后的准备状态规则：

- N4R2 的 `2 MB` PSRAM 必须先识别成功。
- 编解码器初始化失败时，语音客户端直接进入失败状态，不建立语音长连接。
- 后端握手成功不能单独代表语音准备完成；还必须确认当前需要的 Opus 编码和解码能力可用。
- Opus 原生错误码和错误文字必须进入设备状态，不能只返回一句笼统的“语音失败”。
- 正常半双工语音回合仍同时保留编码器和解码器；实测无需搬迁编解码器内部缓冲，也无需改成错峰生命周期。
- 麦克风采集任务和主循环发送保持解耦。主循环每轮最多发送一个 60 毫秒音频包，不能在一次循环里清空全部积压。
- 上行纯软件缓冲使用 PSRAM 中的 6 秒、192000 字节环形队列，覆盖当前 WebSocket 库 5 秒单次写等待；硬件直接采集小帧继续留在内部内存。
- 后端离开监听状态后立即停止上行；网络帧写坏后重建 WebSocket，会话失败事件处理完回到可重试状态，不能永久停在失败状态。

详细设计见 `docs/铜豆实时语音后端架构.md`。

## 网页层

本机网络入口展示由 `network/NetworkInfoService.*` 负责：读取当前真实地址，通过已有屏幕位图接口显示控制台入口并管理至少 30 秒阅读期限（等待回复和播报时延长）。自动进入下一轮监听不收起，服务端识别到新的 `stt` 文本后立即收起并恢复正常表情。普通语音表情让出屏幕，语音灯光继续更新，到点提醒优先。此服务不控制网络连接，也不启动独立语音播报。实现和验收见 [网络信息查询](网络信息查询.md)。

网页层负责配置，不负责剧情执行。

| 文件 | 职责 |
| --- | --- |
| `WebConfigServer.*` | HTTP 服务和路由，包括 WiFi、语言、时间、提醒和诊断入口 |
| `ScenarioConfigApi.*` | 剧情配置接口 |
| `ScenarioConfigStore.*` | 用户剧情配置存储 |

网页诊断接口只能调用诊断层，不允许直接控制硬件。

## MCP 层

MCP 层负责把铜豆能力暴露给电脑端大模型和实时语音服务器。

后续扩展能力优先走 MCP（模型上下文协议）事件入口。  
邮件、日程、吃药提醒、电脑任务完成提醒等外部能力，不应该直接塞进硬件层或剧情层。

边界是：

> MCP 和本地助手负责把外部世界整理成事件，铜豆内部模块负责决定怎么提醒、怎么显示、怎么演。

当前最小工具：

- `get_status`：获取联网、时间、硬件降级和保留能力。
- `create_reminder`：创建提醒。
- `list_reminders`：查询提醒。
- `delete_reminder`：删除提醒。
- `snooze_reminder`：延后刚播报的提醒，同时保留同事件的正点节点。
- `play_scenario`：按事件名触发剧情。
  - 彩蛋表演事件：`dance_show`（国内版）、`dance_show_global`（海外版）。
- `set_personality`：切换人格模式。
- `start_voice_turn`：开始一次实时语音回合。
- `voice_exit`：请求服务器按正常告别时序结束当前会话。
- `voice_status`：查看实时语音状态。
- `play_voice_response`：播放服务端返回文本。
- `fail_voice_turn`：报告语音回合失败并触发补救剧情。
- `tongdou.audio.get_volume`：读取设备当前真实喇叭音量，不修改设置。
- `tongdou.audio.set_volume`：设置或增减喇叭音量，设置会断电保存。
- `tongdou.network.show_info`：查询并显示铜豆本机网络地址和控制台访问提示。

MCP 层只处理协议和工具注册，不直接控制硬件。需要触发剧情或切换人格时，必须交给 `AppCommandService`。

### 语音短动作边界

四个动作工具经 `AppCommandService` 转交现有 `ScenarioExecutor`，共用唯一的 `GyroMotionController`，不另建电机控制器。前进复用 `NudgeForward`，后退复用 `ShrinkBack`，扭动复用 `TinyShake`；不开放轮速、时长、步数或循环参数。

应用命令层在提醒播报、安静模式、已知低电量或已有动作运行时拒绝新的移动请求；电机故障、陀螺仪未就绪由现有执行器拒绝启动。停止先于以上判断，取消动作和回正，但不取消提醒、不修改屏幕、灯光或声音。到期提醒仍能通过原有剧情入口接管电机。

工具返回 `motion_started` 只表示开始准备执行，不代表实际位移已完成；后续采样故障仍可能终止。语音仍是一方说完另一方再说，播音期间不能依靠语音即时急停。详细测试步骤见 [语音动作控制](语音动作控制.md)。

### 喇叭音量边界

铜豆只有一个统一喇叭输出音量，范围为 `0%` 到 `100%`，默认值为 `100%`。它在所有单声道音频送入 NS4168 前统一缩放，因此同时作用于服务器语音回复、本地提示音、离线通知和测试音。

音量设置保存在 NVS（芯片内部配置存储），重启和断电后继续生效。语音工具支持两种互斥参数：

- 明确说“调到 50%”或“静音”时传 `volume`，静音等于 `0`。
- 只说“大一点”或“小一点”时传 `delta`，默认步进分别为 `10` 和 `-10`。

询问“现在音量多少”时必须调用无参数的 `tongdou.audio.get_volume`，直接读取设备当前值。不能拿设置工具传空参数代替查询，也不能根据上一轮聊天记录猜测音量。

这项设置只管喇叭。它不能修改麦克风输入增益、人声检测阈值、唤醒词灵敏度或服务器语音合成配置，避免把“我听不清铜豆”和“铜豆听不清我”混成一个参数。

网页 `/api/mcp` 仍保留完整工具表，供本地调试和受控的本地助手使用。这样做是为了防止大模型误调用语音后端配置、诊断或剧情管理工具。

语音提醒的职责边界：

```text
服务端：把自然语言整理成相对秒数或明确的本地日历时间
MCP：传递结构化调用和真实执行结果
TimeService：用设备已同步时钟换算并校验到期时间
ReminderStore：持久保存事件关系、节点正文和预渲染显示位图
ReminderManager：本地判断到期，送达前不提前写完成
ReminderAlertService：立即显示正文，选择在线播报或本地异常兜底，并在声音结束后报告完成
剧情层：只负责提醒到点时的表情、灯光和动作
```

提醒创建禁止要求大模型心算 Unix 时间戳：

- “五分钟后”传 `delaySeconds: 300`。
- “今天 19:10”传 `localDateTime: 2026-08-24 19:10:00`。
- `dueAt` 只接受外部已经从可信时钟得到的绝对时间。
- “10 点开会，提前 10 分钟提醒”把 10 点作为正点时间，并传 `advanceSeconds: 600`；固件一次创建提前和正点两个关联节点。
- 刚播报后说“5 分钟后再提醒我”调用 `tongdou.reminder.snooze`，不能重新创建一个失去事件关系的孤立提醒。

`App` 只把实时语音传来的 MCP 请求接到 `McpServer`，不解析提醒内容，也不直接写提醒存储。

### 提醒播报与多语言资源边界

提醒到期后的正常路径使用服务端在线语音播报具体提醒正文；离线路径不尝试在固件内保存每条提醒的语音，也不把所有语言的异常播报一起打包进固件。

固件只维护一个当前语言资源槽。所有本地化欢迎语、配网、验证码、数字、升级、错误提示、`offline_notice.ogg` 和固定界面小字库组成一套语言资源包，其他语言版本全部由服务器保存。语音文件使用 Ogg 容器封装 Opus 音频，不再把多套语言文件嵌入应用程序镜像。

语言切换时，完整新资源包先下载到外部扩展内存，在内存中完成校验后再覆盖唯一持久资源槽，最后保存语言设置。外部扩展内存只负责下载和播放缓冲，不能承担断电后仍需存在的资源存储。单资源槽更新若遇到写入期间断电，启动校验负责发现损坏并重新下载；本项目不为保留新旧两份语言包设置双资源槽。

固定界面使用当前语言的小字库。任意提醒正文由服务器在创建提醒时预渲染为 128×48 单色图片，固件按提醒编号保存图片，避免下载中文、俄文等完整字库。

正常语音创建提醒时，服务端在发出 `tongdou.reminder.create` 前自动加入隐藏位图参数；事件提醒会分别生成提前和正点正文位图。提醒到期后的 `tongdou_reminder` 仍是独立播报，不进入普通聊天历史。最后一段声音真正排空并提交当前节点完成后，在线设备开放最长 8 秒的提醒回应收音，让用户直接说延后、取消或继续对话；无人说话时安静回到空闲。服务端可以让大模型润色语气，但只有结果原样包含完整提醒正文时才采用；否则直接使用当前语言固定前缀加原正文，避免药量、金额、时间等内容被改写。

离线或在线语音失败时，执行顺序固定为：OLED 显示提醒正文、播放当前语言通用异常播报、等待喇叭排空、实时生成三声提示音。异常播报文件不可用时，直接退化为 OLED 正文和三声提示音。

### 当前语言与提醒位图分区（已落地）

N4R2 的闪存末端分成两个原始数据分区：

- `locale`：`0x1C000`（112 KB），地址范围 `0x3D0000` 到 `0x3EBFFF`，只保存当前语言的一套资源。
- `reminder`：`0x4000`（16 KB），地址范围 `0x3EC000` 到 `0x3EFFFF`，保存最多 12 个提醒节点的 128×48 单色位图。

两者都不建立文件系统，避免和唤醒模型现有的文件系统分区混用。当前最大语言包为 `84,211` 字节，低于 112 KB 上限，给包头、目录和后续小幅增长仍留有空间。

资源包当前包含欢迎、配网、升级、激活码、激活错误、密码错误、通用离线播报和数字 0～9，共 17 个 Ogg Opus 文件。包头保存格式版本、语言、资源版本、文件目录、总大小，以及“文件目录＋资源正文”的 SHA-256 摘要；固件启动时会检查边界、必需文件和摘要，任何一项不对就拒绝使用整个资源包。

生成命令：

```bash
cd firmware
python tools/build_locale_pack.py --locale ru-RU --output .pio/build/esp32s3/locale_ru-RU.bin
```

当前播放器只从与设备当前语言一致的资源包读取本地化语音，并把单个待播文件读入外部扩展内存后解码播放。应用程序镜像不再包含欢迎、配网、验证码、数字等任何语言相关语音，也不存在英语隐藏回退。语言包不可用时，本地化语音明确失败；通用离线流程仍保住 OLED 正文和三声实时提示音。

第二阶段已经实现服务器下载和语言切换覆盖：语音服务器在 WebSocket `hello` 中明确下发资源接口地址和格式版本，固件不猜测服务器 HTTP 端口。`LocaleResourceUpdateService` 只负责把资源包下载到外部扩展内存并交给资源存储层；`LocaleResourceStore` 在覆盖前校验内存中的完整包，分块写入闪存后再从分区复核。`DeviceLocaleStore` 只有在这两次校验都成功后才保存新语言。

服务器接口为 `GET /tongdou/resources/{locale}.bin`，只允许固定语言和固定文件名。服务端发送前也会检查包格式、语言、目录、必需文件和摘要，避免把已损坏文件交给设备。

第三阶段已经把通用离线播报加入服务端八套资源包，并把资源版本升到 2。固件发现资源缺失、摘要损坏或资源语言与设备语言不一致时，不会在语音会话中抢占网络和喇叭；它会等服务器完成新一轮 `hello`、语音状态空闲后自动下载当前语言，失败后至少等待 60 秒再重试。

`AudioCuePlayer` 负责完整异常声音序列：先播放当前语言的 `offline_notice.ogg`，确认最后一段声音已经离开喇叭缓冲，再实时生成三声 1047 Hz 短提示音。离线播报缺失或解码失败时仍继续三声提示音。`AudioOutput` 只负责按指定频率发声，不知道“提醒”“离线”等业务含义。

事件编号、节点类型、提醒正文、时间和完成状态使用小尺寸 NVS 记录，避免把约 10 KB 位图硬塞进 NVS。位图按提醒槽位写入 `reminder` 原始分区，启动时用节点编号和校验值核对；完整 12 条运行记录共 `10,608` 字节，统一放入 PSRAM。旧格式会自动迁移为 `eventId=id` 的一次性节点，不能因结构升级清空用户提醒。首次把整条记录写入 NVS 的尝试曾在实机明确返回空间不足，因此该失败方案已经撤销。

动态提醒闭环已经完成实机验收：在线时 OLED 立即显示正文并播放服务端语音，最后一段声音真正排空后才结束；服务器离线时自动播放当前语言通用异常播报，排空后再发三声提示音；硬复位后正文位图仍能按提醒编号恢复。

正式构建分成两个明确入口：

- `esp32s3_factory`：用于全新出厂烧录，在写入程序和唤醒模型的同时，把默认 `en-GB` 版本 2 语言包写入 `locale` 分区。全新设备即使尚未联网，也能播放默认语言的欢迎、配网和验证码语音。
- `esp32s3`：用于普通开发和升级，只写程序、分区表、启动数据和唤醒模型，不触碰 `locale` 分区，避免升级把用户当前语言覆盖回英语。

语言无关的 `wake`、`success`、`error`、`low_battery`、`vibration` 五个短提示音仍嵌入程序镜像。除此之外，语言目录只作为资源包构建输入，不再链接进应用程序。启动时若设备语言与分区语言不一致，或者包头、目录、必需文件和摘要任一校验失败，固件会在联网且语音空闲后自动下载当前语言并修复唯一资源槽；离线期间不会假装播放另一种语言。

