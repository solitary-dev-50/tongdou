# 正式固件远程升级

## 一句话结论

铜豆 4 MB 闪存采用“固定救援程序 + 一份正式固件”：正式固件发现新版本后只负责安全交接，救援程序负责下载、校验、写入和失败恢复。

## 为什么不是两份正式固件

当前正式固件约 1.75 MB，而唤醒模型、语言资源、提醒位图和崩溃记录都必须保留。剩余程序空间总共约 2.8 MB，放不下两份完整正式固件。

如果硬塞双槽，每个槽只有约 1.4 MB，现有正式固件根本无法启动。固定救援程序只有约 718 KB，正式固件还能保留完整的 2 MB 分区，因此适合当前 `ESP32-S3-MINI-1-N4R2`。

## 升级流程

```text
正式固件上报当前版本
  -> 服务器返回新版本、下载地址、字节数、SHA-256 摘要
  -> 设备检查版本更高、地址同源、大小能装下、摘要格式正确
  -> 等 USB 电源接入，语音和提醒空闲、喇叭排空
  -> 安全停止当前剧情动作和电机
  -> 把升级请求写入独立 ota_req 分区
  -> 重启到固定 recovery 救援程序
  -> 救援程序连接已保存的 WiFi
  -> 下载并逐块写入 app0
  -> 核对实际字节数、SHA-256 和芯片镜像格式
  -> 启动新正式固件
  -> 新固件稳定运行 10 秒后确认成功
```

任何下载不完整、大小不符、摘要不符或镜像格式错误，都不会启动半成品。

## 启动失败和回退

芯片启动器已经启用首次启动回退。新正式固件确认前如果崩溃或复位，下次启动会回到固定救援程序。

救援程序会记住刚才启动失败的版本，不会原样反复重装。它用 `Device-Recovery: 1` 请求头向服务器查询另一份镜像：

- 有更高版本时，优先安装更高版本。
- 没有更高版本但服务器还保留其他版本时，可以安装较旧的已知可用版本。
- 服务器没有其他版本时，救援程序留在原地，每 30 秒复查，不覆盖自身。

这不是本地保存两份完整固件。旧正式固件不会一直留在芯片内；回退版本必须继续保存在服务器的 `data/bin` 目录里。

## 版本发布

### 主板升级通道（V9.0 / V9.4）

主板型号与软件版本分开管理，两块板共用源码、分别编译。默认入口继续支持 V9.0。

| 主板 | 升级型号 | 正式应用环境 | 出厂环境 | 救援环境 |
| --- | --- | --- | --- | --- |
| V9.0 | `tongdou-esp32s3`（保留原标识） | `esp32s3` | `esp32s3_factory` | `esp32s3_recovery` |
| V9.4 | `tongdou-esp32s3-v9.4` | `esp32s3_v94` | `esp32s3_v94_factory` | `esp32s3_v94_recovery` |

V9.4 另有 `esp32s3_v94_xiaozhi` 应用和 `esp32s3_v94_xiaozhi_factory` 出厂入口，供连接 `xiaozhi.me`。该版本不接受小智云下发的通用固件升级信息，也不进入铜豆服务器的 V9.4 镜像发布目录；构建、绑定和待做实机验收见 [V9.4 小智云版固件](V9.4小智云版固件.md)。

`firmware/include/tongdou/BoardProfile.h` 只负责主板身份定义；正式程序与救援程序共用它。V9.4 出厂入口自动构建并烧入 V9.4 救援程序，不能搭配 V9.0 救援镜像。救援程序不随普通远程升级更新，已经装错救援程序的板子需要通过 USB 重新烧入对应程序，不能只升级正式应用来纠正。

V9.4 的 BQ27220 电量计驱动与引脚接入已完成，见 [电量计接入说明](BQ27220电量计接入.md)。编译和模拟测试通过不代表 V9.4 硬件验收完成。

在 `firmware` 目录运行：

```powershell
# V9.0：原命令保持有效
platformio run -e esp32s3
python tools/publish_ota_image.py --check-only

# V9.4：独立构建、检查，文件名自动包含主板型号
platformio run -e esp32s3_v94
python tools/publish_ota_image.py --environment esp32s3_v94 --check-only

# V9.4 全新板出厂烧录（正式程序、救援程序、模型、默认语言）
platformio run -e esp32s3_v94_factory -t upload
```

实际发布时，把 `--check-only` 替换为 `--server-bin-dir '服务器的data/bin目录'`，保留 `--environment esp32s3_v94`。生成的文件为 `tongdou-esp32s3-v9.4_软件版本.bin`；V9.0 仍为 `tongdou-esp32s3_软件版本.bin`。

发布脚本检查固件内部的完整主板及软件版本标识，错主板、未重新编译的旧版本和无标识的旧构建都会拒绝发布。已发布的 V9.0 固件继续保留，无需重新命名或重新上传。现有 `tools/build_early_tester_release.py` 仍只用于 V9.0 早期测试完整包，不能用于 V9.4 打包。

当前相邻 `tongdou-server` 仓库中的 Python 单模块接口先按完整型号分组，再在组内选择更新或救援回退版本。没有对应型号时返回空下载地址，不回退到其他型号。每块主板都应单独保留稳定版；V9.4 第一版没有旧版可回退时，救援程序只能等待本通道出现可用镜像。

此结论不代表完整智控台已接通远程升级，也不代表运行中的远端服务器已更新或通过实机验收。不要手工把 V9.4 文件改成 V9.0 文件名；现有服务器按文件名分类，不识别被手工错命名的镜像内容。

发布前验证：同时放入两种主板的测试镜像，分别验证正常升级、失败后回退、仅剩另一型号镜像时不下发。再上板验证断网、断电、升级后原功能和语言、提醒数据保留。

本地验证记录（2026-09-14）：

- V9.0、V9.4 的正式程序和救援程序均编译通过。V9.4 救援程序在消除检查任务重叠后清理重编通过。
- V9.4 出厂环境展开检查通过，烧录列表的 `0x100000` 对应 V9.4 救援镜像；这次未完整编译出厂应用，也未连接设备烧录。
- `python -m unittest discover -s firmware/tools/tests -v` 共 6 项测试通过。发布测试覆盖错主板、旧版本、无标识和冲突标识；服务器测试直接执行相邻仓库的真实请求处理类与固件选择代码，网络、日志和认证用测试替身，不代表在线服务联调。
- 两个真实应用镜像均通过内部标识检查，并成功发布到本地 `.pio/ota-channel-check` 测试目录，文件名分别属于各自主板通道。未上传运行中服务器或远端仓库。
- 换机器复测时，服务器源码默认取相邻 `tongdou-server/main/xiaozhi-server`；可用 `TONGDOU_TEST_SERVER_DIR` 指定位置。找不到源码时两项服务器测试会跳过，不能把跳过记作通过。

以下发布示例以 V9.0 为例。两种主板目前共用软件版本配置，正式版本只改一处：

```ini
# firmware/platformio.ini
custom_firmware_version = 0.1.2
```

构建普通远程升级镜像：

```powershell
cd 'E:\ESP32-S3\Tong Dou\firmware'
platformio run -e esp32s3
```

先只检查版本、大小和摘要：

```powershell
python tools/publish_ota_image.py --check-only
```

确认无误后，用发布脚本复制到服务器：

```powershell
python tools/publish_ota_image.py --server-bin-dir 'E:\ESP32-S3\tongdou-server\main\xiaozhi-server\data\bin'
```

脚本会生成：

```text
E:\ESP32-S3\tongdou-server\main\xiaozhi-server\data\bin\tongdou-esp32s3_0.1.2.bin
```

发布脚本会先复制到服务器目录内的临时文件，复制完整后再改成正式文件名，避免服务器扫描到半个升级包。文件名必须是 `tongdou-esp32s3_版本.bin`。服务器扫描文件后自动计算准确大小和 SHA-256 摘要；设备不需要手工填写摘要。服务器默认缓存 30 秒，所以新文件放入后最多等约 30 秒再检查。

发布时至少保留当前稳定版和新版本两份文件。确认所有设备稳定后，才删除过旧镜像。

## 第一次迁移

旧正式固件只有一个大程序分区，和新布局地址重叠。第一次迁移不能远程完成，必须通过 USB 完整擦除并烧录一次：

```powershell
cd 'E:\ESP32-S3\Tong Dou\firmware'
platformio run -e esp32s3_factory -t erase
platformio run -e esp32s3_factory -t upload
```

`esp32s3_factory` 会一次准备并烧入：

- 启动器和新分区表。
- 中文本地唤醒模型。
- 固定救援程序。
- 正式固件。
- 默认 `en-GB` 语言资源包。

整片擦除会清掉 WiFi、服务器地址、语言和提醒。迁移后需要重新配网。后续普通远程升级只覆盖 `app0`，不会再清这些数据。

## 安全边界

当前救援程序只接受和设备注册接口同源的 `http://` 下载地址，并强制核对大小、SHA-256 和镜像格式。这能防止传输损坏、错文件和服务器配置串线。

但 SHA-256 只能证明“下载内容和服务器通知一致”，不能单独证明“服务器没有被冒充”。当前版本适合可信局域网或受保护的虚拟专网。准备直接暴露到公网前，必须补上带证书校验的加密连接或固件数字签名；不能把普通 HTTP 当成公网安全方案。

## 后续完整实机验收清单

v0.1.2 是早期测试交付，不以量产级远程升级压力测试为本次发布条件；以下项目不能因此标为已完成。

1. 完整擦除后执行出厂烧录，确认能够启动包内正式固件；启动选择数据决定入口，不要求首次启动一定显示救援日志。
2. 配网并设置服务器地址，确认设备注册请求上报的 `application.version` 与当前稳定版一致。
3. 服务器只放当前稳定版，确认设备不重启。
4. 构建并放入一个版本号更高的测试版，但不接 USB，确认设备只等待、不开始升级。
5. 接入 USB，确认设备在空闲时进入救援程序，下载后启动版本号更高的测试版。
6. 下载到一半断网，确认设备留在救援程序并在网络恢复后重试。
7. 下载到一半断电，重新上电后确认救援程序继续重试。
8. 把服务器文件改坏但不更新摘要缓存，确认摘要不符时不启动。
9. 制作一个启动确认前主动复位的测试版本，确认芯片回到救援程序。
10. 服务器同时保留稳定旧版，确认救援请求能拿到另一版本并恢复。
11. 成功升级后检查当前语言、提醒、音量、人格和服务器地址仍在。
12. 完整走一轮语音、提醒、屏幕、灯光、电机、雷达、触摸和姿态功能，确认升级没有破坏原功能。


## v0.1.2 配套管理端的升级边界

当前 Python 单模块服务已有按版本、大小、摘要下发镜像的实现；完整智控台的设备注册和升级回复尚未完整对齐救援程序所需元数据，不能把这两种部署方式混为已接通。v0.1.2 配套服务器按完整智控台交付，默认采用 USB 烧录，不自动放入远程升级镜像。固件包保留 OTA 单应用文件供兼容环境后续使用，不宣称随包管理端远程升级已验收。本次不扩展修改升级业务。
