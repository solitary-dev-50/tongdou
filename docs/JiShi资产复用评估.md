# JiShi 资产复用评估

本文用于判断 `可参考的项目/JiShi` 里哪些软件资产适合铜豆复用。

## 一句话结论

铜豆不是迁移到 JiShi，而是用 JiShi 已经跑通的软件体系，给铜豆 PCB 做板级适配。

JiShi 最新版已经有这些成熟资产：

- 分模式启动：配网模式 / 正常模式 / 离线模式。
- 分阶段硬件启动：基础反馈、音频和运动、视觉。
- 网页配置和硬件诊断控制台。
- 实时音频链路：采音、编码、发送、服务端音频回放。
- MCP 工具注册和协议处理。
- TTS 播放队列和音频回放服务。

## 可以优先复用

| JiShi 资产 | 铜豆价值 | 处理方式 |
| --- | --- | --- |
| `SystemBootstrap` | 启动模式选择、配网/正常模式分流 | 保留结构，改名为铜豆启动器 |
| `HardwareManager` | 分阶段启动、ready/degraded 状态 | 保留思想，硬件驱动全部换成铜豆版 |
| `AsyncConfigServer` + `data/test_console.*` | 配网、状态页、硬件诊断页 | 保留页面和接口结构，删摄像头/舵机，改成电机/雷达/剧情 |
| `SpeakerDriver` | I2S 输出、测试音、音量控制 | 参考写法，适配 `NS4168` 和铜豆引脚 |
| `TtsPlaybackService` + `TtsAudioQueue` | 服务端音频回放队列 | 后续接大模型语音输出时复用 |
| `RealtimeAudioPipeline` | 音频上传、队列、后台任务、错误状态 | 后续接大模型实时语音时复用 |
| `McpServer` / `McpToolRegistry` | MCP 协议和工具注册 | 保留核心结构，工具换成铜豆提醒/状态/剧情/动作 |
| `NetworkManager` / 配网策略 | 联网、断线重连、DNS 处理 | 按铜豆需求裁剪 |

## 需要改造复用

| JiShi 资产 | 为什么要改 | 铜豆做法 |
| --- | --- | --- |
| `MicrophoneDriver` | JiShi 是 `IM69D130 x2 + TLV320ADC5140` 双麦链路 | 不能直接搬，只参考 I2S 标准通道和音量诊断写法 |
| `ServoDriver` / `MotionEngine` | JiShi 是舵机运动 | 只借动作曲线思想，落地成铜豆双电机 |
| `RawMicDiagnostic` | JiShi 依赖 PSRAM 和复杂 WAV 诊断 | 第一版只做短采样和音量统计，后续再加 WAV 下载 |
| `DOAEngine` / `JishiDoaTracker` | 依赖双麦声源定位 | 铜豆单麦第一版不做声源定位 |
| `JishiRealtimeRuntime` | 绑定教育业务和 JiShi 状态 | 只拆实时语音链路，不整类搬入 |
| `LocalCommandEngine` | 业务命令不是铜豆人格命令 | 改成提醒、安静、确认、失败补救等事件 |

## 不进入第一版

- 摄像头。
- 双麦声源定位。
- 儿童教育业务。
- 儿童身份资料。
- 兴趣图谱。
- 成长记录。
- 多供应商复杂云端适配。

## 迁移顺序

1. 先把铜豆现有 `AudioInput` / `AudioOutput` 升级成 JiShi 风格的标准 I2S 通道写法。
2. 引入硬件自检服务：麦克风采样、喇叭测试音、灯、电机、雷达、电池。
3. 迁移网页诊断控制台，删掉摄像头和舵机，换成铜豆硬件。
4. 迁移启动编排：配网模式、正常模式、降级模式。
5. 迁移 MCP 工具注册结构，工具改成铜豆自己的状态、提醒、剧情、动作。
6. 再接实时音频链路和 TTS 回放。
7. 最后再考虑更复杂的人格、长期记忆和桌面智能体能力。

## 边界

铜豆第一版要先能演示、能提醒、能稳定工作。

JiShi 给的是成熟工具箱，不是让铜豆背上不属于它的业务包袱。

## 当前判断

现在最值得先做的是第 1 步：把铜豆当前的音频输入/输出底层从旧 I2S 接口，升级成 JiShi 最新版正在使用的标准 I2S 通道接口。

原因很简单：

- JiShi 这条链路已经跑过实机。
- 铜豆后面要接大模型语音，音频底座必须稳。
- 先改底层接口，不会影响剧情、提醒、网页和 MCP。
