# 语音链路常驻方案

> 本文定义语音链路的目标架构和交互边界。`2026-08-24` 已完成网页、MCP 工具、Logo 物理触摸和连续对话实机验收。内存与 Opus 编解码故障的证据和执行记录见 `docs/实时语音链路内存与编解码故障修复方案.md`。

## 1. 一句话结论

铜豆的麦克风采音链路在固件本地常驻运行，但待机时不上传环境声音。

Logo、网页、MCP 工具和后续唤醒词只负责启动第一轮上传；铜豆回复播放彻底结束后，连续对话会自动进入一轮临时上传，由服务端判断用户有没有继续说话。

雷达不负责唤醒语音。雷达负责判断人在不在附近、久坐提醒、屏幕和低功耗表现。

## 2. 先把几个词说清楚

### 2.1 本地音频链路

这里说的本地音频链路，指的是铜豆固件里的链路，不是本地电脑上的服务端。

当前已经实现的部分包括：

- 麦克风采音。
- 只在语音回合有效时，把实时音频放入上传队列。
- 由语音回合层取出音频、编码并发送。

后续本地唤醒词、降噪和唤醒词前置缓存还没有实现，不能把目标设计写成当前能力。

这条链路平时只在本地跑，不等于一直上传。

### 2.2 唤醒

唤醒不是打开麦克风。

唤醒的真实含义是：

```text
用户明确要和铜豆说话
  -> 固件发送 listen start
  -> 开始上传处理后的音频
  -> 服务端开始识别、思考、合成、回放
```

所以不管是唤醒词，还是 Logo 单击，本质上都是一个明确触发。

### 2.3 雷达

雷达只告诉铜豆：

> 附近大概有没有人。

雷达不能决定用户是不是在说话，也不能决定麦克风开不开。

原因很简单：

- 用户可能在铜豆背后。
- 雷达可能误判。
- 人在桌前不等于要和铜豆说话。
- 没人在雷达正前方，也不等于用户没有叫铜豆。

第一版里，雷达可以影响睡觉眼、待命表现、久坐提醒和省电策略，但不能作为语音入口的硬开关。

## 3. 为什么要这样做

本次连续对话修复前，服务端和首轮语音都已经能跑通，真正的问题在回复后的下一轮启动时序：

音频链路已经通了，语音链路也能跑通。真正的问题是：

```text
铜豆回复完成
  -> 固件先等本地简单音量门控判断“像不像人声”
  -> 用户紧接着说话时，第一段话反而被拿去估算环境底噪
  -> 后续阈值被抬高，真正的人声没有触发上传
```

这就像客人已经说话了，门卫却把客人的音量当成“大厅平时就这么吵”，随后把门槛抬得更高，后面当然听不见。

小智的做法更像：

```text
厨房一直热着
客人一开口
直接下锅
```

铜豆也应该走这条路线。

## 4. 和小智方案的关系

小智固件里，待机时并不是把麦克风链路彻底关掉。

可以参考这些源码位置：

- `E:\ESP32-S3\xiaozhi-esp32\main\application.cc`
- `E:\ESP32-S3\xiaozhi-esp32\main\audio\audio_service.cc`
- `E:\ESP32-S3\xiaozhi-esp32\main\audio\engines\afe_audio_engine.cc`
- `E:\ESP32-S3\xiaozhi-esp32\main\audio\wake_words\wake_word_audio_cache.cc`

小智的关键思路是：

| 状态 | 做了什么 |
| --- | --- |
| 待机 | 本地麦克风和唤醒检测在跑，不上传普通环境声音 |
| 听到唤醒词 | 发送 `listen start`，进入监听 |
| 监听中 | 把处理后的音频包发给服务端 |
| 唤醒词缓存 | 保留唤醒前后一小段声音，减少丢字 |
| 回答后 | 等播放队列真正排空，再根据连续对话模式重新进入监听和上传 |

铜豆不用照搬小智所有代码，但这条原则要借过来：

> 本地音频链路常驻，明确唤醒后才上传；进入连续对话后，每次回复播放排空就临时恢复上传，让服务端做人声判断。

## 5. 铜豆第一版状态设计

第一版建议把语音相关状态分成下面几层。

### 5.1 本地音频待命

```text
正常启动联网成功
  -> 本地音频链路启动
  -> 不上传普通环境声音
```

这时铜豆可以睡觉眼，也可以待命眼，但麦克风采音链路不应该冷掉。

### 5.2 明确触发

明确触发包括：

- 用户单击 Logo。
- 网页调试按钮，作为开发入口保留。
- MCP 工具命令，作为开发入口保留。
- 后续真正实现的本地唤醒词。

触发后流程：

```text
明确触发
  -> 发送 listen start
  -> 带上当前模式，比如 auto
  -> 立即上传后续实时音频
```

### 5.3 正在听

```text
正在听
  -> 固件持续发音频包
  -> 服务端做人声检测和语音识别
  -> 固件等待服务端返回文本和语音
```

第一版先不让固件决定复杂语义，只要保证音频别慢、别丢、别断。

### 5.4 正在说

```text
铜豆正在说
  -> 播放服务端语音
  -> 保留打断入口
```

后续要支持：

- 唤醒词打断。
- Logo 单击打断。
- 长按 Logo 退出。

第一版可以先保证说完后进入窗口期。

### 5.5 对话窗口

```text
铜豆说完
  -> 等下行播放队列彻底排空
  -> 等待 120 ms 扬声器尾音保护时间
  -> 自动发送 auto 模式的 listen start
  -> 立即上传实时音频
  -> 用户继续说话时不用再叫铜豆
```

窗口期内的关键规则：

- 回复播放期间不上传，保持第一版半双工，避免把铜豆自己的声音送回服务端。
- 播放排空后的连续对话窗口会临时上传，由服务端人声检测判断有没有用户说话。
- 不再使用本地平均音量门控决定是否开始上传。
- 这不是待机常开上传；只在用户已经启动一段对话后临时生效。
- 不是每句话都强制叫“铜豆”。
- 当前固件设置 `20 s` 监听保险上限；无人说话时再等待 `12 s` 服务端收尾，随后正常退出，不播放“识别失败”。

### 5.6 退出

退出来源：

- 服务端未检测到人声，连续对话窗口超时。
- 长按 Logo。

退出后：

```text
停止上传
  -> 可播短退出提示
  -> 回到本地音频待命
```

注意：回到本地音频待命，不等于关闭麦克风采音链路。

## 6. 雷达的新边界

雷达在语音链路里只提供环境状态，不做入口裁判。

### 6.1 雷达可以做

- 有人时，铜豆从睡觉眼变成待命眼。
- 长时间有人时，做久坐提醒。
- 无人一段时间后，降低屏幕、灯光和动作表现。
- 作为省电策略的参考条件。

### 6.2 雷达不能做

- 不能一检测到人就上传语音。
- 不能因为短暂无人就直接关掉语音链路。
- 不能挡住唤醒词和 Logo 触摸。
- 不能替代服务端人声检测或后续本地唤醒词检测。

一句话：

> 雷达管“桌前状态”，不管“用户是不是正在说话”。

## 7. 第一版落地顺序

### 第一步：锁定文档和日志

先把本文作为语音链路实现依据。

同时保留现在已经加上的时间线日志：

- 本地触发时间。
- `listen start` 发送时间。
- 第一帧麦克风采样时间。
- 第一包音频发送时间。
- 服务端收到第一包音频时间。
- 服务端检测到人声时间。
- 语音识别开始时间。

这样后面每改一步，都能看出是不是变好了。

### 第二步：拆出本地音频链路

已新增固件模块 `LocalAudioPipeline`。

它只负责一件事：

> 让麦克风采音常驻，并在语音回合有效时输出可上传音频。

职责边界：

| 模块 | 职责 |
| --- | --- |
| `AudioInput` | 只读 PDM 麦克风，做基础采样 |
| `LocalAudioPipeline` | 常驻采音；只在上传状态维护短上传队列并输出音频 |
| `RealtimeVoiceService` | 管理一次语音回合，发送 `listen start/stop`，消费可上传音频 |
| `App` | 只连接“回复播放完成”和“启动下一轮连续对话”两个事件，不做人声判断 |

不要把这些职责全塞进 `App`。

### 第三步：Logo 先按物理唤醒词处理

第一版先把 Logo 单击当成“物理唤醒词”。

Logo 单击时：

```text
本地音频链路已经在跑
  -> 发送 listen start
  -> 立即上传后续实时音频
```

Logo 只是第一轮对话的物理入口，不拥有单独的采音、编码或发送实现。

### 第四步：接入真正本地唤醒词

本地唤醒词成熟后：

```text
本地检测到“铜豆”
  -> 发送 listen start
  -> 上传唤醒词前后缓存
  -> 支持“铜豆 + 任务”一句话完成
```

这时才是正式的自然入口。

### 第五步：再做省电优化

省电优化不能抢在链路稳定前面。

后续可以按这些层级做：

| 场景 | 策略 |
| --- | --- |
| 有人 | 本地音频链路完整运行 |
| 短时间无人 | 降低屏幕和灯光表现，音频链路保持 |
| 长时间无人 | 可以降低本地检测频率，但保留唤醒能力 |
| 极低电量 | 明确进入省电模式，并给用户提示 |

## 8. 验收标准

第一版改完后，用这些标准判断是不是走对了。

### 8.1 必须做到

- 待机时，本地麦克风链路在运行。
- 待机时，不上传普通环境声音。
- Logo 单击后，能很快发出 `listen start`。
- Logo 单击后，第一包音频不能明显慢于当前版本。
- 一轮回答播放彻底结束后，等待 120 ms，再进入连续对话上传窗口。
- 窗口内继续说话，不需要再叫铜豆。
- 窗口无人说话时正常退出，不能当成语音识别失败。
- 雷达无人不能直接挡住 Logo 或唤醒词。

### 8.2 重点观察

- 第一包音频到服务端的时间。
- 服务端检测到人声的时间。
- 语音识别开始的时间。
- 第一句话前几个字有没有丢。
- 连续 10 轮对话是否稳定。

### 8.3 不能接受

- 待机时一直把环境声音上传。
- 铜豆回复还没播完就重新上传，导致识别到自己的声音。
- 用本地平均音量阈值挡住连续对话上传。
- 每轮对话都必须重新点网页按钮。
- 用户每句话都必须叫一次“铜豆”。
- 雷达误判导致用户叫铜豆没反应。
- 为了修语音链路，把剧情、网页、硬件职责混在一起。

## 9. 禁止事项

- 不允许把“本地音频链路常驻”理解成“一直上传”。
- 不允许把雷达当语音唤醒开关。
- 不允许把 Logo 单击写成特殊语音流程，它只是物理唤醒入口。
- 不允许把服务端改成唯一兜底，固件本地链路必须先做对。
- 不允许为了临时跑通，把音频处理、窗口计时、上传协议都塞进同一个文件。

## 10. 当前代码切入点

当前已经完成并通过实机验收：

> `LocalAudioPipeline` 负责常驻采音和上传队列；`RealtimeVoiceService` 负责一次语音回合；回复完成后由 `App` 延迟 120 ms 启动下一轮临时上传，服务端负责判断有没有人声。

第一版不急着接真正唤醒词。

当前先做到：

```text
开机后本地音频链路常驻
Logo 单击只触发上传
回复播放排空后自动进入下一轮临时上传
服务端检测到人声后继续完成识别和回复
无人说话则正常退出
```

`2026-08-24` 实机连续完成“现在几点了”“再说短一点儿”“今天天气怎么样”等至少 7 轮连续对话，中间没有再次触摸 Logo；最后保持安静时，服务端收到 `333` 包音频、判定人声包为 `0`，设备最终回到空闲状态且错误码为空。
