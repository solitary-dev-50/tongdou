# 实时语音链路内存与编解码故障修复方案

本文档只负责一件事：

> 规定铜豆实时语音上行链路当前故障的证据、修复顺序、验收标准和回滚办法。

大白话说：

> 这是本次故障的施工单和验收单，不是大而全的语音系统重构方案。

## 1. 文档状态

- 基线日期：`2026-08-24`
- 当前状态：主故障和连续对话时序故障已经修复；网页、MCP 工具、Logo 物理触摸、至少 7 轮连续对话及无人说话退出均完成实机验收
- 已消除第一断点：`PCM -> Opus`
- 原始已证实错误：`opus_decoder_create_failed`
- 已验证根因：板载 `2 MB PSRAM` 没有按当前硬件路线启用；只修正板级内存配置后，原有编解码器和缓冲区不再修改即可稳定通过自测和完整回合
- 修复原则：一次只改一层，上一层没验收，不进入下一层

`PSRAM` 是板载外部扩展内存。它容量大，适合放大的音频缓冲区；但速度和硬件直接访问能力不如芯片内部内存，不能把所有数据不分用途地全部搬进去。

## 2. 问题定义

当前要解决的不是“Logo 触摸语音问题”，也不是某个语音识别供应商的问题。

准确问题是：

> 铜豆从任意合法语音入口启动实时语音回合后，本地能够采集麦克风声音，但音频编解码器初始化失败，导致第一包上行音频无法完成编码并发送到语音后端。

语音入口包括：

- Logo 单击。
- 回复完成后自动进入的连续对话上传窗口。
- 网页调试命令。
- MCP（模型上下文协议）工具命令。
- 后续本地唤醒词入口。

Logo 只是当前方便复现故障的物理入口，不得在修复中建立 Logo 专用语音链路。

当前使用的语音识别、对话模型、语音合成和兼容服务端，都只是后端可替换实现。本次修复不得把铜豆固件绑死到某个供应商或某个服务端项目。

## 3. 先把几个词说清楚

### 3.1 PCM

`PCM` 是麦克风采集到的原始数字音频。

当前上行音频参数是：

- `16000 Hz`，也就是每秒 16000 个采样点。
- 单声道。
- 每帧 `960` 个采样点。
- 每帧对应 `60 ms`。

### 3.2 Opus

`Opus` 是当前上行和下行使用的音频压缩格式。

上行是：

```text
PCM 原始音频
  -> Opus 编码
  -> 二进制音频包
  -> 语音后端
```

下行是：

```text
语音后端二进制音频包
  -> Opus 解码
  -> PCM 原始音频
  -> 扬声器
```

### 3.3 准备完成

客户端只有在下列必需能力全部可用时，才能对上层报告“准备完成”：

- 网络长连接已建立。
- 协议握手已完成。
- 上行编码能力可用。
- 当前需要的下行解码能力可用，或者已有明确的延迟初始化策略。

不能只因为服务端回复了 `hello` 就宣布整条语音链路可用。

## 4. 已经确认的事实

下面内容是当前基线，修复前不得被猜测替代。

### 4.1 本地采音已到达语音回合层

串口日志出现：

```text
voice timeline first_pcm ... samples=960
```

这证明语音回合层已经拿到一帧 PCM 采样。

它不能单独证明用户声音足够清楚。音质和音量要另看 `mean_abs` 和 `peak` 等采样数据。

### 4.2 语音回合开始消息已到服务端

`2026-08-24` 的运行中服务端日志确认收到 5 次：

```text
type=listen state=start mode=auto
```

因此，这 5 轮不是“开始语音回合消息根本没到服务端”。

### 4.3 服务端没有进入第一包音频处理

同一轮测试中：

- `first_audio_received` 计数为 `0`。
- `listen stop` 计数为 `0`。
- 未进入后端语音识别。
- 未进入对话模型。
- 未进入语音合成。

### 4.4 设备运行状态明确报告编解码器未就绪

在线设备的语音状态接口返回：

```text
codecReady=false
codecLastError=opus_decoder_create_failed
```

### 4.5 独立编解码自测重复出现同一错误

设备现有的独立编解码自测返回：

```text
ok=false
inputSamples=0
encodedBytes=0
decodedSamples=0
error=opus_decoder_create_failed
```

这证明错误不是上一轮语音状态残留，而是当前运行环境下可稳定重现的编解码初始化故障。

### 4.6 当前错误提示音日志不是上行统计

下面这行：

```text
audio cue voice_recognition_failed ok=1 packets=15 samples=14400
```

只表示本地“语音失败”提示音成功播放了 15 个内置音频包。

它不表示向语音后端上传了 15 包，也不表示用户语音在第 15 包时失败。

## 5. 已证实的代码执行路径

当前代码的真实执行顺序是：

```text
建立语音客户端
  -> 创建 Opus 编码器
  -> 创建 Opus 解码器
  -> 解码器创建失败
  -> 销毁已创建的编码器
  -> 编解码器标记为未就绪
```

随后连接流程没有阻止：

```text
编解码器未就绪
  -> 仍然继续建立网络长连接
  -> 收到服务端 hello
  -> 客户端错误地报告 ready
  -> 允许启动语音回合
```

第一帧 PCM 到达后：

```text
第一帧 PCM
  -> 尝试 Opus 编码
  -> 编码器未就绪
  -> 返回编码失败
  -> 没有调用二进制音频发送
  -> 语音回合进入失败状态
  -> 停止上传
  -> 不会走到 listen stop
  -> 播放本地失败提示音和补救台词
```

这条路径能完整解释当前日志。

## 6. 根因分层

为了防止把“直接错误”和“底层原因”混为一谈，本次故障按三层记录。

### 6.1 第一层：已证实的直接故障

```text
Opus 解码器创建失败
```

这是设备状态和独立自测都已经重现的事实。

### 6.2 第二层：已证实的状态管理问题

```text
编解码器初始化失败
  -> 失败没有阻止客户端进入 ready
```

这导致设备表面上能“开始听”，实际上不具备发送语音的条件。

### 6.3 第三层：高概率底层原因

当前主线硬件使用 `ESP32-S3-MINI-1-N4R2`，其中 `R2` 表示板载 `2 MB PSRAM`。

当前固件编译配置选择的是：

```text
ESP32-S3-DevKitC-1-N8
8 MB 闪存
不带 PSRAM
```

项目虽然把闪存容量另行调整为 `4 MB`，但没有看到当前模组所需的 PSRAM 内存类型配置，也没有运行时的 PSRAM 识别日志。

故障基线固件当时有三块常驻音频缓冲区，合计约占 `115200` 字节：

| 缓冲区 | 采样点 | 约占用 |
| --- | ---: | ---: |
| 本地预录音缓冲 | 19200 | 38400 字节 |
| 上传缓冲 | 19200 | 38400 字节 |
| 对话窗口预录音拷贝 | 19200 | 38400 字节 |

后续对齐连续对话时序后，两份已经不再使用的预录音缓存和本地简单音量门控已删除。当前只保留一份 `19200` 采样点的短上传队列，静态内部内存由 `194648` 字节降到 `117792` 字节。这里的删除是清理失效设计，不是把硬件直接访问缓冲搬进 PSRAM。

这还没计入：

- 网络长连接。
- 网页服务。
- 显示、灯光、电机和其他固件对象。
- 音频提示音解码缓冲。
- Opus 编码器和解码器本身。
- 任务堆栈和动态分配开销。

已知 Opus 初始化顺序是“编码器成功，再创建解码器”，而最终报错在解码器创建。这高度符合“内部内存已被前面对象和编码器占用，无法再提供足够大的连续内存块”。

但当前代码丢掉了 Opus 原生错误码，还没有运行时的剩余内存和最大连续内存数据。因此，在完成第一阶段前，底层原因应记为“高概率内存配置和分配问题”，不应把“内存不足”写成已有原生错误码证明的最终结论。

### 7.1 允许修改

- 如果启用 PSRAM 后仍无法同时创建编码器和解码器，允许调整半双工下的编解码器生命周期。

### 7.2 本轮禁止修改

- 不改 Logo 与其他语音入口的交互含义。
- 不改本地音频链路常驻原则。
- 不改自动、手动和实时监听模式的业务策略。
- 不更换语音识别供应商。
- 不更换对话模型。
- 不改语音合成供应商。

- 不做无关的固件目录重构。

## 10. 阶段 1：启用并验证 2 MB PSRAM

### 10.1 目标

让固件正确识别并使用 `ESP32-S3-MINI-1-N4R2` 的 `2 MB PSRAM`。

这是板级基础能力修正，不是为某个语音供应商做的专用优化。

### 10.2 开工前核对

在修改配置前，先核对：

- 当前实物模组确实是 `ESP32-S3-MINI-1-N4R2`。
- 当前芯片模组的 PSRAM 总线类型。
- 当前固件构建工具 PlatformIO 所支持的内存类型配置名称。
- 闪存容量仍为 `4 MB`，不能因为启用 PSRAM 而把闪存错改为 `8 MB`。
- 当前分区表不得被顺手更换。

不允许仅根据网上某个工程的复制片段直接填写内存类型。必须同时与模组型号和当前本地工具链支持项对齐。

### 10.3 本阶段允许修改

- `firmware/platformio.ini` 中与当前模组对应的板型、闪存和 PSRAM 配置。
- 一个已有启动诊断位置中的最小内存报告。

不为了打印内存日志新建一串跨层模块。优先放入已有的启动报告或硬件诊断入口。

### 10.4 必须输出的运行时数据

- PSRAM 是否识别成功。
- PSRAM 总容量。
- PSRAM 剩余容量。
- 内部剩余内存。
- 历史最低内部剩余内存。
- 当前最大连续可分配内存块。

这些数据至少要在两个时间点可查：

1. 编解码器初始化前。
2. 编解码器初始化后。

### 10.5 通过标准

- 启动日志明确显示 PSRAM 已找到。
- 报告总容量与 `2 MB` 规格相符，允许工具链和统计方式带来的少量差异。
- 固件正常启动。
- 无线网络、网页、OLED 屏幕、灯光、电机、麦克风和扬声器的原有初始化结果不变。
- 没有因为启用 PSRAM 改错闪存容量或分区表。

### 10.6 未通过时

如果 PSRAM 未找到或容量不对：

1. 立即停止。
2. 不进入语音代码修改。
3. 回查模组型号、内存总线类型、编译参数和启动日志。
4. 只修板级内存配置，不用语音代码遮住板级错误。

### 10.7 回滚

只回滚本阶段的板型和诊断改动，恢复到阶段 0 保留的基线。

## 11. 阶段 2：独立验证 Opus 编解码

### 11.1 目标

在不启动真实语音回合的情况下，确认编码器和解码器能否正常创建和工作。

### 11.2 测试入口

优先复用现有入口：

```text
POST /api/voice/codec-self-test
```

不为这一阶段再写第二套自测。

### 11.3 通过标准

返回至少满足：

```text
ok=true
inputSamples=960
encodedBytes>0
decodedSamples=960
error=空
```

同时：

- 自测前后没有重启。
- 没有看门狗超时。
- 没有破坏已经连接的语音客户端状态。
- 自测临时对象销毁后，可用内存能回到合理范围。

### 11.4 如果启用 PSRAM 后直接通过

立即停止内存方面的额外改动。

不做这些事：

- 不搬迁所有缓冲区。
- 不改编解码器生命周期。
- 不为了“再稳一点”扩大修改范围。

证据已说明问题消失时，就不要继续动底层。

### 11.5 如果仍然失败

只允许进入下面两个分支中的一个，不得同时开工。

#### 分支 A：精确放置大缓冲区

适用条件：

- PSRAM 已成功启用。
- 编解码器仍报动态分配失败。
- 内部剩余内存或最大连续内存块过小。

优先评估放入 PSRAM 的对象：

1. 上传排队缓冲。
2. 后续真正实现唤醒词时需要的前置音频缓存。

当前两份旧预录音缓存已经因连续对话方案改为“播放排空后立即临时上传”而删除，不能为了照搬旧方案重新加回。

不允许优先搬迁：

- I2S（芯片间数字音频总线）硬件直接使用的 DMA 缓冲。
- 高频中断或硬件实时路径必须使用的小缓冲。
- 已经足够小且没有影响内存的对象。

`DMA` 是硬件直接读写内存的机制。这类缓冲对内存位置有特殊要求，不能只因为大就搬到 PSRAM。

#### 分支 B：错峰使用编码器和解码器

适用条件：

- 上行时只需要编码器。
- 下行播放时只需要解码器。
- 第一版仍保持半双工，不会边播边听。

可评估的生命周期：

```text
进入监听
  -> 创建上行编码器
  -> 编码和发送
  -> 上行结束
  -> 销毁编码器
  -> 创建下行解码器
  -> 解码和播放
  -> 下行结束
  -> 按下一轮需求准备
```

这个分支必须由一个清楚的音频编解码对象负责，不得把创建和销毁逻辑散落到 `App`、网页或协议处理器。

### 11.6 分支选择原则

只看运行数据：

- 大缓冲区挤压内部内存，选分支 A。
- 两个编解码器同时存在时才失败，选分支 B。
- 证据不够，先补最小诊断，不猜。

不允许因为两个方案都“看起来更稳”就同时实施。

## 12. 阶段 3：修正编解码准备状态

### 12.1 目标

不再出现这种假状态：

```text
codecReady=false
voice client state=ready
voice client state=listening
```

### 12.2 状态规则

如果保持编码器和解码器同时常驻：

```text
网络连接成功
  + 协议握手成功
  + 编码器成功
  + 解码器成功
  = 语音客户端准备完成
```

如果采用半双工错峰生命周期：

- 必须分开记录上行编码是否就绪。
- 必须分开记录下行解码是否就绪。
- 启动监听前必须确认上行编码就绪。
- 进入播放前必须确认下行解码就绪。
- 不能用一个含糊的 `ready` 掩盖其中一个未就绪。

### 12.3 错误报告要求

至少保留：

- 失败发生在编码器还是解码器。
- Opus 原生错误码。
- 错误码对应文本。
- 失败前的内部剩余内存。
- 失败前的最大连续可分配内存块。
- 失败时的 PSRAM 可用状态。

错误码应继续使用可稳定查询的机器可读字符串，例如：

```text
opus_decoder_create_failed
voice_codec_not_ready
```

不得只打印“语音失败”。

### 12.4 通过标准

- 编解码器失败时，语音客户端不进入准备完成。
- 上层启动语音回合时直接收到明确失败原因。
- 服务端不再收到“开始听了但永远没有音频”的假回合。
- 网页语音状态能看到编解码器的真实准备状态。

### 12.5 回滚

只回滚准备状态和错误传递改动，不回滚已经验收通过的 PSRAM 配置。
