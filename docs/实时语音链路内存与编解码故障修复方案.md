# 实时语音链路内存与编解码故障修复方案

本文档只负责一件事：

> 规定铜豆实时语音上行链路当前故障的证据、修复顺序、验收标准和回滚办法。

大白话说：

> 这是本次故障的施工单和验收单，不是大而全的语音系统重构方案。

## 1. 文档状态

- 基线日期：`2026-08-24`
- 当前状态：主故障、连续对话时序、正常在线退出、空闲连接保活和识别连接等待优化均已完成实机验证；旧的本地 `20 s + 12 s` 收口已退出正常流程，只保留服务器无响应等异常保险
- 已消除第一断点：`PCM -> Opus`
- 原始已证实错误：`opus_decoder_create_failed`
- 已验证根因：板载 `2 MB PSRAM` 没有按当前硬件路线启用；只修正板级内存配置后，原有编解码器和缓冲区不再修改即可稳定通过自测和完整回合
- 修复原则：一次只改一层，上一层没验收，不进入下一层

`PSRAM` 是板载外部扩展内存。它容量大，适合放大的音频缓冲区；但速度和硬件直接访问能力不如芯片内部内存，不能把所有数据不分用途地全部搬进去。

## 2. 问题定义

当前要解决的不是“Logo 触摸语音问题”，也不是某个语音识别供应商的问题。

准确问题是：

> 铜豆从任意合法语音入口启动实时语音回合后，本地能够采集麦克风声音，但音频编解码器初始化失败，导致第一包上行音频无法完成编码并发送到语音后端。

语音入口包括：

- Logo 单击。
- 回复完成后自动进入的连续对话上传窗口。
- 网页调试命令。
- MCP（模型上下文协议）工具命令。
- 后续本地唤醒词入口。

Logo 只是当前方便复现故障的物理入口，不得在修复中建立 Logo 专用语音链路。

当前使用的语音识别、对话模型、语音合成和兼容服务端，都只是后端可替换实现。本次修复不得把铜豆固件绑死到某个供应商或某个服务端项目。

## 3. 先把几个词说清楚

### 3.1 PCM

`PCM` 是麦克风采集到的原始数字音频。

当前上行音频参数是：

- `16000 Hz`，也就是每秒 16000 个采样点。
- 单声道。
- 每帧 `960` 个采样点。
- 每帧对应 `60 ms`。

### 3.2 Opus

`Opus` 是当前上行和下行使用的音频压缩格式。

上行是：

```text
PCM 原始音频
  -> Opus 编码
  -> 二进制音频包
  -> 语音后端
```

下行是：

```text
语音后端二进制音频包
  -> Opus 解码
  -> PCM 原始音频
  -> 扬声器
```

### 3.3 准备完成

客户端只有在下列必需能力全部可用时，才能对上层报告“准备完成”：

- 网络长连接已建立。
- 协议握手已完成。
- 上行编码能力可用。
- 当前需要的下行解码能力可用，或者已有明确的延迟初始化策略。

不能只因为服务端回复了 `hello` 就宣布整条语音链路可用。

## 4. 已经确认的事实

下面内容是当前基线，修复前不得被猜测替代。

### 4.1 本地采音已到达语音回合层

串口日志出现：

```text
voice timeline first_pcm ... samples=960
```

这证明语音回合层已经拿到一帧 PCM 采样。

它不能单独证明用户声音足够清楚。音质和音量要另看 `mean_abs` 和 `peak` 等采样数据。

### 4.2 语音回合开始消息已到服务端

`2026-08-24` 的运行中服务端日志确认收到 5 次：

```text
type=listen state=start mode=auto
```

因此，这 5 轮不是“开始语音回合消息根本没到服务端”。

### 4.3 服务端没有进入第一包音频处理

同一轮测试中：

- `first_audio_received` 计数为 `0`。
- `listen stop` 计数为 `0`。
- 未进入后端语音识别。
- 未进入对话模型。
- 未进入语音合成。

### 4.4 设备运行状态明确报告编解码器未就绪

在线设备的语音状态接口返回：

```text
codecReady=false
codecLastError=opus_decoder_create_failed
```

### 4.5 独立编解码自测重复出现同一错误

设备现有的独立编解码自测返回：

```text
ok=false
inputSamples=0
encodedBytes=0
decodedSamples=0
error=opus_decoder_create_failed
```

这证明错误不是上一轮语音状态残留，而是当前运行环境下可稳定重现的编解码初始化故障。

### 4.6 当前错误提示音日志不是上行统计

下面这行：

```text
audio cue voice_recognition_failed ok=1 packets=15 samples=14400
```

只表示本地“语音失败”提示音成功播放了 15 个内置音频包。

它不表示向语音后端上传了 15 包，也不表示用户语音在第 15 包时失败。

## 5. 已证实的代码执行路径

当前代码的真实执行顺序是：

```text
建立语音客户端
  -> 创建 Opus 编码器
  -> 创建 Opus 解码器
  -> 解码器创建失败
  -> 销毁已创建的编码器
  -> 编解码器标记为未就绪
```

随后连接流程没有阻止：

```text
编解码器未就绪
  -> 仍然继续建立网络长连接
  -> 收到服务端 hello
  -> 客户端错误地报告 ready
  -> 允许启动语音回合
```

第一帧 PCM 到达后：

```text
第一帧 PCM
  -> 尝试 Opus 编码
  -> 编码器未就绪
  -> 返回编码失败
  -> 没有调用二进制音频发送
  -> 语音回合进入失败状态
  -> 停止上传
  -> 不会走到 listen stop
  -> 播放本地失败提示音和补救台词
```

这条路径能完整解释当前日志。

## 6. 根因分层

为了防止把“直接错误”和“底层原因”混为一谈，本次故障按三层记录。

### 6.1 第一层：已证实的直接故障

```text
Opus 解码器创建失败
```

这是设备状态和独立自测都已经重现的事实。

### 6.2 第二层：已证实的状态管理问题

```text
编解码器初始化失败
  -> 失败没有阻止客户端进入 ready
```

这导致设备表面上能“开始听”，实际上不具备发送语音的条件。

### 6.3 第三层：高概率底层原因

当前主线硬件使用 `ESP32-S3-MINI-1-N4R2`，其中 `R2` 表示板载 `2 MB PSRAM`。

当前固件编译配置选择的是：

```text
ESP32-S3-DevKitC-1-N8
8 MB 闪存
不带 PSRAM
```

项目虽然把闪存容量另行调整为 `4 MB`，但没有看到当前模组所需的 PSRAM 内存类型配置，也没有运行时的 PSRAM 识别日志。

故障基线固件当时有三块常驻音频缓冲区，合计约占 `115200` 字节：

| 缓冲区 | 采样点 | 约占用 |
| --- | ---: | ---: |
| 本地预录音缓冲 | 19200 | 38400 字节 |
| 上传缓冲 | 19200 | 38400 字节 |
| 对话窗口预录音拷贝 | 19200 | 38400 字节 |

后续对齐连续对话时序后，两份已经不再使用的预录音缓存和本地简单音量门控已删除。当前只保留一份 `19200` 采样点的短上传队列，静态内部内存由 `194648` 字节降到 `117792` 字节。这里的删除是清理失效设计，不是把硬件直接访问缓冲搬进 PSRAM。

这还没计入：

- 网络长连接。
- 网页服务。
- 显示、灯光、电机和其他固件对象。
- 音频提示音解码缓冲。
- Opus 编码器和解码器本身。
- 任务堆栈和动态分配开销。

已知 Opus 初始化顺序是“编码器成功，再创建解码器”，而最终报错在解码器创建。这高度符合“内部内存已被前面对象和编码器占用，无法再提供足够大的连续内存块”。

但当前代码丢掉了 Opus 原生错误码，还没有运行时的剩余内存和最大连续内存数据。因此，在完成第一阶段前，底层原因应记为“高概率内存配置和分配问题”，不应把“内存不足”写成已有原生错误码证明的最终结论。

## 10. 阶段 1：启用并验证 2 MB PSRAM

### 10.1 目标

让固件正确识别并使用 `ESP32-S3-MINI-1-N4R2` 的 `2 MB PSRAM`。

这是板级基础能力修正，不是为某个语音供应商做的专用优化。

### 10.2 开工前核对

在修改配置前，先核对：

- 当前实物模组确实是 `ESP32-S3-MINI-1-N4R2`。
- 当前芯片模组的 PSRAM 总线类型。
- 当前固件构建工具 PlatformIO 所支持的内存类型配置名称。
- 闪存容量仍为 `4 MB`，不能因为启用 PSRAM 而把闪存错改为 `8 MB`。
- 当前分区表不得被顺手更换。

不允许仅根据网上某个工程的复制片段直接填写内存类型。必须同时与模组型号和当前本地工具链支持项对齐。

### 10.3 本阶段允许修改

- `firmware/platformio.ini` 中与当前模组对应的板型、闪存和 PSRAM 配置。
- 一个已有启动诊断位置中的最小内存报告。

不为了打印内存日志新建一串跨层模块。优先放入已有的启动报告或硬件诊断入口。

### 10.4 必须输出的运行时数据

- PSRAM 是否识别成功。
- PSRAM 总容量。
- PSRAM 剩余容量。
- 内部剩余内存。
- 历史最低内部剩余内存。
- 当前最大连续可分配内存块。

这些数据至少要在两个时间点可查：

1. 编解码器初始化前。
2. 编解码器初始化后。

### 10.5 通过标准

- 启动日志明确显示 PSRAM 已找到。
- 报告总容量与 `2 MB` 规格相符，允许工具链和统计方式带来的少量差异。
- 固件正常启动。
- 无线网络、网页、OLED 屏幕、灯光、电机、麦克风和扬声器的原有初始化结果不变。
- 没有因为启用 PSRAM 改错闪存容量或分区表。

### 10.6 未通过时

如果 PSRAM 未找到或容量不对：

1. 立即停止。
2. 不进入语音代码修改。
3. 回查模组型号、内存总线类型、编译参数和启动日志。
4. 只修板级内存配置，不用语音代码遮住板级错误。

### 10.7 回滚

只回滚本阶段的板型和诊断改动，恢复到阶段 0 保留的基线。

## 11. 阶段 2：独立验证 Opus 编解码

### 11.1 目标

在不启动真实语音回合的情况下，确认编码器和解码器能否正常创建和工作。

### 11.2 测试入口

优先复用现有入口：

```text
POST /api/voice/codec-self-test
```

不为这一阶段再写第二套自测。

### 11.3 通过标准

返回至少满足：

```text
ok=true
inputSamples=960
encodedBytes>0
decodedSamples=960
error=空
```

同时：

- 自测前后没有重启。
- 没有看门狗超时。
- 没有破坏已经连接的语音客户端状态。
- 自测临时对象销毁后，可用内存能回到合理范围。

### 11.4 如果启用 PSRAM 后直接通过

立即停止内存方面的额外改动。

不做这些事：

- 不搬迁所有缓冲区。
- 不改编解码器生命周期。
- 不为了“再稳一点”扩大修改范围。

证据已说明问题消失时，就不要继续动底层。

### 11.5 如果仍然失败

只允许进入下面两个分支中的一个，不得同时开工。

#### 分支 A：精确放置大缓冲区

适用条件：

- PSRAM 已成功启用。
- 编解码器仍报动态分配失败。
- 内部剩余内存或最大连续内存块过小。

优先评估放入 PSRAM 的对象：

1. 上传排队缓冲。
2. 后续真正实现唤醒词时需要的前置音频缓存。

当前两份旧预录音缓存已经因连续对话方案改为“播放排空后立即临时上传”而删除，不能为了照搬旧方案重新加回。

不允许优先搬迁：

- I2S（芯片间数字音频总线）硬件直接使用的 DMA 缓冲。
- 高频中断或硬件实时路径必须使用的小缓冲。
- 已经足够小且没有影响内存的对象。

`DMA` 是硬件直接读写内存的机制。这类缓冲对内存位置有特殊要求，不能只因为大就搬到 PSRAM。

#### 分支 B：错峰使用编码器和解码器

适用条件：

- 上行时只需要编码器。
- 下行播放时只需要解码器。
- 第一版仍保持半双工，不会边播边听。

可评估的生命周期：

```text
进入监听
  -> 创建上行编码器
  -> 编码和发送
  -> 上行结束
  -> 销毁编码器
  -> 创建下行解码器
  -> 解码和播放
  -> 下行结束
  -> 按下一轮需求准备
```

这个分支必须由一个清楚的音频编解码对象负责，不得把创建和销毁逻辑散落到 `App`、网页或协议处理器。

### 11.6 分支选择原则

只看运行数据：

- 大缓冲区挤压内部内存，选分支 A。
- 两个编解码器同时存在时才失败，选分支 B。
- 证据不够，先补最小诊断，不猜。

不允许因为两个方案都“看起来更稳”就同时实施。

## 12. 阶段 3：修正编解码准备状态

### 12.1 目标

不再出现这种假状态：

```text
codecReady=false
voice client state=ready
voice client state=listening
```

### 12.2 状态规则

如果保持编码器和解码器同时常驻：

```text
网络连接成功
  + 协议握手成功
  + 编码器成功
  + 解码器成功
  = 语音客户端准备完成
```

如果采用半双工错峰生命周期：

- 必须分开记录上行编码是否就绪。
- 必须分开记录下行解码是否就绪。
- 启动监听前必须确认上行编码就绪。
- 进入播放前必须确认下行解码就绪。
- 不能用一个含糊的 `ready` 掩盖其中一个未就绪。

### 12.3 错误报告要求

至少保留：

- 失败发生在编码器还是解码器。
- Opus 原生错误码。
- 错误码对应文本。
- 失败前的内部剩余内存。
- 失败前的最大连续可分配内存块。
- 失败时的 PSRAM 可用状态。

错误码应继续使用可稳定查询的机器可读字符串，例如：

```text
opus_decoder_create_failed
voice_codec_not_ready
```

不得只打印“语音失败”。

### 12.4 通过标准

- 编解码器失败时，语音客户端不进入准备完成。
- 上层启动语音回合时直接收到明确失败原因。
- 服务端不再收到“开始听了但永远没有音频”的假回合。
- 网页语音状态能看到编解码器的真实准备状态。

### 12.5 回滚

只回滚准备状态和错误传递改动，不回滚已经验收通过的 PSRAM 配置。

## 22. 阶段 7：正常退出机制对齐方案

本节只负责一件事：

> 让正常在线退出由服务器统一裁决，保证铜豆先把告别语完整说完，再回到空闲待命。

本节是前六个阶段已经跑通后的新增施工阶段。它允许修改服务器退出编排和铜豆退出状态，不推翻前面已经验收的采音、Opus 编解码、上下行传输和连续对话链路。

### 22.1 一句话原则

> 正常在线时，服务器是会话是否结束的唯一裁判；铜豆只执行明确的退出结果，不再用本地计时猜测用户是不是聊完了。

这不表示铜豆在网络故障时什么也不做。网络已经断开、服务器无法裁决时，铜豆必须走本地异常兜底，停止录音和播放，给出失败反馈并回到可重试状态。

### 22.2 三方实施前基线

#### 服务器实施前状态

- 精确退出命令当前直接关闭连接，没有告别语。
- 语义退出依赖对话模型调用 `handle_exit_intent` 工具；模型只说告别语但没调用工具时，不会退出。
- 无人说话由服务器无声超时触发结束提示，但铜豆旧的 `20 s` 本地保险会先停止上传，服务器配置的无声超时没有机会成为最终裁判。
- 普通回复结束和会话退出都只发送 `tts stop`；当前没有 WebSocket（网络长连接）层的明确 `goodbye` 消息。

#### 小智固件参考状态

- 自动对话模式下，普通 `tts stop` 表示本轮回复结束，固件会在播放排空后重新监听。
- WebSocket 模式下，正常退出依靠服务器结束会话并关闭连接，固件收到音频通道关闭后回到空闲。
- MQTT（消息队列遥测传输）模式已经有明确的 `goodbye` 消息：收到后结束音频会话，不再开启下一轮监听。
- 小智不在固件里判断“退下吧”是什么意思，退出语义由服务器负责。

#### 铜豆实施前状态

- 普通回复播放队列排空后等待 `120 ms`，自动开启下一轮上传，连续对话已经通过实机验证。
- 自动监听存在本地 `20 s` 采音上限；停止上传后又用本地 `12 s` 等待服务器结果。
- 超时后铜豆自己把会话关掉，服务器没有机会按自身无声超时配置生成告别语。
- Logo 长按当前只在本地关闭对话窗口并发送打断，没有经过服务器正常退出出口。

### 22.3 对齐后的统一退出时序

服务器、小智和铜豆三方对齐的不是某个参数值，而是下面这条生命周期：

```text
退出来源
  ├─ 精确命令，例如“退出”
  ├─ 语义退出，例如“好了没事了，你先退下吧”
  ├─ 持续无人说话
  └─ 设备手动退出请求，例如 Logo 长按
        ↓
服务器统一标记“正常退出处理中”
        ↓
服务器生成告别文字并合成为语音
        ↓
服务器发送完整告别音频
        ↓
服务器发送 tts stop
        ↓
服务器发送明确的 goodbye
        ↓
铜豆锁住会话，不允许再次开启连续监听
        ↓
铜豆继续播放已经收到的最后音频包
        ↓
软件音频队列为空，并且 I2S 扬声器硬件缓冲真正排空
        ↓
铜豆回到空闲待命
```

`I2S` 是芯片把数字音频送到功放的硬件通道。软件队列为空不等于喇叭已经播完，因此最后一步不能只看“网络音频包已取完”，还必须覆盖硬件缓冲里的尾音。

### 22.4 服务器职责

服务器必须做到：

1. 维护单向变化的退出状态。一旦进入“正常退出处理中”，后来的 `listen start`、残留音频或迟到的识别结果不能把它改回普通对话。
2. 精确命令、保守的语义退出判断、模型退出工具、无人说话和设备手动退出请求，都调用同一个退出入口。
3. 先把告别语送入现有语音合成和音频发送队列，不直接断连接。
4. 等服务器侧最后一包告别音频发送完成后，先发 `tts stop`，再发：

```json
{
  "type": "goodbye",
  "session_id": "当前会话编号",
  "reason": "退出原因"
}
```

5. 发出 `goodbye` 后结束本次会话连接。旧客户端即使不认识 `goodbye`，仍能通过连接关闭回到空闲；认识该消息的铜豆可以在连接关闭前先锁住连续监听。
6. 第二道服务器连接超时仍是异常保险，但不能在正常退出已经开始后重复关闭或覆盖退出原因。

### 22.5 铜豆职责

铜豆必须做到：

1. 握手时声明支持 `goodbye`。
2. 收到 `goodbye` 后立即停止上传，并进入“正在退出”状态。
3. “正在退出”状态下，任何普通 `tts stop`、回复完成事件和延迟到期事件都不能再次开启连续监听。
4. 保留已经收到的下行音频包，不能因为服务器随后关闭连接就清空告别语尾部。
5. 等待软件下行队列为空。
6. 再等待扬声器硬件缓冲按当前采样率和缓冲容量排空，确认尾音已经从喇叭播完。
7. 产生一次“正常会话已结束”事件，由 `App` 清除连续对话窗口并回到空闲。
8. Logo 长按等手动退出只向服务器请求退出，不在网络正常时自行宣布正常结束。

### 22.6 本地计时和异常兜底边界

旧行为：

```text
自动监听 20 s 到期
  -> 铜豆发送 listen stop
  -> 本地再等 12 s
  -> 铜豆自行退出
```

目标行为：

```text
网络和服务器正常
  -> 铜豆持续上传
  -> 服务器按统一规则判断有人说话或应该退出

网络断开、发送失败或服务器长时间没有任何可用响应
  -> 铜豆走本地异常兜底
  -> 停止上传和残留播放
  -> 给出失败反馈
  -> 回到可重试状态
```

因此：

- 删除自动连续监听的 `20 s` 正常收口职责。
- `12 s` 只能保留为“已经结束上传但服务器没有返回任何结果”的异常响应保险，不能再代表无人说话正常退出。
- 网络心跳确认断开、WebSocket 发送失败等情况属于异常，可以由铜豆本地收口。
- 网络正常时的安静不是异常，必须交给服务器的无声超时规则。

### 22.7 台词边界

告别语必须由服务器侧提供并经过服务器语音合成，不能在铜豆固件里另写一套正常退出录音。

默认告别语应满足：

- 短。
- 口语化。
- 不像客服结束通话。
- 不继续追问用户。
- 不要求用户再做一次确认。

服务器仍可根据退出来源或智能体人格替换具体内容，但具体参数值不能改变“告别语 -> `tts stop` -> `goodbye`”的固定顺序。

### 22.8 修改边界

本阶段允许修改：

- 服务器统一退出状态和出口。
- 服务器 `goodbye` 消息收发。
- 铜豆协议解析、退出状态、连续监听锁定和播放排空判断。
- Logo 长按的手动退出接线。
- 与退出时序直接相关的日志和测试。

本阶段禁止修改：

- 麦克风采样参数。
- Opus 编解码参数和生命周期。
- 已经通过验收的首包发送路径。
- 当前语音识别、对话模型和语音合成供应商。
- Logo 单击、网页、MCP 和未来唤醒入口共用语音链路的原则。

- 网络恢复后可以重新连接并开始新会话。

- 新增单一正常退出入口。精确命令、保守语义判断、模型退出工具、无人说话、设备手动请求和服务器第二道超时只提交退出原因，不再各自关连接。
- 统一出口固定执行“锁定退出 -> 清理旧回合 -> 生成告别语 -> 发送告别音频 -> `tts stop` -> `goodbye` -> 关闭连接”。
- 退出锁定后拒绝迟到的 `listen start`、音频包和识别结果，退出原因不会被后来的事件覆盖。
- 服务器额外区分“已经开始对话”和“只是保持连接”。对话中的第二道超时仍走正常告别；已经绑定且尚未开始对话的空闲连接由 WebSocket 底层心跳保活，不再被业务无活动计时器误关。
- 自动化测试共 `4` 项通过：保守语义判断、告别语与 `goodbye` 顺序、无人说话进入同一出口、健康空闲连接持续保活。其中无人说话用例把上次人声时间放到 `121 s` 以前，验证退出原因为 `no_voice`，消息顺序为 `tts start -> tts stop -> goodbye`。

#### 铜豆实施结果

- 握手声明支持 `goodbye`；协议层能收发带退出原因的 `goodbye`。
- 新增“正在退出”状态。收到 `goodbye` 后停止上传、取消连续监听候选，并拒绝再次开始语音回合。
- 网络连接关闭时保留已经收到的告别音频；软件队列排空后，再按当前 `4 × 256` 帧硬件缓冲和采样率等待喇叭尾音排空。
- 自动连续监听不再设置本地 `20 s` 截止时间。原来的服务器无响应保险仍按异常处理，不能冒充正常安静退出。
- Logo 长按、网页和 MCP（模型上下文协议）手动退出入口最终都调用同一个服务器退出请求；固件不再叠加本地正常告别录音。

#### 四类验收结果

1. **语义退出：通过。** 实机输入“好了没事了，你先退下吧”，服务器记录退出原因为 `semantic`，发送告别音频后发送 `goodbye`。铜豆记录软件队列和扬声器均已排空，回到 `idle`，中间没有新的 `listen start`。
2. **精确退出：通过。** 实机输入“退出”，服务器记录退出原因为 `exact_command`，走同一告别出口，铜豆正常回到空闲。
3. **手动退出：通过。** 通过设备手动退出接口触发与 Logo 长按相同的服务方法，服务器记录退出原因为 `manual`，告别、`goodbye`、播放排空和回到空闲的顺序完整通过。物理 Logo 到该方法的接线已经编译并烧录；后续整机回归仍应顺手补一次真实长按触摸。
4. **保持安静：实机通过。** 在无电视、视频和旁人说话的环境中，铜豆从 `13:53:09` 开始持续上传，超过原本地 `20 s` 时仍保持监听；服务器持续记录到 `1900` 包以上，`voice_packets=0`。`13:55:09`，服务器按 `120 s` 无声时限以 `no_voice` 进入统一退出出口，生成“你好像去忙啦，那我先安静待着。有需要再叫我。”并发送完整告别音频；`13:55:19` 发送 `goodbye`。铜豆记录软件队列排空、扬声器尾音排空和 `conversation ended source=server_goodbye state=idle`，最终 `lastTurnOk=true`、错误码为空，并自动重新连接。
5. **网络断开：通过。** 实机监听时停止服务器，铜豆记录 `voice_backend_disconnected` 和 `voice abnormal fallback reason=backend_disconnected`，没有伪造 `goodbye`，并播放本地失败提示。服务器恢复后设备重新连接并完成握手。

#### 最终结论

正常在线退出已经由服务器统一裁决。铜豆只负责发起请求和执行服务器给出的退出结果；只有连接断开、发送失败或服务器无响应时，才走本地异常兜底。语义退出、精确退出、手动退出、纯安静 `120 s` 退出和网络断开五类路径均已完成实机验证。

### 22.13 回滚原则

服务器和固件改动必须能分开回滚：

- 只回滚服务器时，铜豆仍能忽略未收到的 `goodbye`，但不能宣称新退出机制验收通过。
- 只回滚固件时，服务器发送 `goodbye` 后仍关闭连接，旧固件按连接关闭回到空闲。
- 任何回滚都不得撤销已经通过实机验收的 PSRAM、Opus 编解码和连续对话主链路修复。

## 23. 阶段 8：响应速度和空闲连接保活

### 23.1 本阶段只解决什么

本阶段不再调整麦克风、音量判断、连续对话和退出规则，只处理两个已经有日志证据的问题：

1. 铜豆处于空闲待命时，固件每 `15 s` 发送一次 WebSocket 底层心跳，服务器连接实际健康，但服务器原来的业务无活动计时器仍会在约 `180 s` 后主动关闭连接，造成无意义的重连和组件重新初始化。
2. 用户开口后，服务器才开始建立讯飞语音识别连接。实测一轮连接等待为 `2007 ms`，这段等待直接叠加在用户说话后的响应时间上。

### 23.2 修改边界

本阶段允许修改：

- 服务器空闲连接超时判断。
- 讯飞语音识别连接的建立时机、失败回退和未使用连接回收。
- 识别文字到首包回复音频之间的分段耗时日志。
- 与上述机制直接相关的自动化测试。

本阶段明确不改：

- 固件 WebSocket 心跳参数。
- 麦克风增益、音量门限和 VAD（是否有人说话）阈值。
- 讯飞识别参数、对话模型、工具判断和语音合成音色。
- 已经通过验收的连续对话和正常退出时序。

### 23.3 空闲连接保活机制

正常逻辑固定为：

```text
设备已绑定且没有开始对话
  -> 不使用业务无活动时间关闭连接
  -> 由 WebSocket 底层 ping/pong 心跳判断网络是否真实可用
  -> 心跳失败或网络断开时按异常连接处理
```

以下两个超时仍然保留：

- 已经进入连续对话后，用户持续不说话达到服务器配置时间，仍由服务器走“告别语 -> `tts stop` -> `goodbye`”正常退出。
- 尚未完成绑定的连接仍可使用绑定超时，不能永久占用连接。

实机验收结果：铜豆在 `15:54:34` 完成正常退出后的重新连接，持续空闲到 `15:57:55`，超过旧的 `180 s` 关闭点；期间没有“连接超时”、没有静默关闭，也没有第二次握手重连。

### 23.4 识别连接提前握手机制

讯飞官方文档说明，累计 `10 s` 不发送数据会触发读取超时。当前实现使用更保守的 `5 s` 窗口，参考：[讯飞语音听写流式版 WebAPI 文档](https://www.xfyun.cn/doc/asr/voicedictation/API.html)。

当前时序为：

```text
服务器收到本轮第一包音频
  -> 后台提前建立讯飞 WebSocket，只完成鉴权和网络握手，不发送音频
  -> 本地 VAD 确认用户开口
  -> 预连接可用：立即复用并发送缓存音频
  -> 预连接失败或不可用：回到原来的现场建连流程
  -> 5 s 内用户没有开口：关闭预连接，本轮不再反复重建
```

这样做不会绕过本地 VAD，也不会把环境底噪提前送给讯飞。它只是像“先把电话拨通但不讲话”，等本地确认用户真的开口后再发送声音。

### 23.5 强制耗时日志

每轮至少记录：

- `asr_preconnect_start`：提前握手开始。
- `asr_connected`：是否复用预连接、用户开口后实际等待了多久。
- `chat_start`：识别文字进入回复阶段。
- `llm_first_chunk`：对话模型开始返回数据。
- `tts_connected`：语音合成连接完成。
- `tts_first_text_sent`：第一段文字送入合成。
- `tts_first_audio_received`：收到第一段合成音频。
- `first_tts_packet_sent`：首包回复音频真正发给铜豆。

### 23.6 自动化和实机结果

- 原有退出和保活测试 `4` 项通过。
- 新增识别预连接测试 `2` 项通过：用户及时开口时复用连接；用户没有开口时按时关闭未使用连接。
- 合计 `6` 项服务器自动化测试通过。
- 优化前实测：本地确认用户开口后，讯飞连接等待 `2007 ms`。
- 优化后实测：日志出现 `preconnected=1`，本地确认用户开口后连接等待为 `0 ms`，该轮直接消除约 `2 s` 等待。
- 优化后回复阶段：模型首个数据 `2922 ms`，语音合成连接 `3022 ms`，首段文字 `4146 ms`，首段合成音频 `4901 ms`，服务器首包音频 `4922 ms`。优化前服务器首包音频为 `4979 ms`，说明本次修改没有拖慢识别文字之后的回复链路。
- 无人继续说话的跟随监听在 `16:01:40` 建立预连接，`16:01:46` 记录“ASR预连接未使用，已按时关闭”，证明回收机制生效。
- 优化后的安静退出回归通过：服务器在 `16:03:40` 仍按 `no_voice` 进入统一退出出口，`16:03:47` 发送 `goodbye`，设备随后重新连接；提前握手没有改变正常退出机制。

### 23.7 当前结论和下一步边界

空闲连接误关闭已经修复，用户开口后的讯飞连接等待也已经从约 `2 s` 降到本轮 `0 ms`。当前新的主要耗时是对话模型首个数据约 `3 s`，其次是模型开始返回到首段文字可送入语音合成之间约 `1.2 s`。

下一步如果继续提速，必须单独评估模型和工具调用机制，不能为了少几百毫秒直接降低退出、提醒、天气等工具判断的正确率。本阶段不继续修改这部分逻辑。
