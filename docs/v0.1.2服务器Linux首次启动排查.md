## 问题一：两个配置变量为空

结论：发布包漏了 Linux 初始化入口和说明，导致首次启动步骤不完整；不是版本过旧。

原 ZIP 根目录 `.env.example` 包含两项：

```dotenv
MYSQL_ROOT_PASSWORD=GENERATED_ON_FIRST_START
VOICEPRINT_API_TOKEN=GENERATED_ON_FIRST_START
```

示例并未漏打包；真实 `.env` 被打包脚本明确排除，这是正确的凭据保护。
占位文字不是可用密码。Compose 不会自动读取 `.env.example`，也不会运行启动脚本。

原 ZIP 中 `scripts/start_tongdou_server.ps1` 才负责：

1. 用系统安全随机数生成数据库密码，创建根目录 `.env`。
2. 生成或补齐声纹令牌。
3. 显式执行本地镜像构建。
4. 等待管理端数据库初始化，读取 `server.secret`。
5. 初始化声纹数据库、更新内部声纹地址和局域网访问地址、清理对应缓存。
6. 写入 `data/.config.yaml`，使语音服务能带正确密钥访问管理端。

`START_TONGDOU_SERVER.bat` 调用上述脚本。原包没有 `.sh` 或其他 Linux 等价入口；
`README.md` 的首次启动步骤只描述 Windows。

Andrew 的 `docker compose up` 跳过全部初始化。干净目录里没有根目录 `.env`，
且没有导出的同名变量，`${MYSQL_ROOT_PASSWORD}` 和 `${VOICEPRINT_API_TOKEN}`
就被替换成空字符串。`docker-compose.yml` 根本没有容器级 `env_file` 设置；
它使用 `environment` 把替换结果传给各容器。

Compose 普通变量加载顺序是：当前 shell 环境优先；未指定 `--env-file` 时读取工作目录
`.env`；显式文件或项目目录 `.env` 按官方规则参与后续加载。容器的 `env_file`
只负责容器环境，不能补救 Compose 文件自身 `${...}` 的替换。
参考：[Docker 官方变量替换规则](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)。

实际影响：

| 变量 | 接收位置 | 空值后果 |
| --- | --- | --- |
| `MYSQL_ROOT_PASSWORD` | `tongdou-db`、管理端数据库连接密码、声纹数据库连接密码 | 全新 MySQL 没有设置允许空密码或随机密码选项，按官方入口规则会拒绝初始化；管理端和声纹也拿不到有效数据库密码 |
| `VOICEPRINT_API_TOKEN` | 声纹服务环境、管理端声纹地址、声纹健康检查 | `main/xiaozhi-server/docker/voiceprint/start_voiceprint.py` 要求至少 32 位合规字符，空值直接抛出异常；健康依赖不能满足 |

MySQL 依据：[官方容器入口脚本的最小密码检查](https://github.com/docker-library/mysql/blob/master/docker-entrypoint.sh)。
上述为配置和代码可确认的后果，不表示 Andrew 的日志已经显示这些后续错误。
此外，`main/xiaozhi-server/config/config_loader.py` 会读取 `data/.config.yaml`；
只补两个环境变量仍不能替代管理端密钥和语音配置初始化。

## 问题二：三个镜像拉取被拒绝

原 ZIP 的 `docker-compose.yml` 同时有 `image` 和 `build`，没有 `pull_policy`：

| 本地标签 | 构建说明文件 | 构建目录 |
| --- | --- | --- |
| `tongdou/server:v0.1.2` | `Dockerfile-server` | 包根目录 `.` |
| `tongdou/manager:v0.1.2` | `Dockerfile-web` | 包根目录 `.` |
| `tongdou/voiceprint:v0.1.2` | `main/xiaozhi-server/docker/voiceprint/Dockerfile` | 包根目录 `.` |

三份构建说明及对应源码输入都在压缩包内。打包脚本赋予这些标签，Windows 脚本也明确
执行 `docker compose build`。因此它们设计上是本地构建产物，不是测试者必须登录下载的成品镜像。

没有指定拉取策略时，Compose 会先尝试拉取，找不到再从源码构建。
参考：[Docker 官方构建规则](https://docs.docker.com/reference/compose-file/build/#using-build-and-image)。
因此 `pull access denied` 可以是后续本地构建前的警告，不能仅凭这段日志认定部署最终失败，
也没有依据要求 Andrew 执行 `docker login`。本次没有用远端登录凭据试图绕过问题。

MySQL、Redis 和构建基础镜像仍需远端下载；声纹基础镜像固定在 `ghcr.nju.edu.cn`，
语音构建使用阿里云软件源。网络可达性、基础镜像架构和依赖安装仍需实际构建验证，
不能把这些外部依赖宣称为已通过。

## 最小修复

交付目录只改一个已有文件，增加三个文件：

- `docker-compose.yml`：三个本地镜像设为 `pull_policy: never`；两个凭据改用必填替换，缺失时直接提示先初始化。
- `START_TONGDOU_SERVER.sh`：Linux 入口，自动定位包目录，通过 `sh` 执行无需依赖 ZIP 执行权限。
- `scripts/start_tongdou_server.py`：标准库实现首次初始化、明确构建、分阶段启动和状态检查。
- `LINUX_FIRST_START_EN.md`：英文前置条件、首次启动、现有目录补丁步骤、备份和失败边界。

维护文件：

- `tools/fix_server_linux_startup.py`：向交付目录安装上述修复，可重复执行，不调用 Docker。
- `tools/build_early_tester_release.py`：打包阶段调用安装函数，防止以后再次漏掉 Linux 入口；
  修正天气示例清理时复用 `old` 变量、覆盖旧发布目录路径的问题，避免后续打包报错。
  这是当前打包脚本中的另一个缺陷，不是 Andrew 已发布 ZIP 出现启动警告的根因。
- `tools/release_templates/server/README.md` 及新增 Linux 模板：补齐后续发布包说明入口。
- `tools/tests/test_server_linux_startup.py`：启动逻辑回归测试。
- `tools/tests/verify_server_package_linux.py`：从原 ZIP 开始的 Linux 原生 Compose 验证。

安全与功能边界：

- 使用 `secrets.token_urlsafe(32)` 分别生成凭据，私有文件权限为 `0600`；不打印密钥。
- `.env` 对 Linux 入口权威，清除子进程中可能覆盖它的同名环境变量，显式指定所有配置路径和项目名。
- 保留有效 `.env`、已有语音配置和工具配置。非空数据库或声纹数据卷缺凭据时拒绝自动换密码。
- 失败首次启动可能已经创建空卷；用临时容器只读检查，确认完全为空后继续初始化，不删卷。
- 临时只读检查会按需下载 `mysql:8.0`，不启动 MySQL 服务；无法检查时停止。
- 正常入口显式构建三个镜像，再使用 `up --no-build --wait`；构建失败不会继续启动。
- 健康检查之外，补查语音监听端口和管理页面返回状态，检查失败不打印启动成功。
- Windows 启动文件逐字节保持原状；仍走原有显式构建流程。
- Linux 的可选天气/搜索凭据通过管理页面配置，没有移植 Windows 专用共享测试凭据导入功能。
- 未改业务代码、固件、数据库存储格式和其他正在修改的文件。
