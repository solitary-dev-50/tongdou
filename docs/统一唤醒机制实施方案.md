# 铜豆统一唤醒机制实施方案

## 1. 一句话结论

铜豆的唤醒不是“Logo 触摸功能”，而是一套统一入口机制：Logo 触摸和本地语音唤醒只负责发出不同来源的唤醒事件，后面必须共用已经跑通的实时语音、连续对话和服务器退出链路。

本方案先落地两个正式入口：

- Logo 单击唤醒。
- 本地中文语音唤醒，口语为“你好，铜豆”，协议规范文本为 `你好铜豆`。

铜豆不是为某一家语音识别服务设计的。唤醒检测在设备本地完成，服务器只接收标准唤醒事件和后续音频；以后更换语音识别、大模型或语音合成供应商，不应改动本地唤醒入口。

## 2. 本文负责什么

本文只负责：

- 统一 Logo 和本地语音唤醒的入口时序。
- 选择适合当前 N4R2 硬件的本地唤醒模型路线。
- 规定服务器如何识别规范唤醒词并快速回应。
- 规定多语种唤醒语言包的边界。
- 给出分阶段实施、日志、测试和回滚清单。

本文不负责：

- 重新设计已经跑通的实时语音上行、识别、回复、播放和正常退出链路。
- 把雷达变成语音唤醒开关。
- 更换当前语音识别、大模型或语音合成供应商。
- 为了接唤醒词整体迁移固件框架。

## 3. 已确认的当前基线

### 3.1 已经跑通的能力

- `LocalAudioPipeline` 已经在本地持续读取 16kHz、16 位、单声道麦克风数据。
- 待机时普通环境声音不会上传服务器。
- Logo 单击已经通过统一的 `RealtimeVoiceService::startAutoTurn()` 开始语音会话。
- 一次回复结束后可以自动进入连续对话。
- 正常在线退出由服务器发送告别语和明确的 `goodbye`，铜豆等扬声器尾音真正播完后回到待机。
- 网络故障才走铜豆本地异常兜底。

### 3.2 当前资源基线

`2026-08-24` 基线编译结果：

| 项目 | 当前值 | 上限或实机情况 |
| --- | ---: | ---: |
| 程序闪存 | `1,818,865` 字节 | 应用分区 `3,145,728` 字节 |
| 应用分区余量 | `1,326,863` 字节 | 约 `1.27 MiB` |
| 静态内部内存 | `117,848` 字节 | 编译期上限 `327,680` 字节 |
| 外部扩展内存总量 | 约 `2.0 MB` | 实机识别成功 |
| 稳定语音回合前外部内存剩余 | 约 `2,005,203` 字节 | 已通过实机语音测试 |

这里必须区分两件事：

- 外部扩展内存已经启用，不是一直闲置。
- 当前没有加载本地唤醒模型，所以大部分外部扩展内存仍可供唤醒模型使用。

### 3.3 当前工具链边界

铜豆当前稳定工具链是：

- Arduino ESP32 `2.0.17`。
- ESP-IDF `4.4.7`，即乐鑫底层开发框架 4.4.7。
- PlatformIO Espressif32 `6.10.0`。

当前小智代码使用 ESP-SR `2.4.7`。它的唤醒架构可以参考，但依赖版本不能原样复制到铜豆，否则任务会从“增加本地唤醒”扩大成“升级整套固件底座”。

### 3.4 本轮实施后的实测资源

`2026-08-24` 已在当前铜豆实机完成模型、正式固件和现有语音编解码器同时启动：

| 项目 | 实测值 | 结果 |
| --- | ---: | --- |
| ESP-SR 版本 | `1.4.2` | 与现有底层框架兼容 |
| 唤醒模型 | `mn4q8_cn` | 已从独立模型分区加载 |
| 模型镜像 | `901,693` 字节 | 小于 `983,040` 字节模型分区 |
| 正式固件 | `2,129,553` 字节 | 小于 `3,080,192` 字节应用分区 |
| 静态内部内存 | `129,144` 字节 | 编译占用 `39.4%` |
| 唤醒模型刚创建后外部内存剩余 | `1,053,243` 字节 | 模型和 32KB 音频队列已在内存中 |
| 语音编解码器创建前外部内存剩余 | `1,015,335` 字节 | 联网等常驻服务也已启动 |
| 语音编解码器创建后外部内存剩余 | `958,967` 字节 | 唤醒模型与现有语音链路可以同时运行 |

实机启动日志已经确认：

- 模型分区存在且模型创建成功。
- 本地唤醒任务进入待命状态。
- 语音编解码器随后创建成功。
- WebSocket 与服务器完成握手并进入 `ready`。
- 服务器就绪后，本地唤醒检测自动进入 `armed=1`。

这证明“2MB 外部扩展内存能否同时容纳本地唤醒和现有语音链路”已经过关。它还不能代替口令命中率、误触发和距离测试。

## 4. 三方职责

### 4.1 铜豆固件

铜豆负责：

- 麦克风本地持续采样。
- 待机时运行一个本地唤醒模型。
- 检测到唤醒词后生成一次性唤醒事件。
- 禁止同一句声音重复触发。
- 将规范唤醒文本发给服务器。
- 复用现有自动监听入口，不新增第二套语音上传逻辑。
- 会话开始后暂停普通待机唤醒检测；会话正常或异常结束后恢复。
- 本地模型不可用时保留 Logo 唤醒。

铜豆不负责：

- 用云端持续监听环境声音。
- 决定服务器使用哪一家语音识别服务。
- 自己生成正常在线告别语或抢先结束服务器会话。

### 4.2 服务器

服务器负责：

- 使用同一套规则规范化输入文本和配置中的唤醒词。
- 识别 `你好铜豆`、`你好 铜豆`、`你好，铜豆` 等等价写法。
- 对英文等拉丁文字忽略大小写和分隔空格。
- 收到明确唤醒事件后走固定的快速问候出口，不把唤醒词当普通问题交给大模型。
- 唤醒问候结束后允许设备进入现有连续对话。
- 保持正常在线退出的唯一裁判身份。

服务器的 `wakeup_words` 参数只是协议别名表，不是本地声音模型。只改服务器参数，设备不会凭空获得本地唤醒能力。

### 4.3 本地模型

本地模型只负责回答一个问题：

> 刚才这段声音是不是当前启用的唤醒词？

它不负责语音识别全文、不负责理解用户意图，也不绑定讯飞或其他云服务。

## 5. 统一唤醒事件

内部统一事件至少包含：

| 字段 | 含义 |
| --- | --- |
| `source` | 来源：Logo 或本地语音 |
| `canonicalText` | 规范文本，例如 `你好铜豆` |
| `locale` | 当前唤醒语言，例如 `zh-CN` |
| `detectedAtMs` | 本地检测完成时间 |

第一版不把模型概率、原始音频或服务器供应商写进统一事件。需要诊断时把概率和资源占用写入日志即可。

## 6. 统一时序

### 6.1 Logo 单击

```text
Logo 单击
-> 生成 source=logo 的唤醒事件
-> 检查现有语音服务是否可进入新会话
-> 调用现有 startAutoTurn()
-> 上传用户说话
-> 服务器识别、回复
-> 进入现有连续对话
```

Logo 继续作为无语言、无模型依赖的永久兜底入口。

### 6.2 本地语音唤醒

```text
待机本地采音
-> 当前语言模型检测“你好，铜豆”
-> 立即锁住本次检测，防止重复触发
-> 向服务器发送 listen/detect，text=你好铜豆
-> 进入现有自动监听入口
-> 服务器走快速问候，不进入大模型
-> 快速问候播放结束
-> 进入现有连续对话监听
```

这里对齐的是小智已经验证过的机制：先发送明确的唤醒事件，再切入正常监听；不是复制小智的整个固件。

### 6.3 仅说唤醒词

用户只说“你好，铜豆”时：

- 铜豆应在本地确认触发。
- 服务器应快速回应简短问候。
- 问候播放结束后自动等待用户下一句话。
- 不应把“你好，铜豆”送给大模型生成随机长回复。

### 6.4 唤醒词后紧接任务

最终目标是支持：

> 你好，铜豆，今天天气怎么样？

第一阶段先保证“唤醒词”和“下一句话”不丢失。检测完成后立即开启上传，优先捕获唤醒词后的尾部声音。

如果实机证明任务开头仍被切掉，再增加短前置缓存。未用日志证明丢字前，不先堆一份大缓存。

## 7. 本地模型选择

### 7.1 小智当前做法

小智提供两类本地做法：

- WakeNet：真正的唤醒词模型，占用较低、误触发控制更适合量产，但自定义品牌词需要专门模型。
- MultiNet：离线命令词识别模型，可以直接配置中文或英文命令，被小智用作自定义唤醒词入口。

### 7.2 铜豆当前硬件能承受什么

乐鑫公开资源数据：

| 模型 | 外部内存占用 | 当前 N4R2 判断 |
| --- | ---: | --- |
| WakeNet9 量化模型 | 约 `324 KB` | 合适，但需要“你好，铜豆”专用模型 |
| MultiNet4 Q8 中文 | 约 `1009 KB` | 可用于第一阶段验证 |
| MultiNet5 Q8 中文 | 约 `2310 KB` | 超过 2MB，不能使用 |
| MultiNet5 Q8 英文 | 约 `2310 KB` | 超过 2MB，不能使用 |

音频前端还会额外占用约 `740 KB` 到 `820 KB` 外部内存。因此中文 MultiNet4 Q8 加音频前端虽然理论上能放进 2MB，但余量较紧，必须用实机内存日志验收，不能只看编译成功。

### 7.3 当前决定

分成两个阶段：

1. 工程验证版：使用兼容 ESP-IDF 4.4.7 的 ESP-SR 版本和中文 MultiNet4 Q8，只配置 `ni hao tong dou`，验证完整入口和真实误触发情况。
2. 量产目标版：取得或训练“你好，铜豆”的 WakeNet9 专用模型后替换 MultiNet，降低内存、功耗和误触发风险。

不能做的事：

- 不能直接使用需要超过 2MB 外部内存的 MultiNet5/6/7。
- 不能同时加载中文和英文 MultiNet。
- 不能为了接 ESP-SR 2.4.7 直接升级整个稳定固件框架。
- 不能把工程验证版 MultiNet 宣传成已经达到量产唤醒可靠性。

## 8. 闪存安排

当前 `huge_app.csv` 只有约 3MB 应用分区，没有独立模型分区。

第一阶段采用 4MB 模组可用的独立模型布局：

```text
0x000000 - 0x00FFFF  启动、分区表、系统数据
0x010000 - 0x0FFFFF  本地模型分区，约 960KB
0x100000 - 0x3FFFFF  正式应用分区，3MB
```

中文 MultiNet4 Q8 原始模型约 `901,533` 字节，理论上可以放入约 `983,040` 字节的模型分区，但打包头和对齐也要计入。构建时必须检查最终模型镜像尺寸，不能按原始文件大小想当然。

模型和应用要分别烧录并分别记录版本。只烧应用、不烧模型时，固件必须明确打印“模型缺失”，然后保留 Logo 唤醒，不能反复重启。

## 9. 内存边界

优先放外部扩展内存：

- 唤醒模型运行内存。
- 音频前端的大缓冲。
- 后续经过证明确有必要的短前置缓存。

必须保留在内部内存：

- 麦克风硬件直接访问缓冲。
- 任务控制结构和少量实时状态。
- 现有已经验证稳定的关键音频发送缓冲。

唤醒模型初始化后必须打印：

- 模型名称和版本。
- 当前语言和规范唤醒词。
- 模型分区是否找到。
- 初始化是否成功和原始错误码。
- 初始化前后内部内存剩余和最大连续块。
- 初始化前后外部内存剩余和最大连续块。

## 10. 多语种机制

### 10.1 原则

多语种不是把所有模型同时塞进 2MB 外部内存，而是：

> 每台设备保存多个可选语言包信息，但同一时刻只安装并运行一个本地唤醒模型。

### 10.2 语言包内容

每个语言包至少包含：

| 字段 | 示例 |
| --- | --- |
| 语言编号 | `zh-CN` |
| 口语显示 | `你好，铜豆` |
| 协议规范文本 | `你好铜豆` |
| 模型类型 | `WakeNet9` 或工程验证版 `MultiNet4Q8` |
| 模型版本 | 可追踪版本号 |
| 模型校验值 | 防止下载或烧录损坏 |
| 服务器别名 | 同一语言允许的等价文本 |

### 10.3 当前语言策略

- 第一阶段只交付中文 `zh-CN` 本地模型。
- Logo 在所有语言下始终可用。
- 英文、法文等不能只翻译显示文字，必须有对应声音模型。
- 当前硬件不能运行英文 MultiNet5 Q8；英文量产入口应使用专用 WakeNet 模型。
- 服务器可以同时保存多语言规范别名，但设备只运行当前激活的一个本地模型。
- 本地唤醒语言与界面语言允许暂时分开保存，避免改变现有语音提示语言时意外卸掉可用唤醒模型。

## 11. 服务器修复清单

1. 新增唤醒词专用规范化函数。
2. 输入文本和配置别名必须经过同一函数。
3. 规范化时移除标点和所有空白，并对拉丁文字忽略大小写。
4. 删除依赖内部假唤醒词“嘿，你好呀”再次匹配的做法。
5. `listen/detect` 命中真实唤醒词后，直接把真实规范文本送入统一快速问候出口。
6. 不命中唤醒词的 `detect` 文本仍按原有文字入口处理。
7. 增加中文空格、中文标点、英文空格和英文大小写测试。
8. 更新服务器参数后让设备重连，避免旧连接继续持有旧配置副本。

第一版服务器别名建议保留兼容项：

```text
你好铜豆;铜豆;HelloTongDou;TongDou
```

内部假词不再放进配置。

## 12. 固件实施清单

### 阶段 0：保留基线

- 记录当前编译占用。
- 记录当前实机内部和外部内存。
- 保存 Logo、连续对话和正常退出的回归日志。

### 阶段 1：模型构建探针

- 新建 4MB 模型分区表。
- 固定使用与 ESP-IDF 4.4.7 兼容的官方 ESP-SR 依赖。
- 只打包中文 MultiNet4 Q8。
- 只编译最小模型加载和创建探针。
- 未通过模型尺寸、链接和创建测试前，不接业务入口。

### 阶段 2：本地检测模块

新增模块只能负责：

> 接收本地 16kHz 单声道音频，判断当前唤醒词是否命中，并产生一次性事件。

它不能控制服务器、剧情、灯光、电机或退出逻辑。

### 阶段 3：接入本地采音

- `LocalAudioPipeline` 继续是麦克风数据唯一读取者。
- 通过小而清楚的本地音频处理接口把同一帧交给唤醒检测模块。
- 不允许唤醒模块再次直接读取 I2S 麦克风，避免两个任务抢同一硬件。
- 上传队列和唤醒检测互不替代。

### 阶段 4：接入统一入口

- Logo 和语音检测都生成统一唤醒事件。
- Logo 保持现有自动监听行为。
- 语音检测先发送规范 `detect` 文本，再进入现有自动监听行为。
- 复用现有连续对话和服务器退出机制。
- 会话期间停用普通待机唤醒检测；回到空闲后恢复。

### 阶段 5：保护性降级

- 模型分区缺失：打印错误，Logo 可用。
- 模型创建失败：打印错误和内存，Logo 可用。
- 服务器未连接：不伪装成功唤醒，播放现有错误提示或保持明确日志。
- 不允许因为唤醒模块失败导致设备重启循环。

## 13. 必须新增的关键日志

```text
wake model init locale=zh-CN model=mn4q8_cn ok=1
wake memory phase=before ...
wake memory phase=after ...
wake detector state=enabled
wake detected source=voice text=你好铜豆 t=...
wake detect sent ok=1 text=你好铜豆
wake voice turn start ok=1
wake detector state=disabled reason=conversation_active
wake detector state=enabled reason=conversation_ended
```

失败时必须有：

```text
wake model init ok=0 code=... message=...
wake detect send ok=0 backend_state=...
wake voice turn start ok=0 code=... message=...
```

## 14. 验收清单

### 14.1 编译和资源

- [ ] 正式固件编译通过。
- [ ] 应用镜像小于 3MB。
- [ ] 模型镜像不超过模型分区。
- [ ] 实机识别到 2MB 外部扩展内存。
- [ ] 唤醒模型和现有编解码器可同时创建。
- [ ] 最小内部连续内存不低于现有语音链路安全线。

### 14.2 Logo 唤醒

- [ ] 单击 Logo 仍能开始第一轮语音。
- [ ] 回复后仍能连续对话。
- [ ] 服务器告别后仍等扬声器播放完再待机。

### 14.3 中文语音唤醒

- [ ] 安静环境正常音量说“你好，铜豆”可唤醒。
- [ ] 近距离、1 米、3 米分别测试。
- [ ] 男声、女声各测试至少 20 次。
- [ ] 快速说、正常说、慢速说各测试至少 20 次。
- [ ] 单说“铜豆”、日常聊天提到“铜豆”不应大量误触发。
- [ ] 只说唤醒词时得到短问候并进入连续监听。
- [ ] “你好，铜豆”后紧接任务时不丢任务开头。

### 14.4 抗误触发

### 16.3 开机成功提示与唤醒就绪时序修复

`2026-08-26` 的实机日志出现过以下现象：设备开机后很快播放成功提示音，但用户随后每隔 3～4 秒连续说了 6 次“你好，铜豆”，直到很久以后才第一次唤醒。

日志已经把原因分成了两段：

1. 唤醒模型很早就完成初始化，但当时语音后台尚未就绪，所以待机检测保持 `armed=0`。这段时间说出的唤醒词不会进入模型检测。
2. 设备第一次请求激活服务时返回 `status=-1`，对应底层连接被拒绝。旧实现不分故障轻重，直接等待 30 秒才重试；成功提示音却在无线网络刚连接时就已经播放，造成“听起来已经完全就绪，实际上还不能唤醒”的假象。

这不是唤醒模型不灵敏，也不是麦克风、讯飞识别或大模型故障。语音后台真正就绪后，同一轮日志的唤醒概率达到 `0.854`，说明当时的模型输入和命中能力正常。

本轮修复只调整启动时序：

- 无线网络连接事件只记录 `wifi_ready`，不再播放通用成功提示音。
- 设备激活或配置请求连续失败时，依次等待 1 秒、2 秒、5 秒重试；仍然失败才进入 30 秒稳定重试，避免一次瞬时拒绝让整机假死半分钟。
- `status=-1` 等网络错误同时打印可读原因，不能再只留一个数字。
- 只有语音后台已握手、本地唤醒模型可用、语音状态空闲且喇叭没有其他内容时，才播放一次 `voice_ready` 成功提示音。
- 成功提示音在喇叭中真正排空之前，本地唤醒保持关闭；播放完成后才打印 `wake_ready` 并开放检测，避免铜豆自己的提示音进入唤醒模型。
- 后续网络短暂断开仍按原有状态门控关闭唤醒，重连后自动恢复，但开机成功提示不重复播放。

验收必须看到以下顺序，顺序不能颠倒：

```text
startup timeline wifi_ready ... waiting_voice_backend=1
voice client state=ready
startup timeline voice_backend_ready ... cue=success
audio cue voice_ready ok=1 ...
startup timeline wake_ready ...
wake detector armed=1
```

如果首次激活请求失败，还必须看到短间隔重试，而不是直接沉默 30 秒：

```text
device activation failed: ota_post_failed status=-1 error=connection refused
device activation retry failures=1 delay_ms=1000
```

正式固件已在当前铜豆实机完成烧录和正常启动验收：

```text
startup timeline wifi_ready elapsed_ms=2919 waiting_voice_backend=1
voice client state=ready
startup timeline voice_backend_ready elapsed_ms=4520 cue=success
audio cue voice_ready ok=1 packets=18 samples=17280
startup timeline wake_ready elapsed_ms=5631
wake detector armed=1
```

这轮启动证明成功提示没有在无线网络刚连接时提前播放；提示音开始于语音后台握手成功之后，并且直到喇叭排空才开放唤醒。随后只说一次“你好，铜豆”即命中，概率为 `0.886`，服务器问候和连续监听正常接上。

本轮服务端正常在线，因此没有人为关闭激活服务来制造故障；1 秒、2 秒、5 秒的快速重试分支已经通过编译和代码检查，但仍保留到真实瞬时故障或专门断网测试时补充串口证据。不能为了凑日志影响正在使用的服务器。

### 16.4 识别超时调整为 10 秒（用户反馈明显改善）

`2026-09-09` 用户反馈待机时反复说唤醒词仍可能没有回应。两次串口诊断均为 `ready=1 armed=1`，唤醒队列丢弃数为 0，模型处理量基本追上收到的采样量；约 45.9 秒音频发生 15 次超时清空，约 15 秒音频发生 5 次超时清空。

按用户要求，将 `LocalWakeWordDetector.cpp` 的 `kRecognitionTimeoutMs` 从 `3000` 改为 `10000` 毫秒，以减少识别中途清空的次数。模型、声音放大量、识别门槛和会话开关规则保持原样。命中后仍立即产生唤醒事件，不需要等满 10 秒。

当前证据确认了频繁超时，尚未证明失败喊话恰好跨过清空边界。此调整用于实机对照，不能写成唤醒困难已经修复。

正式固件编译通过后，用户于同日反馈“现在好很多了”。随附实机日志记录了 9 次本地唤醒命中，评分为 `0.855 / 0.949 / 0.927 / 0.801 / 0.862 / 0.952 / 0.937 / 0.862 / 0.947`；9 次均成功启动唤醒会话，随后均记录到服务器正常结束对话。此记录支持保留 10 秒设置继续观察，但没有总喊话次数，不能写成首次唤醒成功率为 100%。新日志未包含 `wake diagnostic`，实际超时间隔仍需通过诊断计数核验；长时间待机、不同距离和背景声音误唤醒也尚未完成验收。

烧录后，在持续待机且没有命中的情况下，使用 `wake` 命令检查超时计数是否约每 10 秒增加一次；再以相同距离、音量完成至少 10 次独立唤醒，记录首次喊话成功数，并检查背景声音是否更容易误唤醒。若没有改善或误唤醒增加，可将该常量恢复为 `3000`。
