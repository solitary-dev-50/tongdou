# 事件提醒系统实施方案

## 1. 一句话目标

把铜豆现有的“一次性到点播报”升级为可关联、可延后、可确认、不会因播报打断而丢失对话的事件提醒系统。

这次不采用“提醒播完后强行再开一次麦克风”的临时补丁。数据、调度、播报、回应和失败状态必须形成同一条可追踪链路。

## 2. 用户看到的规则

### 2.1 普通一次性提醒

用户说：

> 5 分钟后提醒我喝水。

铜豆只创建一个到点节点。到点播报完成后，用户可以直接说“再过 5 分钟提醒我”。

### 2.2 带提前量的事件提醒

用户说：

> 10 点开会，提前 10 分钟提醒我准备材料。

铜豆必须创建同一事件下的两个节点：

```text
会议事件：10:00
├─ 09:50 提前提醒：准备会议材料
└─ 10:00 正点提醒：该开会了
```

创建成功后的确认必须把两个时间说清楚，不能只说“已经设置好了”。

### 2.3 延后提醒

09:50 播报结束后，用户直接说：

> 5 分钟后再提醒我。

铜豆应在同一会议事件下增加 09:55 延后节点：

```text
会议事件：10:00
├─ 09:50 提前提醒：已送达
├─ 09:55 延后提醒：待送达
└─ 10:00 正点提醒：待送达
```

延后节点不能覆盖或删除正点节点。用户只有明确说“正点不用提醒”“取消会议提醒”等话时，才能取消相应节点或整个事件。

### 2.4 第一版范围

第一版不是“只能做一次性提醒”。第一版正式支持：

- 普通一次性提醒。
- 同一事件下的提前提醒、用户临时延后提醒和正点提醒。
- 查询和整件事取消。

每天、每周、工作日等周期重复日程暂不进入第一版。周期提醒需要单独定义重复规则、跨时区、夏令时、错过补发和结束条件，不能把一次性节点简单复制成一个看似能用的循环。

## 3. 雷达边界

LD2412 只能说明铜豆附近是否检测到目标，不能确认目标身份，也不能判断用户是否已经去开会。

因此第一阶段执行以下硬规则：

- 正点节点按计划保留并触发，雷达不能删除或完成提醒。
- 播报时记录附近有人或无人，供后续送达策略和日志分析使用。
- 雷达故障、未安装或短暂漏检不能造成提醒消失。
- 后续若增加“无人时静默、回来后补提醒”，必须先增加雷达健康状态和未送达队列，不能只凭一个低电平跳过播报。

## 4. 数据模型

### 4.1 事件和节点

设备继续使用固定提醒槽位，但每条记录从“孤立提醒”升级为“事件节点”：

- `id`：当前节点编号。
- `eventId`：所属事件编号。
- `dueAt`：当前节点触发时间。
- `kind`：节点类型。
- `active`：记录是否有效。
- `completed`：当前节点是否已经完成送达流程。
- `text`：当前节点自己的原始正文。
- `displayBitmap`：当前节点自己的 OLED 位图。

节点类型固定为：

- `one_shot`：普通一次性提醒。
- `advance`：事件提前提醒。
- `snooze`：用户要求的延后提醒。
- `punctual`：事件正点提醒。

同一事件的节点共享 `eventId`，但各自保存时间、正文和位图。这样取消事件、查询事件和增加延后节点时不会靠文字猜关系。

### 4.2 空间边界

`reminder` 原始分区仍为 16 KB，最多保存 12 个提醒节点的位图。带提前量的会议会使用两个节点。延后提醒优先复用刚完成节点释放出来的槽位，不额外扩大闪存分区。

运行记录仍从 2 MB PSRAM 分配，不把位图重新塞回内部内存或 NVS。

### 4.3 旧数据兼容

旧记录只有 `id、dueAt、active、completed、text`。升级后必须自动迁移为：

- `eventId = id`
- `kind = one_shot`
- 原时间、正文、完成状态和位图保持不变

迁移成功后再保存新格式。不能因为结构长度变化把用户已有提醒清空。

## 5. 完成和失败规则

当前实现到点后立刻写入 `completed=true`，随后才请求服务器播报。这会造成“用户没听到，系统却认为完成”。新规则固定为：

1. 调度器发现到期节点，只交出记录，不修改完成状态。
2. OLED 显示正文。
3. 在线时请求服务器生成并发送具体提醒语音。
4. 固件等待最后一包语音真正离开喇叭。
5. 在线失败时执行当前语言通用异常播报、等待排空，再播放三声提示音。
6. 只有在线具体播报排空，或完整离线兜底序列结束后，当前节点才标记完成。

`completed` 表示铜豆已经完成一次明确的送达流程，不表示用户已经口头确认。

## 6. 提醒回应窗口

### 6.1 播报前正在连续对话

提醒到期时可以发送 `abort` 暂停当前收音，避免用户声音和提醒语音混在一起，但必须记录“对话被提醒临时暂停”。

提醒播完并确认喇叭排空后：

- 设置当前提醒上下文。
- 启动一轮最长 8 秒的提醒回应收音；到时主动停止上传，不依赖服务器全局空闲超时。
- 用户可以直接说延后、取消、确认或继续原对话。
- 服务器正常退出、手动退出和网络故障仍按原有统一出口处理。

提醒不能清空连续对话意图后悄悄回到空闲。

### 6.2 播报前处于空闲

提醒播完后同样开放一轮最长 8 秒的提醒回应窗口。用户不需要重新说唤醒词或触摸 Logo，就能说“5 分钟后再提醒我”。

若用户没有说话，回应窗口安静结束并回到空闲，不播放失败台词，不把环境底噪当成一次识别失败。

### 6.3 上下文生命周期

提醒上下文保存刚播报的真实节点编号。执行延后时，存储层再通过该节点读取真实 `eventId`，不让大模型靠正文猜事件关系。上下文在以下情况清除：

- 服务器明确结束当前对话。
- 回应窗口无人说话并超时。
- 用户用 Logo 或唤醒词开始一轮全新对话。
- 网络故障导致本轮失败。
- 新提醒取代旧提醒上下文。

## 7. MCP 工具边界

现有创建、查询、删除工具保留，并补齐事件语义。

### 7.1 创建

`tongdou.reminder.create`：

- 普通提醒只传一个到点时间和正文。
- 事件提醒额外传提前秒数和提前正文。
- 带提前量时，固件一次性创建提前节点和正点节点。
- 服务端分别为两个正文生成 OLED 位图。
- 任一必要节点创建失败时，整次创建失败，不能只留下半场会议。

### 7.2 延后

新增 `tongdou.reminder.snooze`：

- 支持相对时间或明确时间。
- 提醒回应窗口内可以省略编号，由设备使用当前提醒上下文。
- 普通对话中必须提供可靠的节点编号，不能猜。
- 新节点继承原事件编号，不修改尚未完成的正点节点。

### 7.3 删除

删除任意事件节点时，默认删除同一 `eventId` 下的全部未完成节点。若以后需要只删除正点或提前节点，应增加明确工具参数，不能复用含糊语义。

## 8. 三方时序

```text
设备本地时间到点
  -> ReminderManager 交出到期节点，不提前完成
  -> App 暂停当前上传并保存是否正在对话
  -> ReminderAlertService 显示正文并请求独立提醒播报
  -> 服务器生成含完整原文的台词并发送语音
  -> 固件等软件队列和喇叭全部排空
  -> ReminderStore 标记当前节点完成
  -> 固件设置当前提醒上下文
  -> 固件开启提醒回应监听
  -> 用户说“5 分钟后再提醒我”
  -> 服务器调用 tongdou.reminder.snooze
  -> 固件创建同 eventId 的 snooze 节点
  -> 服务器语音确认
  -> 正点节点继续保留
```

## 9. 实施顺序

1. 增加事件节点字段和旧记录迁移。
2. 让调度器不再提前标记完成。
3. 增加播报完成事件，由应用层在喇叭排空后提交完成状态。
4. 增加事件创建和延后工具。
5. 服务端为提前正文生成第二张位图。
6. 增加提醒上下文和回应监听。
7. 区分提醒回应无人说话与普通识别失败。
8. 更新查询、删除、网页接口和状态日志。
9. 编译、服务器自动测试和旧记录迁移测试。
10. 实机测试完整会议时间线。

## 10. 必测场景

- 普通一次性提醒只播一次。
- 10:00 会议同时建立 09:50 和 10:00 两个节点。
- 09:50 后说“5 分钟后再提醒我”，09:55 新增并触发，10:00 仍触发。
- 提醒前正在连续对话，提醒后可以直接继续说话。
- 提醒前空闲，播完可以直接说延后命令。
- 提醒后不说话，安静回到空闲，不播失败反馈。
- 删除任意节点后，同一事件的未完成节点全部取消。
- 在线播报完成前断电，重启后提醒不会被错误当成已送达。
- 旧固件保存的提醒升级后仍存在、时间和位图不变。
- 服务器离线时 OLED、当前语言异常播报和三声提示音仍完整执行。
- 雷达有人、无人和不可用时都不会删除正点节点。

## 11. 验收标准

只有同时满足以下条件，才能宣布事件提醒系统完成：

- 数据关系可查询、可持久化、可迁移。
- 提前、延后和正点节点互不覆盖。
- 完成状态发生在真实送达流程之后。
- 提醒后自然说话能进入服务器并调用正确工具。
- 连续对话不会被提醒永久杀死。
- 无人回应能安静收口。
- 断网、重启和存储不足都有明确日志和可预测结果。
- 正式固件编译通过，并完成至少一轮真实 09:50、09:55、10:00 等比例缩短实机验证。

## 12. 2026-08-25 实施和实测记录

### 12.1 已落地

- 旧提醒自动迁移为 `one_shot`，保留原编号、时间、正文、完成状态和位图。
- 普通提醒仍使用单节点；带提前量的事件一次建立 `advance` 和 `punctual` 两个关联节点。
- 新增 `snooze` 工具，提醒回应窗口内可以不传节点编号。
- 调度器只选择到期节点；在线语音真正离开喇叭或离线兜底完整结束后才提交完成。
- 查询只返回未完成节点；删除任一节点会取消整个关联事件。
- 提醒播报完成后开启最长 8 秒的专用回应收音，无人说话不播放识别失败台词。
- 完成状态写入失败时每秒重试一次并保留明确日志，不在主循环里连续写闪存。
- 语音失败、服务器告别、手动退出、新唤醒和回应超时都会清除旧提醒上下文。

### 12.2 自动测试和编译

- 正式固件编译通过：内部内存 `92080 / 327680` 字节，占 28.1%；应用闪存 `1732369 / 2949120` 字节，占 58.7%。
- 服务器镜像内 25 项自动测试全部通过，其中包含正点和提前正文双位图注入，以及延后工具不伪造节点编号。
- 服务器和正式固件部署后，设备工具数量从 5 增加到 6，新增工具为 `tongdou.reminder.snooze`。

### 12.3 真机等比例结果

升级前设备已有旧格式节点 5 至 8；升级后第一个新事件从编号 9 开始，证明旧存储编号链没有被当成全新数据重置。

严格顺序测试使用事件 14：

```text
提前节点 15
  -> 喇叭排空
  -> 节点 15 提交完成
  -> 开启提醒回应窗口
  -> 不传 id 调用 snooze 成功
  -> 创建同 eventId=14 的延后节点 16
  -> 延后节点 16 到点、播报、排空并完成
  -> 正点节点 14 仍保留并最后触发
```

节点 16 比正点节点 14 早 27 秒，三段播报均有 `speaker drained` 和 `reminder delivered` 日志。无人回应时设备记录 `reminder response timeout state=idle`，没有播放失败补救台词。最后 `/api/reminders` 返回空数组，没有残留测试提醒。

删除测试另外创建事件 12，拿其中提前节点 13 执行删除，设备返回 `scope=event`，随后查询为空，证明整件事取消生效。

### 12.4 仍需用户真人确认

自动测试已经证明服务器会把“延后”工具调用原样转给设备，真机已经证明无编号提醒上下文能创建正确关联节点；最后仍需用户在一次真实提醒播完后亲口说“20 秒后再提醒我”，确认当前麦克风距离和现场噪声下的识别体验。完成这一步前，不把“真人语音延后”写成已验收。
